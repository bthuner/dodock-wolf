## Tamper-evident journal

Wolf records security-relevant changes in **Wolf Journal Entry** and chains them with an HMAC.
Editing, removing or reordering an entry breaks the chain.

### What is recorded

Each entry is written in the same transaction as the change:

- security events (their payload, as a SHA-256 digest);
- incident decisions: status, owner, merge, the NIS2, DORA and GDPR fields, auto-resolve and
  reopen;
- response actions and their results;
- comments on incidents;
- Wolf Settings changes: the names of the fields changed and who changed them, never the values.

Entries are read-only through Frappe: edits and deletions are refused.

### How it is signed

Every minute, the `chain_journal` job signs the waiting entries in creation order, under a lock:

```text
mac = HMAC-SHA256(key, seq|at|kind|record|digest|prev_mac)
```

An entry waits a minute at most before it is signed.

The key is `wolf_journal_key` in the site config. Wolf creates it on first use and never stores
it in the database, so someone who can only write the database cannot forge a chain.

::warning
Back up `wolf_journal_key` with the site config. Without it, the chain cannot be verified.
::

### Verify the journal

```bash
bench --site wolf.example.com wolf-verify-journal
bench --site wolf.example.com wolf-verify-journal --anchor <seq>:<mac>
```

Or click **Verify** on **Wolf → Security**. Both recompute every digest and mac, and find an
edited, removed or reordered entry.

Deleting the newest entries leaves a valid, shorter chain. To catch that, keep an **anchor**:

::steps{level="4"}
#### Copy the anchor

**Wolf → Security** shows the newest `seq:mac`.

#### Store it where Wolf cannot write

A ticket, a password manager, another server.

#### Check against it

Run `wolf-verify-journal --anchor seq:mac`. A chain cut before that entry fails.
::

::tip
The [SIEM export](/security/siem-export) can send every journal entry (seq, digest, mac) to your
collector. That external copy is the best anchor.
::

### Retention

**Wolf Settings → Journal Retention Days** (default `0`: kept forever). With a value set, the
nightly `purge_journal` job removes signed entries older than that, as the oldest part of the
chain:

- it first writes and signs a `journal_purge` entry that records where the purge stopped
  (`through_seq` and its mac), then deletes, under the signing lock;
- it always keeps the newest entry, and never removes an entry the SIEM export has not sent yet
  (when the export sends the journal);
- verification then requires a journal that does not start at entry 1 to start right after the
  newest purge record's cut. Deleting more of the oldest entries, or any without a purge, breaks
  it;
- an anchor in the purged part is reported as purged: copy a newer one. The cut itself still
  verifies, since the purge record keeps its mac.

## Deception: honeytokens

**Wolf Settings → Threat intelligence and deception**. Nobody legitimate knows a honeytoken, so a
single touch raises a critical `honeytoken_triggered` event. The preset *Honeytoken touched*
alerts on it. Each token raises at most one event per address every 10 minutes.

| Setting | One per line | Raises an event when | ATT&CK |
|---|---|---|---|
| **Decoy users** | an e-mail of an account nobody uses | any login attempt on it, failed or not (Activity Log) | T1078, T1110 |
| **Decoy API keys** | an API key, for example one left in an old backup or a repository | any request whose `Authorization` header (`token key:secret` or Basic) carries it | T1552 |
| **Decoy paths** | a path linked from nowhere, such as `/app/backup-admin` | any request for it | T1083 |

The decoy API key check runs before Frappe rejects the unknown key, and commits the event at once.

::caution
Do not create a decoy API key on a real user. The key only needs to appear in the setting.
::

## IP reputation lists

**Wolf Settings → Use IP reputation lists** (off by default).

- Once a day, the `refresh_reputation` job downloads the lists in **IP reputation lists** into
  `private/wolf/ip_reputation.json`.
- Each line of **IP reputation lists** is a name, then a URL or a file path relative to the site.
  Each list holds one address or CIDR per line. Prefilled:

  ```text
  firehol_level1 https://iplists.firehol.org/files/firehol_level1.netset
  spamhaus_drop https://www.spamhaus.org/drop/drop.txt
  ```

- At ingest, a security event whose payload `ip` is on a list gets
  `reputation: {listed, lists}` and one severity step more.
- Lookups never leave the site: only the lists are downloaded. A list that fails to download
  keeps its last copy.

::warning
Check each list's terms of use before enabling it.
::

The CEF format of the [SIEM export](/security/siem-export) carries the lists an IP is on in `cs5`.

Wolf can also read the decisions of a CrowdSec Local API (**Wolf Settings → CrowdSec**, off by
default). Events whose IP is under a CrowdSec decision are tagged and raised one step in the same
way. See [Response actions](/agent/response-actions).
