## Central

One Frappe 16 app and a Vue console (`/dashboard`) on **one global site**. It owns identity, teams, capabilities, the catalogue, billing, the list of regions and the managed services. It reaches a region only through `central/integrations/`.

**Stores.**

| Purpose | DocTypes |
|---|---|
| Teams and rights | `Team` (with an immutable 32-bit `tenant_id`; 0 is reserved for the platform), `Team Member`, `Team Role`, `Capability` (18, on two planes: `central` and `atlas`) |
| Regions | `Region`: the Atlas address, the proxy domain, one webhook secret for Atlas and one for Cargo, the telemetry data source |
| Keys | `Central SSO Settings`: three signing keys (see [Calls and trust](/internals/interop#keys)) |
| Servers | `Virtual Machine` (Central's record of a server), `Resource Action` (one row per create, start, stop, resize, terminate), `Pilot Credential`, `VM Snapshot`, `Team SSH Key`, `Firewall Ruleset`, `WireGuard Device` |
| Sites and routes | `Site` (only the site baked into a trial image), `Site Domain` (one proxy route per hostname) |
| Billing | About 55 DocTypes: `Plan`, `Subscription`, `Invoice`, `Usage Day`, `Usage Rollup`, `Credit Wallet`… |
| Feed | `Activity Event` (kept 365 days), `Team Notification`, 49 `Notification Event Type` |

There is **no Bench DocType and no deployment record**. What a server runs is Pilot's business.

**Accepts.**

| From | Entry | Authenticated by |
|---|---|---|
| A person | The console and `central.api.{servers,sites,snapshots,teams,ssh_keys,wireguard,firewall_rulesets,activity,…}` | A Frappe session, then a capability |
| Pilot | `central.api.pilot.*`, `central.notification.api.report_pilot_event`, about 28 `central.billing.api.billing_api.*`, `central.api.email_oauth.*`, `central.api.integrations.github.*` | Header `X-Pilot-Token`: 48 hex characters; Central stores only its SHA-256. The team and the server always come from the credential, never from the request |
| Atlas and Cargo | `central.api.state_delivery.receive` | `X-FC-Source`, `X-FC-Region`, `X-Frappe-Webhook-Signature` (HMAC-SHA256 with a secret per region and per sender) |
| Anyone | `central.api.jwks.get_jwks` | Nothing: public keys |
| A metered service | `central.billing.api.metering.report` | `X-Central-Service`, `X-Central-Signature` (HMAC) |
| Grove | `central.api.grove.datum_token` | `X-Grove-Token` |
| Payment gateways, GitHub | Their webhooks | Their own signatures |

**Calls.** Atlas, the proxy, the WireGuard gateway and Cargo of each region; Pilot on each server, through the proxy; Datum of one region, for its own errors and gauges; Grove; Stripe, Razorpay, PayPal; GitHub; a Helpdesk site for support tickets. Central is not on the private network of any region and never opens an SSH session to a server.

**To a customer it gives** the console: servers (create, start, stop, restart, resize, rename, terminate, rescue mode), firewall rulesets, public addresses, WireGuard devices, SSH keys, a web console, snapshots, "open bench" and "log in to the site as Administrator", buckets, AI keys, billing, team roles. It gives no API token page and sends no webhook to a customer. An ordinary Frappe API key of a team member does work against `central.api.*` (`suite_cloud` relies on it), but nothing in the console issues one.

## Atlas

The virtual machine manager of **one region with one provider** (AWS, Scaleway or generic hardware). A monorepo:

| Part | What | Runs |
|---|---|---|
| The Atlas app | Frappe 16 site, REST API under `/api/atlas` | One site per region, itself in a virtual machine on a host |
| `metald` | Go daemon: Firecracker, ZFS, network namespaces, eBPF | Every physical host |
| `atlas-guest-agent` | Static Go binary | **Inside every virtual machine image** |
| The proxy | OpenResty and a control daemon | 1 to 5 service machines |
| WireGuard mesh, IPv6 router, WireGuard gateway | eBPF programs and Python | Hosts and service machines |

**Stores.** `Virtual Machine`, `Virtual Machine State`, `Virtual Machine Image`, `Metal Server`, `Public IP Pool`, `Proxy Server`, `Cargo Server`, `SSH Task`, `Investigation`, and `Atlas Settings` (region id, wildcard domain and certificate, the region's signing key, Central's keys). On each host, `metald` keeps the machine's `config.json`, `status.json` and 7 days of 10-second samples.

**Accepts.** `Authorization: Bearer`, an Ed25519 token with audience `atlas-admin:<region>`, scope `*`, a `tenant` claim (`*` for Central, a number otherwise) and the header `X-Tenant-ID`. Routes: `virtual-machines` and their actions (`start`, `stop`, `pause`, `resume`, `restart`, `resize`, `snapshot`, rescue mode, `console-token`), `…/metrics`, `images`, `public-ips`, `webhooks`, `beacon/resources`, `hosts/<id>/access`, `dns-records`, `investigations`, and the public `jwks.json`. A tenant never holds an Atlas token: Central calls for it. Another tenant's record answers 404.

**Calls.** `metald` on each host (mutual TLS, port 9000, every 10 seconds); Central (the state webhook, and Central's keys every 5 minutes); Cargo (one bucket for its own images); Datum; hosts and service machines over SSH; Route 53; ACME; the hardware's management controllers.

**Also in Atlas.** A Warpgate bastion for staff access to hosts (signed in through Central, grants of 24 hours at most); an LLM "investigator" with read-only SQL on Datum and SSH to hosts, with no access to customer machines; "sleepy" machines that are frozen when no request arrives; rescue mode; live migration.

## Cargo

One Frappe site per region, on a platform machine (tenant 0) that is itself a Pilot bench. Three modules:

- **Image Builder.** It builds Pilot images (Base, Site, Apps) and one-click service images. A build is a virtual machine it rents from Atlas, provisions over SSH, stops, and snapshots. The **tags on the snapshot are the hand-over**: `purpose=pilot`, `pilot_version`, `frappe_version`, `has_site`, `app`. Central finds Pilot images by tag in Atlas; Cargo never tells Central about them.
- **Object Storage.** It runs the region's Garage (S3) cluster and creates buckets and keys when Central asks. A bench then speaks S3 to `https://s3-svc.<region domain>` directly.
- **Telemetry.** It installs and runs the region's **Datum and ClickHouse host**, and publishes the key set Datum trusts.

**Accepts.** Header `X-Cargo-Access-Token`: an Ed25519 token with audience `atlas-cargo:<region>`, signed by Central or by the region's Atlas. Methods: `cargo.api.webhooks.configure`, `cargo.object_storage.api.bucket.*`, two `one_click_image` methods. Public: `cargo.api.jwks.get_jwks`. For its own machines: `cargo.api.telemetry.datum_token` with `X-Cargo-Machine-Token`.

**Calls.** Atlas, as tenant 0, with a token Atlas gave it at install (scope `*`, 365 days); Central, with one webhook that says whether `storage` and `telemetry` are available and at which address; Datum; its own machines over SSH; GitHub for Pilot's releases and Frappe's branch heads.

A tenant never talks to Cargo.

## Pilot

"Frappe Server Manager", the successor of `bench`: a Python CLI, a Flask Admin API (about 300 routes) and a Vue Admin UI. It runs inside each server as one unprivileged user (`frappe`), in `~/pilot`. It has no database of its own: `bench.toml` per bench, `common_config.toml` per host, task folders, JSON logs.

It is one codebase for two cases. The switch is **`[central] enabled`** in `common_config.toml`.

| Behaviour | Self-hosted | Frappe Cloud v2 |
|---|---|---|
| Benches, sites, apps, Admin UI, tasks, sandbox, nginx, certificates, backups to S3, local metrics, uptime pings, webhooks, mail alerts, the marketplace registry, self-update | Yes | Yes |
| Telemetry to Datum | Only with `[telemetry] endpoint` and `token` set by hand | Token fetched from Central and renewed |
| Alerts to Central, the trial lock, private GitHub repositories through Central, billing in the site's Cloud Settings | No | Yes |
| Central signs in to the Admin | Only with `[admin] jwks_url` set by hand | Set at first boot |
| Routing of a new domain | A DNS check and a local certificate | A program from Cargo's image asks Central |

**Accepts.** The Admin API with a session cookie (the bench's Admin password, optional TOTP), a 5-minute token signed by Central (checked against Central's keys and the bench's audience; scope `bench`), or the site's own token (`pilot_auth_token`, HS256, 365 days, scope `site`). And the machine's metadata service, which is how Central's credential and first settings arrive.

**Calls.** Central (`X-Pilot-Token`); Datum; `github.com/frappe/marketplace` (git, at most hourly); `github.com/frappe/pilot` releases for its own update (00:00 UTC, on by default, no checksum or signature beyond TLS); the S3 bucket; Let's Encrypt; any `[[webhook_endpoints]]` the operator adds.

Details of what is on the server and what leaves it: [Inside a customer server](/internals/customer-server).

## Datum

One FastAPI process per region (two workers on `127.0.0.1:8000`, behind Caddy), on a host Cargo installs, next to ClickHouse. **It only writes.** There is no read route.

| Route | Body |
|---|---|
| `POST /v1/ingest` | JSON samples `{metric, value, ts, labels}` |
| `POST /v1/ingest/remote` | Prometheus remote write v1 |
| `POST /v1/logs/ingest` | Log lines |
| `POST /v1/traces` | OTLP over HTTP (no application in these repositories sends traces) |
| `GET /health` | Open |

**Authentication.** An Ed25519 token with audience `atlas-datum:<region>`, a `resource_id` (stamped on every row) and `access` containing `write`. Three issuers are accepted, told apart by the key id's prefix: `central:`, `atlas:<region>:`, `cargo:<region>:`. Limits: 12 requests per 60 seconds per resource and per route, in each worker; 10,000 samples, lines or spans per request. No queue and no retry on Datum's side.

**Tables** (database `datum`): `samples` (15 days for `system_*`, 90 days otherwise), `samples_recent` (2 days), `samples_5m` (90 days), `logs` (30 days), `traces` (7 days), and daily volume statistics.

**Three addresses**, all served by Caddy on the Datum host:

| Address | Goes to | Used by |
|---|---|---|
| `https://telemetry-svc.<region domain>` | Datum | Senders outside the private network (Central) |
| `http://internal-telemetry-svc.<region domain>` | Datum, plain HTTP on the private network | Pilot on customer servers, Cargo's machines. It is the address Cargo reports to Central |
| `https://telemetry-read-svc.<region domain>` | ClickHouse's HTTP interface | Beacon (user `beacon`), Insights (user `insights`) |

**The "Datum agent"** is Vector 0.59.0 with a fixed configuration, installed as root by Atlas or Cargo on **hosts, service machines and Cargo's machines**: host metrics, the journal at warning and above, nginx's `error.log`. It is not installed on customer servers.

The repository has **no license file**. Three consumers (Pilot's Admin, Cargo, Atlas) import its `datum_client` package from the `main` branch.

## Beacon

One Frappe 16 app on **one global site**, outside the regions it watches. Its home page is the status page. **It only pulls**: it has no agent and no ingest API.

**Inputs.**

| Input | How |
|---|---|
| Rules, service levels, charts | Files in each producer's repository (`beacon/rules/*.sql`, `*.http`, `*.tls`, `beacon/services/*.sql`, `beacon/charts/*.sql`), read through GitHub's API at the head of a branch, **only when an administrator presses Sync Definitions**. Each new query is run once before anything is saved |
| Telemetry | SQL on each region's ClickHouse, as user `beacon` (read only, 20 seconds, 100,000 rows, `SELECT` on `datum.*`). No row policy exists: `beacon` reads every tenant's rows of the region |
| The resource tree | `GET /api/atlas/beacon/resources` on each region's Atlas, every minute: Atlas, the hosts, every virtual machine (customers' included, with its host as parent), the service machines, Cargo |
| HTTP and TLS checks | Made from the Beacon site, every minute, on platform addresses only |

**What the producers declare.**

| Producer | Rules | Service levels | What they watch |
|---|---|---|---|
| Atlas | 36 | 5 (`servers`, `proxy`, three networking services; 99.9%) | Hosts, `metald`, the proxy, the mesh, certificates |
| Cargo | 21 | 1 (`object-storage`, 99.9%) | Image builds, Garage, and Datum itself |
| Central | 10 | 3 (`dashboard-api` 99.9%, `server-actions` 99%, `billing` declared) | API errors, payments, stuck actions |
| Pilot | 5 | 1 (`sites` 99.9%, hidden from the status page) | The only rules that read customer servers' data |

**From alert to person.** Rule → Alert (Pending, Firing, Resolved) → Incident, grouped by the resource tree. Every incident posts to a chat webhook. High and Critical also send email and call the responders through Twilio, one after another (the next after 2 minutes for Critical, 5 for High; a new round every 15 minutes). Answering the call acknowledges. Service levels raise burn alerts over two windows (14.4× over 1 hour and 5 minutes; 6× over 6 hours and 30 minutes; 1× over 3 days and 6 hours, which never pages).

**To a customer it gives** the public status page, a per-incident RSS feed and email subscription. Nothing else: no account, no API.

## Around the six

| Repository | What | Link to the six |
|---|---|---|
| `cloudtoolkit` (AGPL-3.0) | Durable pipelines and an SSH client, taken from Press' workflow engine | Only Cargo requires it |
| `marketplace` | The registry of 132 installable apps, one JSON per app | Pilot clones it for `get-app`; Cargo reads Pilot's copy to choose the apps of a signup image. A new app that passes the automated check merges by itself |
| `one-click-templates` | Redis, MariaDB, Prometheus and Grafana as ready servers | Cargo builds each into an Atlas image; Central writes the customer's answers to `/etc/one-click/inputs.env` through cloud-init. These servers have no Pilot |
| `grove`, `pathway` (MIT) | An AI inference platform: a Frappe control plane and a Go gateway | Central creates teams and keys in Grove, reads usage hourly to bill it, and signs Datum tokens for Grove's machines. Grove's machines come from AWS and RunPod, not from Atlas |
| `suite_cloud` (AGPL-3.0) | Mail servers of Frappe Suite | A customer of Central like any other: it creates servers with a team member's API key and drives Pilot. Its mail clusters are outside Frappe Cloud v2 |
