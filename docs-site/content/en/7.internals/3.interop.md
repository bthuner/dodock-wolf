The applications share no database. Each link below is an HTTPS request, except where it says otherwise.

## The calls

### Control

| From → to | What | Authenticated by |
|---|---|---|
| Console → Central | Everything a person does | Frappe session, then a capability |
| Central → Atlas | `{region}/api/atlas/…`: machines and their actions, images, metrics, hosts | Token `atlas-admin:<region>`, 5 minutes, `tenant=*`, plus `X-Tenant-ID: <team's tenant number>` |
| Atlas → Central | `vm.state` and `vm.state.deleted` to `central.api.state_delivery.receive` | HMAC-SHA256 of the body, with a secret Central set through `PUT /api/atlas/webhooks` |
| Central → Cargo | `cargo.object_storage.api.bucket.*`, one-click images, `webhooks.configure` | Header `X-Cargo-Access-Token`: token `atlas-cargo:<region>`, 5 minutes |
| Cargo → Central | `storage` or `telemetry` is `Available` or `Not Available`, and at which address | HMAC, as Atlas. Cargo holds no credential of Central |
| Cargo → Atlas | Rents machines, sets their metadata and firewall, snapshots them into images, DNS records | Token `atlas-admin:<region>` as tenant 0, scope `*`, **365 days**, given at install |
| Atlas → Cargo | One bucket for Atlas' own images | Token `atlas-cargo:<region>`, 5 minutes |
| Atlas → hosts | `metald`, port 9000, every 10 seconds | Mutual TLS, a private authority per region |
| Central → the proxy | `PATCH` and `DELETE` on `/v1/sites/<name>` and `/v1/domains/<domain>` | Token `atlas-proxy:<region>`, scope `site:* domain:*` |
| Central → the WireGuard gateway | `/v1/peers` | Token `atlas-wg-gateway:<region>` |
| Central → Pilot | `https://admin-vm-<label>.<region domain>/api/v1/…`: site login, rename, domains, apps, settings | Token signed with Central's Pilot key, audience = that bench's id, scope `bench` or `site`, 5 minutes. **Through the public proxy**, not the private network |
| Pilot → Central | `central.api.pilot.*`, `report_pilot_event`, billing, GitHub tokens | Header `X-Pilot-Token`, read from the machine's metadata at each call, never written to disk |
| A site → Pilot → Central | `GET` or `POST /api/v1/sites/<site>/central/<method>` on the loopback, for an allowlist: `heartbeat`, `get_team_identity_token`, `email_oauth.*`, `billing_api.*` | The site's `pilot_auth_token`, then `X-Pilot-Token` |
| Cargo's domain program → Central | `central.api.pilot.domain_records`, `register_domain`, `deregister_domain` | `X-Pilot-Token` (the program is on the server; Pilot runs it) |

### Telemetry

| From → to | What | Authenticated by |
|---|---|---|
| Pilot → Datum | Eight metrics and update events ([the list](/internals/customer-server#what-leaves-the-server)) | Token `atlas-datum:<region>` signed by Central, 7 days, `resource_id` = the machine's Atlas id |
| `metald` → Datum | `system_*` and `metal_*` of each host. A machine id is never a label | Token signed by Atlas, 7 days, renewed daily at 03:30 |
| Vector → Datum | Journal and machine metrics of hosts, service machines and Cargo's machines | Same, or a token from Cargo |
| Atlas → Datum | `atlas_*`, its Error Logs, `bmc_*` | Token signed by Atlas, 5 minutes |
| Cargo → Datum | `cargo_*`, its Error Logs | Token signed by Cargo, 7 days |
| Central → Datum | `central_*`, its Error Logs, to **one** region | Token signed by Central |
| Datum → ClickHouse | Inserts, on the loopback | A ClickHouse password |

### Reading and alerting

| From → to | What | Authenticated by |
|---|---|---|
| Beacon → ClickHouse | SQL through `https://telemetry-read-svc.<region domain>` | Basic authentication, user `beacon`, read only |
| Beacon → Atlas | `GET /api/atlas/beacon/resources`, every minute | A Frappe API key. Atlas gives that route only to Central's identity, and treats a System Manager as Central: so Beacon holds a **System Manager key on every region's Atlas** (inferred from both ends of the code) |
| Beacon → GitHub | The rule files of each producer's repository | An optional GitHub token |
| Beacon → Twilio, chat, email | Calls and messages | A Twilio API key; the secret in the chat webhook's address |
| Twilio → Beacon | The call's status | An HMAC in the callback's address |
| Central → ClickHouse | Billing reports and the operator's investigator, through an Insights data source | A ClickHouse password |
| Atlas → ClickHouse | The investigator's read-only SQL | A ClickHouse password |

The chart of a server in Central's console does **not** come from Datum: Central asks Atlas (`…/virtual-machines/<id>/metrics`).

## Keys

| Key | Held by | Signs |
|---|---|---|
| Atlas plane key (Ed25519) | Central | Every token for a region: `atlas-admin`, `atlas-proxy`, `atlas-cargo`, `atlas-wg-gateway`, `atlas-datum` |
| Pilot key (Ed25519) | Central | Tokens for a server's Admin, and team identity tokens |
| OIDC key (RS256) | Central | Sign-in to Warpgate and internal tools |
| Region key (Ed25519) | Each Atlas | The same five audiences, for its own region |
| Cargo key (Ed25519) | Each Cargo | Datum tokens and its machines' tokens |
| Site secret (HS256) | Each bench (`bench.toml`) | Admin sessions and each site's `pilot_auth_token` |

No rotation is implemented for any of the Ed25519 keys.

### The chain of public keys

Each verifier fetches its keys from the layer above it:

1. **Central** publishes its Pilot and Atlas plane keys together at `central.api.jwks.get_jwks`.
2. **Atlas** fetches them every 5 minutes and publishes them with its own key at `/api/atlas/jwks.json`. The proxy, the WireGuard gateway and Cargo check tokens against that set.
3. **Cargo** adds its own key and publishes the three at `cargo.api.jwks.get_jwks`.
4. **Datum** is configured with Cargo's address, and nothing else.

So Datum trusts Central and Atlas through Cargo, and a customer's Pilot trusts Central directly (the keys come with the machine's metadata, then from Central's address).

Because one set carries keys of two planes, every verifier has to check the audience and the scope, not the signature alone. Pilot checks the signature and the audience, not the issuer.

## Tokens

| Token | Signed by | Audience | Lifetime | Carries |
|---|---|---|---|---|
| Region call | Central | `atlas-admin:<region>` | 5 min | `scope=*`, `tenant=*` |
| Proxy route | Central | `atlas-proxy:<region>` | 5 min | `scope="site:* domain:*"` |
| Cargo call | Central or Atlas | `atlas-cargo:<region>` | 5 min | Cargo checks no scope: any valid token may call every method |
| Datum write, for a Pilot | Central | `atlas-datum:<region>` | 7 days | `resource_id`, `access=["write"]` |
| Datum write, for a host | Atlas | `atlas-datum:<region>` | 7 days | Same |
| Cargo's token for Atlas | Atlas | `atlas-admin:<region>` | 365 days | `tenant=0`, `scope=*` |
| Cargo's token for the proxy | Atlas | `atlas-proxy:<region>` | 365 days | Sites whose name ends in `-svc` only |
| A Cargo machine's token | Cargo | `cargo:machine` | No expiry | Honoured while the machine's record says Running |
| Admin API call | Central | The bench's id | 5 min | `scope=bench`, `sub=admin` |
| Site login | Central | The bench's id | 5 min | `scope=site`, the site |
| Open bench | Central | The bench's id | Session length (60 min by default) | Single use |
| Team identity | Central | An address the site chooses | 5 min | `sub=<team>`, `team_name`, `hosts` (the server's site addresses) |
| Web console | Atlas (random, not a JWT) | — | 30 s | Single use, in the address' fragment |
| `X-Pilot-Token` | Central (random, not a JWT) | — | Until the machine is deleted or staff revoke it | Central keeps its SHA-256 |
| `pilot_auth_token` | The bench | — | 365 days | `scope=site`, one site |

There is no revocation list anywhere. A 7-day Datum token of a deleted server is valid until it expires, and Pilot renews by expiry only (when 24 hours or less remain).

## Secrets on the way to a machine

Central passes the customer's `user_data` (16 KiB at most) to cloud-init unchanged and stores it on the `Resource Action`, so its own specification says it must hold no long-lived secret.

The platform's own secrets travel through the **machine's metadata**, the service at `169.254.169.254` inside the machine:

| Attribute | Contains | Applied by Pilot to |
|---|---|---|
| `pilot-central` | Central's address, the `X-Pilot-Token`, the address of the keys, the bench's audience id, a first copy of the keys | Nothing: read at each call |
| `pilot-common-site-config` | `fc_team`, the SMTP settings of a pooled mailbox, AI keys on a trial | `sites/common_site_config.json`, once |
| `pilot-common-config` | The Let's Encrypt contact, `telemetry.endpoint` | `common_config.toml`, once |
| `pilot-config` | The `[s3]` backup bucket's keys, when the plan includes storage | `bench.toml`, once |

SSH keys take the same way: Atlas serves the authorized keys from the metadata at each login, so `~/.ssh/authorized_keys` of an image holds nothing (Pilot's Admin can still write to it).

## Where the regions meet the customer

| Name | Where TLS ends | What the server receives |
|---|---|---|
| `<site>.<region domain>` | At the proxy, with the region's wildcard certificate | Plain HTTP on port 80, from the proxy's private address, with `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` |
| A custom domain | On the server | The TLS stream on port 443, passed by SNI, with a PROXY protocol v2 header. Pilot holds the certificate; HTTP-01 challenges reach port 80 |
| `admin-vm-<label>.<region domain>` | At the proxy | Pilot's Admin |

A 502 or 504 the proxy makes itself (server stopped, asleep, unreachable) never reaches the server's logs. The proxy counts it, in aggregate, with no series per site.

Servers of one team in one region share a private IPv6 network (`fdaa:<region>:<tenant>::/64`), separated from other teams in eBPF on the hosts. It does not cross regions. The platform's service machines are reachable on it.
