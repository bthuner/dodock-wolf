Everything here is planned or to check, not built. The decisions are tracked in [#136](https://github.com/bthuner/dodock-wolf/issues/136) and the three reviews [#133](https://github.com/bthuner/dodock-wolf/issues/133) (Datum), [#134](https://github.com/bthuner/dodock-wolf/issues/134) (Central) and [#135](https://github.com/bthuner/dodock-wolf/issues/135) (Beacon).

## Two grounds

Dokos will operate its own Frappe Cloud v2, with **dokopilot**, its fork of Pilot, in the servers. So Wolf stands on two grounds, and each idea below says which one it is for:

| Ground | Who holds what | What it changes |
|---|---|---|
| **Dokos' own platform** | Dokos runs Central, Atlas, Cargo, Datum and Beacon. It holds the signing keys, the ClickHouse passwords, Desk on every application, and the script that builds the images | Most bridges are open: Wolf can be in the image, call Beacon, receive Central's events |
| **Pilot alone** | An operator runs Pilot (or dokopilot) on its own machines, with no Central, Datum or Beacon. Or is a customer of someone else's platform | Only what is on the server counts: its files, its logs, Pilot's webhooks |

## The finding that holds

No Frappe Cloud v2 application reads the inside of a bench. Central has no log, no per-site error and no security signal of any kind. Datum receives eight metrics and update events from a customer server. Beacon ignores a single failing site by design. Atlas sees a machine from its edge.

So on a customer's server the Wolf Agent is the only collector of: per-site 5xx, Frappe tracebacks, scheduler and worker failures, Frappe logins and role changes, SSH and sudo, attacks seen in nginx, file integrity, outbound connections. That is the ground [#136](https://github.com/bthuner/dodock-wolf/issues/136) chose.

## What this reading corrects in the reviews

| Review said | The code says |
|---|---|
| Central merges `fc_team` into the server's `common_site_config.json` (#134) | Central puts it in the machine's metadata (`pilot-common-site-config`); **Pilot** merges it once, at first boot. Pilot's code never names `fc_team` |
| The Pilot API of Central is `heartbeat`, `datum_token`, `register_domain`, `get_team_identity_token`, `report_pilot_event` (#134) | It is more than 40 methods: also `config`, `get_server_access`, `storage_regions`, `domain_records`, `deregister_domain`, about 28 billing methods, mailbox OAuth, GitHub repository tokens. `report_pilot_event` is at `central.notification.api` and takes only fixed event types |
| `get_team_identity_token` is hard for an app to reach (#134) | A site already reaches it: `POST /api/v1/sites/<site>/central/central.api.pilot.get_team_identity_token` on `pilot_endpoint`, with the site's own `pilot_auth_token`. Central answers with a 5-minute token for any audience the site names |
| The default firewall allows outbound traffic (#134) | The firewall is off by default: everything is allowed, in and out |
| `server_metrics` are samples taken from outside the machine (#134) | Partly: a guest agent in every image adds load, memory, root file system use and the system's state |
| On a customer server Pilot sends a heartbeat, site counts, backup status, `pilot_database_up`, disk, update events (#133) | Also `pilot_central_requests_last_5_minutes`, and `pilot_site_backup_failed` with the **site's name**. Update events carry the site and up to 8,192 characters of output |
| Datum accepts tokens from Central, Atlas or Cargo (#133) | Yes, and it learns all three keys from **Cargo's** address only |
| Datum's documents say RSA/ECDSA (#133) | `docs/tokens.md` now says Ed25519. One comment in `CLAUDE.md` still says otherwise |
| Reading Datum needs a row policy on `resource_id` (#133) | There is no row policy at all: a reader sees the whole region |
| Beacon's bridge: `POST /api/resource/Beacon Incident` with a Responder key, then `page_on_call` (#135) | Confirmed, with two cautions. `page_on_call` pages at **any** severity. And the controller only defaults `visibility` and `status` when they are empty, so a Responder key can probably create a Public incident (inferred) |
| Beacon requires Insights (#135) | Only for Beacon's own health dashboard, read from Beacon's database. Beacon reads ClickHouse by itself |
| Trial servers sleep when idle (#134) | And they are **locked**: no SSH, no console, no Admin until the trial is converted |

## What to build, cheapest first

### 1. Recognise a Frappe Cloud v2 server

| Signal | Where | Read by |
|---|---|---|
| `[central] enabled = true` | `~/pilot/benches/common_config.toml` | The agent at discovery (root) |
| `fc_team` | `sites/common_site_config.json` | Same |
| `[telemetry] endpoint` is set | `common_config.toml` | Same. Never read `token` |

Report `platform: frappe-cloud-v2` and the team id in the registration and the inventory. Do not use `pilot_endpoint`: a self-hosted Pilot writes it too.

### 2. Stay quiet about what the platform does

- Do not raise "agent silent" for a server that can sleep. The case is narrow: a paid server is created without idle sleep, and a trial server is locked, so it has no agent. Label a sleeping server; do not page for it.
- A root login from `172.16.0.x` or on `ttyS0` is the web console, started from Central by a team member. Show it as such; it stays worth showing.
- Outbound HTTP to `internal-telemetry-svc.<region domain>` and HTTPS to Central are Pilot. They are not exfiltration.
- Requests arriving from the proxy's network carry the client in `X-Forwarded-For`; a custom domain's come with a PROXY protocol header. Attribute by those, and only when the peer is in `fdaa:<region>::/64`.
- Pilot restarting the bench after 900 idle seconds, or itself at 00:00 UTC, is not a crash.

### 3. Signals this reading adds

| Signal | Why | Source |
|---|---|---|
| A process other than Pilot reads `169.254.169.254` | The answer holds the server's `X-Pilot-Token`. Code that took over a site would want it | Outbound connections; the agent must never make that request itself |
| `[telemetry] token`, `[s3]` keys, the SMTP password and `ai_keys` sit in files the bench user reads | They belong in the list of secrets the scrubber never ships and file integrity watches | `common_config.toml`, `bench.toml`, `common_site_config.json` |
| A new SSH key leaves no file change | On these servers the keys come from the metadata at each login. Watching `authorized_keys` sees only keys added in Pilot's Admin; `auth.log` stays the signal | `auth.log` |
| Admin sessions and logins | Pilot keeps them, with the address, in `logs/audit_<year>_<week>.jsonl`. Admin access is shell access as the bench user | A new reader in the agent |
| The Administrator password of a fresh server | Probably shared by every server of one image until changed (to check). The preset *Admin login from new IP* matters most in a server's first hour | Existing rule |
| Pilot's self-update | It replaces Pilot's tree from a GitHub release with no signature. A change of Pilot's files outside 00:00 UTC is worth a line | File integrity |

### 4. Receive Pilot's events without Frappe Cloud

Pilot posts every bench event (`site_down`, `task_failed`, `backups_failing`, `resource_limit_breached`…) to each `[[webhook_endpoints]]` entry, signed with HMAC-SHA256 (`X-Pilot-Signature-256`). It works on a self-hosted Pilot too. A Wolf endpoint that accepts them would give deployments and backup failures without the root helper `wolf-pilot-export` reading task folders. It is the cheapest new bridge, it needs nothing from Frappe, and it serves both grounds.

### 5. Register a site without a shared secret

The team identity token makes the spike of #134 concrete:

1. The Wolf App on a customer's site calls its own Pilot with `pilot_auth_token`, asking for a token whose audience is the hosted Wolf site's address.
2. Central returns a 5-minute token signed with its Pilot key: `sub` is the team, `hosts` the server's site addresses.
3. The hosted Wolf site checks it against `central.api.jwks.get_jwks`: signature, `aud` equal to its own address, `scope=team-identity`, `exp`, and that the caller's host is in `hosts`.

That proves "this site belongs to team T on Frappe Cloud" without any secret typed by a person. It needs the site's `pilot_auth_token`, so it runs in the Wolf App, not in the agent.

### 6. Show the platform's incidents as context

`GET /api/method/beacon.api.status.get_status` on the status page's domain is open and cached 60 seconds. Polling it lets a Wolf incident say "the platform reports an incident on this region since 01:52". It opens no Wolf incident. It is the only Beacon signal a customer can read; on its own platform Dokos can also read Beacon's incidents over REST.

### 7. A Beacon channel

As planned in #135. On Dokos' own platform there will be a Beacon, with the people on call. Wolf keeps bench, site and security incidents; a critical one creates a Beacon incident, so the same rotation is called and the incident is one, in one place. Keep the two cautions above: never page below critical, never set `visibility`. Beacon never resolves an incident a person or an API created, so Wolf resolves it. For Pilot alone there is no Beacon: Wolf's own channels stay.

### 8. Put Wolf in the image

Dokos' Cargo builds the Pilot images with a script (`provision.sh`). The Wolf Agent, its `[[webhook_endpoints]]` entry and the Wolf App can be installed there, with no secret: at first boot the site registers with the team identity token (step 5). This replaces installing through `user_data`, which is stored in clear on the `Resource Action`.

### 9. Receive Central's events

Central gives a customer no token and no webhook. On Dokos' own Central, a standard Frappe Webhook on `Activity Event` (server created, resized, restarted, snapshot restored, SSH console opened) towards Dokos' Wolf site needs no change of code. Those events then sit on the timeline next to what the agent saw.

### What depends on the ground

| Idea | On Dokos' own platform | With Pilot alone, or as someone's customer |
|---|---|---|
| Write Wolf's findings to Datum | Possible with a change in Central: it already signs Datum tokens for a fourth sender, Grove, under the prefix `grove:`. Only useful if Beacon should read Wolf's findings as rows | No: Datum accepts three issuers, and a customer holds none |
| Read Datum | Possible: Dokos holds the ClickHouse passwords. Such a reader sees the whole region, so only from Dokos' own Wolf site | No |
| A server's events (resize, restart, snapshot) | A Frappe Webhook on Dokos' Central (step 9) | No customer token, no outbound webhook. `Activity Event` is console only |
| Report a Wolf alert to Central | A change in dokopilot or Central could open a way. Using Pilot's token from Wolf would still be impersonation | `report_pilot_event` belongs to Pilot's credential and takes fixed event types |
| Install the agent at server creation | In the image (step 8) | Through `user_data`, with a short-lived, single-use token only |
| Changes in Pilot ([#114](https://github.com/bthuner/dodock-wolf/issues/114)) | Changes in dokopilot, kept small so the fork can still take Frappe's releases | Asks to Frappe |

Not decided: whether the Wolf Agent also runs on the platform's own machines (hosts, the proxy, Cargo's machines). Vector collects their metrics and journal there; nothing looks at their security.

## What the operator inherits

Read from code, not reported to Frappe, and not checked on a running region. They are properties of a young platform. Running it makes them Dokos' own, so they belong in its risk register and in the hardening of its first region.

- **Datum has no license.** The whole stack needs it: Pilot's Admin, Cargo and Atlas import its client. To settle with Frappe before anything else.
- **Site names and update output reach the platform's telemetry**, where Beacon's reader and Insights see the whole region. Dokos is then the one who holds them, for its customers.
- **The operator can read a server's disk** (snapshot, rescue mode) and its serial console. That is true of any host; here it is explicit in the code, and Dokos' customers should be told.
- **The 7-day Datum token of a deleted server stays valid** until it expires. It only writes.
- **Pilot's self-update is not signed.** Whoever can publish a release runs code as the bench user on every server at 00:00 UTC. With dokopilot, that is Dokos' release channel to protect.
- **The marketplace merges a new app by itself** when the automated check passes. Any bench can install anything in it.
- **One key set serves two planes** at Central, and Pilot does not check a token's issuer. Safety rests on audiences.
- **Beacon holds a System Manager key on every region's Atlas** to read one list (inferred).
- **No key rotation** is implemented for the signing keys, and several platform tokens last 365 days.
- **Cargo's SSH client does not verify host keys**; it relies on the private network.

## To check on a real server

Dokos will run its own Frappe Cloud v2, with dokopilot in the servers. The first server of its first region should answer:

- [ ] The paths: `/home/frappe/pilot/benches/default-bench`, `logs/` or `logs/workload/` (is the bench sandboxed on Ubuntu 26.04?), the nginx log's format and what `$pilot_client_addr` holds for a region name and for a custom domain.
- [ ] Lite mode: which log files exist, and where scheduler failures are written.
- [ ] `wolf-agent discover` as root: bench, sites (folder name against public name), domains.
- [ ] The markers: `[central]`, `[telemetry]`, `fc_team`, and that no file holds the `X-Pilot-Token`.
- [ ] `auth.log` for a key from the console, a web console session (SSH and serial), and Central's "open bench".
- [ ] Outbound HTTPS to the Wolf site with the firewall off, then on. The private network between two servers of the team.
- [ ] Whether a paid server ever sleeps, and what the agent's spool does across a freeze.
- [ ] Whether the Admin and Administrator passwords differ between two servers of one image.
- [ ] A snapshot while the agent tails logs.
- [ ] `[[webhook_endpoints]]` towards a test receiver: the events and their bodies.
- [ ] The team identity token, from a site, for a test audience.
- [ ] The status page's `get_status`: its shape, and whether a region can be told apart.
