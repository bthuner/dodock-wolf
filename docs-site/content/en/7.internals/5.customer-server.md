A customer server is a Firecracker virtual machine that boots an image Cargo built, with root SSH for the customer. This page is what a tool running on that server should expect. None of it was checked on a running server yet: the list of what to verify is in [Notes for Wolf](/internals/wolf#to-check-on-a-real-server).

## What is there

### From Atlas, in every image

| What | Detail |
|---|---|
| `atlas-guest-agent` | `/usr/local/lib/atlas/atlas-guest-agent`. Four socket units, `atlas-guest-agent-{usage,freeze,grow,reboot}.socket`, on vsock ports 100000 to 100003: the host asks for usage, freezes file systems before a snapshot, grows the disk, reboots. A firewall in the machine cannot block vsock |
| `atlas-metadata.service` | Polls the metadata service (`169.254.169.254`) every 250 ms: hostname, private address, MTU, routes. Steps the clock forward after the machine was frozen |
| SSH keys from metadata | `/etc/ssh/sshd_config.d/90-atlas-mmds.conf`: sshd runs `atlas-guest-agent authorized-keys` at each login. A key added in the console changes no file on the server |
| cloud-init | `/etc/cloud/cloud.cfg.d/99-atlas-datasource.cfg`, data source `Atlas`; a serial console on `ttyS0` |
| Network | `eth0`, a private IPv6 `fdaa:<region>:<tenant>::<machine>`, MTU 1380, IPv4 to the internet through the host's NAT |

### From Cargo's Pilot image

| What | Detail |
|---|---|
| User | `frappe`, uid 1000. Every other regular user of the Ubuntu image is removed |
| Pilot | `/home/frappe/pilot`, at a fixed release |
| Bench | `/home/frappe/pilot/benches/default-bench`, on MariaDB (`~/pilot/databases/mariadb/run/mysqld.sock`), `restart_idle_seconds = 900` |
| Site | `site.local` on Site and Apps images. It is reached through the alias `*.<region domain>`: **the site's folder name is not its public name** |
| Admin | Domain `admin.local`, reached as `admin-vm-<label>.<region domain>` |
| nginx | Enabled, without TLS for the region's names |
| The domain program | `/usr/bin/bench-domain-provider` |
| Units | `pilot-vm-memory.service` (zswap, 1 GB of swap), `pilot-prewarm.service`, `pilot-grow-file-system@.service` |

An image holds no token, no telemetry setting, no SSH key and no trace of a team. Each build generates one random Admin password and one Administrator password inside the build machine. The build script does not rotate them, so they are probably the same on every server started from one image until something changes them (inferred, to check).

### From Pilot, as on any Pilot host

- systemd **user** units of `frappe`: `<bench>.target`, `<bench>-web` (with its socket), `<bench>-socketio`, `<bench>-worker_pool…`, the two Redis, `<bench>-admin`, `<bench>-central-bootstrap`; and `pilot-monitor.service`, `pilot-mariadb.service`, `pilot-certificates.timer`. The default is "lite mode": one process for web, realtime and jobs.
- `/etc/nginx/conf.d/00-pilot.conf`, `/etc/logrotate.d/pilot` (500 MB, `copytruncate`), sudo rules for nginx and certbot.
- Logs in `<bench>/logs/`, and Frappe's own logs in `<bench>/logs/workload/` on a sandboxed bench. Units write to files there, not to the journal.
- `<bench>/logs/nginx-access.log`, in Pilot's own format: `$pilot_client_addr [$time_local] "$request_method $uri" $status "$host" $request_time`. Only `location /` of the sites is logged: not `/assets`, `/files` or `/socket.io`.
- Local signals: `logs/uptime.json.log`, `logs/audit_<year>_<week>.jsonl` (Admin sessions and logins, with the address), `tasks/<id>/`, `~/pilot/system/logs/system-stats.log`, `updates_<year>_<week>.jsonl`, `central-requests_<year>_<week>.jsonl`.
- No host firewall and no fail2ban. Pilot's `[firewall]` is an allow and deny list in nginx.

Wolf's Pilot support already reads this layout: see [Pilot benches](/install/pilot).

### From Central, at first boot

Through the metadata attributes ([the table](/internals/interop#secrets-on-the-way-to-a-machine)):

| Marker | File |
|---|---|
| `[central] enabled = true`, `bootstrapped = true`, `[[central.hostname_aliases]]` | `~/pilot/benches/common_config.toml` |
| `[telemetry] endpoint`, `token` | Same file. The token is a 7-day Datum write token, in clear |
| `[admin] jwks_url`, `jwks_audience` | Same file |
| `fc_team` (the team's id), SMTP settings of a pooled mailbox, `ai_keys` on a trial | `sites/common_site_config.json` |
| `[s3]` keys of the backup bucket, when the plan includes storage | `bench.toml` |
| `pilot_endpoint`, `pilot_auth_token`, `cloud_server_url` | Each `site_config.json` |

`pilot_endpoint` is **not** a sign of Frappe Cloud v2: a self-hosted Pilot in production writes it too. `[central] enabled` and `fc_team` are.

::caution
`http://169.254.169.254/latest/meta-data/attributes/pilot-central` returns the server's `X-Pilot-Token` to any process outside the bench's sandbox. With it a process can ask Central for the team's billing methods, a Datum token, or a GitHub repository token. A tool on the server must never read it. A process that does is a signal worth an alert.
::

## What leaves the server

Everything Pilot sends to Datum, from `pilot/core/server/monitoring_datum.py`:

| Signal | Every | Labels |
|---|---|---|
| `pilot_sites` | 60 s | `state`: `up`, `down`, `app_error`, `maintenance` |
| `pilot_info` (the heartbeat) | 5 min | `version` |
| `pilot_database_up` | 5 min | — |
| `system_filesystem_size_bytes`, `system_filesystem_available_bytes` | 5 min | `mountpoint`, `device`, `type` |
| `pilot_central_requests_last_5_minutes` | 5 min | `method`, `result` |
| `pilot_site_backups` | 5 min | `status` |
| `pilot_site_backup_failed` | 5 min | **`site`: the site's name** |
| Update events, as log lines | 5 min | `app`, `repository`, versions, `status`, `phase`, **`site`**, and up to the last 8,192 characters of a failed task's output |

And to Central: the event types of [A customer is told](/internals/flows#a-customer-is-told), with a message.

**What stays on the server**: CPU, memory, load, network and MariaDB metrics (Pilot collects them every 10 seconds, into local files only); the journal; nginx's access and error logs; every bench log; scheduler and worker failures; `auth.log`; Frappe's Error Log, Activity Log and Access Log.

Beacon's telemetry contract says "A tenant VM sends no machine metrics" and "a site is never a label value". The first holds. The second does not: a failed backup sends the site's name, and a failed update sends the site and its output.

## What the platform sees from outside

Without anything in the machine's bench, through the host and the guest agent:

- CPU time, memory (from the balloon device), disk size, use and I/O, network bytes and packets at the machine's interface, with counters of sent ICMP, UDP, TCP SYN and TCP RST;
- load average, `/proc/meminfo`, use of the root file system, and `systemctl is-system-running`, from the guest agent;
- whether the machine answers a ping, every minute;
- the serial console's output (128 KiB kept, even with nobody watching);
- at the proxy: request counts and times for the region's names, in aggregate.

Staff with access to a host can snapshot the disk or mount it in rescue mode. The platform does not see inside TLS for a custom domain, and reads no log or process list of the machine.

## How a server behaves

| Behaviour | Consequence for a tool on the server |
|---|---|
| **Sleep.** A trial server (and a staging team's) is frozen when no request arrives for a while, and wakes on traffic. Outbound connections do not keep it awake. Paid servers are created with `sleep_after_idle_seconds: 0` | A timer stops and resumes with a jump of the clock. Silence is not an outage |
| **Trial lock.** While a free trial is open: no SSH, no web console, no Pilot Admin | Nothing can be installed |
| **Warm start.** Base and Apps images resume from a memory snapshot | Boot id, machine id and process start times may be shared between servers of one image (inferred). The journal starts nearly empty |
| **Snapshot.** File systems are frozen for up to 30 seconds | A log reader sees a pause in writes |
| **Idle restart.** In lite mode the bench process restarts after 900 seconds without work | It is not a crash |
| **Firewall.** Off by default, which allows everything in both directions. Once on, a direction without a rule blocks new connections | An agent's outbound HTTPS needs a rule then |
| **Console logins.** The web console signs in as root from a host-side address (`172.16.0.x`) with a temporary key, or on `ttyS0` | An unusual root login that the customer started |
| **Self-update.** Pilot updates itself at 00:00 UTC and restarts each Admin | Paths can move between releases |
| **Addresses in logs.** For the region's names, nginx sees the proxy's private address; the client is in `X-Forwarded-For`. For a custom domain it comes in the PROXY protocol header | Trust those only from the proxy's network, `fdaa:<region>::/64` |
