Each step names the application that acts. Tokens and headers are in [Calls and trust](/internals/interop).

## A server is created

1. **Console → Central.** A team member calls `central.api.servers.create_server`. Central checks the `server:create` capability and the billing gate, and stores a `Resource Action`.
2. **Central.** For an image tagged `purpose=pilot`, Central creates the server's `X-Pilot-Token` and prepares the four metadata attributes (`pilot-central`, `pilot-common-site-config`, `pilot-common-config`, `pilot-config`).
3. **Central → Atlas.** `POST /api/atlas/virtual-machines` with the image, the size, the SSH keys, the customer's `user_data`, the firewall, the idle sleep, the metadata, and `X-Tenant-ID`. A request that fails in transit is marked uncertain and is never sent again by itself.
4. **Atlas → `metald`.** Atlas picks a host. `metald` clones the image's disk (ZFS), builds the network namespace, registers the private address, starts a jailed Firecracker, and fills the metadata service.
5. **In the machine.** `atlas-metadata.service` sets the hostname, the private address and the routes. cloud-init runs the `user_data`. Pilot's `<bench>-central-bootstrap.service` polls the metadata every 0.1 second until the credential is there, applies the three settings once, stores Central's keys, and sets `central.bootstrapped`.
6. **Atlas → Central.** The host is read every 10 seconds; a change of state is posted as `vm.state`. Central also reconciles every 10 minutes, which repairs a missed report.
7. **Central → Pilot.** Central builds the name `admin-vm-<label>.<region domain>` from the machine's private address and asks Pilot to adopt it (`POST /api/v1/settings/admin-domain`).
8. **Pilot → Central.** `datum_token` (refused until Central knows the machine's Atlas id), then telemetry starts.

A trial is the same flow with a warm image that already holds a site (`has_site=1`, resumed from a memory snapshot): Central waits for `/api/method/ping` on the site, signs in to it as Administrator, and queues its rename.

## A hostname is routed

1. **The site or the Admin → Pilot.** `POST /sites/<site>/domains`.
2. **Pilot → the domain program.** Pilot runs `bench-domain-provider generate-dns-records`, then `register <domain>`. On Frappe Cloud v2 that program comes from Cargo's image.
3. **The program → Central.** `central.api.pilot.domain_records`: the customer is told to set a CNAME to `proxy.<region domain>` and a TXT record `_frappe-verification.<domain>`.
4. **The program → Central.** `central.api.pilot.register_domain`. Central checks the TXT record, then reads `http://<domain>/.well-known/frappe-pre-authorize/` to see that the name really arrives at the region's proxy.
5. **Central → the proxy.** Central stores a `Site Domain` and sends `PATCH /v1/domains/<domain>`. Failed routes are retried every 5 minutes.
6. **Pilot.** It writes the nginx server block and, for a custom domain, obtains the certificate itself: the proxy passes that domain's TLS through to the server.

## A number leaves a server

1. **Cargo → Central.** When the region's Datum host is ready, Cargo's webhook reports `telemetry: Available` with the address `http://internal-telemetry-svc.<region domain>`.
2. **Central → the machine.** That address is in the `pilot-common-config` attribute of every new server.
3. **Pilot → Central.** `central.api.pilot.datum_token` returns a 7-day token whose `resource_id` is the machine's Atlas id. Pilot stores it in `[telemetry] token` and asks again when 24 hours or less remain.
4. **Pilot → Datum.** `pilot-monitor.service` sends `pilot_sites` every 60 seconds and the rest every 5 minutes, over the private network.
5. **Datum → ClickHouse.** Datum checks the token against the keys Cargo publishes, stamps `resource_id` on each row, and inserts.
6. **Beacon → ClickHouse.** Every minute Beacon runs the due rules of `pilot/beacon/rules/`. It drops every row whose `resource_id` is not a virtual machine in the tree Atlas gave it, or is younger than 10 minutes.

## A person is paged

1. **Beacon.** A rule returns a row for a resource. The alert is Pending, then Firing after the rule's `pending_for`.
2. **Beacon.** The alert joins an open incident that covers the resource or its parent, or one of the same rule, or a new Internal incident is created.
3. **Beacon → chat.** Every new incident is posted to the chat webhook.
4. **Beacon → responders.** For High or Critical: email to all responders, and escalation. It starts at once when the resource has no parent, after 90 seconds otherwise (so that a host's alert can absorb its machines').
5. **Beacon → Twilio.** The first responder is called. The next one after 2 minutes (Critical) or 5 (High). After the last one, a new round 15 minutes later, until someone acknowledges.
6. **Twilio → Beacon.** An answered call acknowledges the incident as that responder.
7. **Beacon.** When every alert has recovered, Beacon resolves the incident only if it is Internal and Beacon created it. Otherwise it asks a person to.

## A customer is told

1. **Pilot.** `pilot-monitor` or a task raises an event: a site failed its pings for 1 minute; CPU, memory or disk stayed over the limit for 5 minutes; a backup, a migration or a certificate failed.
2. **Pilot.** The event goes to the Admin's feed, to each `[[webhook_endpoints]]`, and to mail.
3. **Pilot → Central.** `central.notification.api.report_pilot_event`, with one of the event types Central accepts from a Pilot (`site_unavailable`, `site_recovered`, `backup_failure`, `migration_failure`, `certificate_expiry`, `certificate_failed`, `resource_limit_breached`…).
4. **Central → the team.** A notification in the console and by email.

## An image is built

1. **Cargo → GitHub.** Every 2 hours Cargo pairs the newest Pilot release with the head of each Frappe branch it follows.
2. **Cargo → Atlas.** It rents a build machine on the base Ubuntu image.
3. **Cargo → the machine.** Over SSH, `provision.sh`: user `frappe`, Pilot, the bench `default-bench`, Frappe at a fixed commit, `site.local` for Site and Apps images, production mode, `pilot setup central`, the domain program. No secret is in that script's environment.
4. **Cargo → Atlas.** Stop the machine, then `POST …/actions/snapshot` with the tags. Base and Apps images also keep a memory snapshot, so a server starts warm.
5. **Central → Atlas.** Central lists images by tag when a server is created. Cargo keeps the 3 newest builds and deletes older images.

## A region comes up

1. **Staff → Atlas.** Hosts are enrolled; the Atlas site runs in a machine on one of them.
2. **Atlas → Cargo's machine.** Atlas creates a platform machine, installs Pilot, a bench and the Cargo site over SSH, and hands it two 365-day tokens (Atlas' API as tenant 0; the proxy, for names ending in `-svc`).
3. **Atlas → the proxy.** `cargo.<region domain>` and `cargo-pilot.<region domain>` are routed.
4. **Central → Cargo.** `cargo.api.webhooks.configure` gives Cargo the address and the secret for its reports.
5. **Cargo → Atlas.** Cargo rents the machines of the Garage cluster and of the Datum host, and installs them over SSH.
6. **Cargo → Central.** `storage: Available`, `telemetry: Available`. Central marks the region's Cargo as registered at the first report.
