Voici les API derrière la Wolf UI (`/wolf`,
[#19](https://github.com/bthuner/dodock-wolf/issues/19)). Elles nécessitent le rôle Wolf User,
Wolf Manager ou System Manager, et appliquent les règles d'accès de l'appelant à l'intérieur de la
requête (voir [Accès](/fr/security/access)). Les réponses ne sont pas mises en cache par
utilisateur : chacune est propre à l'appelant ; deux lectures partagent un cache court filtré par
appelant (voir [Cache court](#cache-court)).

| Domaine | Méthodes |
|---|---|
| [Vue d'ensemble](#vue-densemble) | `scope.get_counts`, `scope.get_inventory` |
| [Page d'incident](#page-dincident) | `incident_view.list_incidents`, `get_incident`, `get_timeline`, `act`, `merge_preview`, `split_preview` |
| [Tableaux de bord](#tableaux-de-bord) | `dashboard.get_signals`, `get_http`, `get_monitoring` |
| [Explorateurs](#explorateurs) | `explore.list_events`, `list_error_groups`, `get_error_group` |
| [Explorateur de métriques](#explorateur-de-metriques) | `metrics.get_metric_catalog`, `query_metric` |
| [Sécurité](#securite) | `security.list_sites`, `get_posture` |
| [Déclaration réglementaire](#declaration-reglementaire) | `compliance.get_report` |
| [Actions de réponse](#actions-de-reponse) | `response.get_response`, `approve` |

Toutes les méthodes sont sous `dodock_wolf.api.`, par exemple `/api/method/dodock_wolf.api.scope.get_counts`.

## Arguments communs

### Fenêtre de temps

| Argument | Signification |
|---|---|
| `range` | Fenêtre relative se terminant maintenant : un nombre suivi de `m`, `h` ou `d`, comme `15m`, `24h`, `7d`. Par défaut `24h`. |
| `since`, `until` | Fenêtre explicite, ISO 8601. Une heure sans décalage est lue en UTC, comme dans le [protocole de l'agent](/fr/reference/protocol). `until` vaut maintenant par défaut et nécessite `since`. Ils l'emportent sur `range`. |

- Une fenêtre relative se mesure en temps réel : lors d'un changement d'heure, `24h` vaut
  24 heures, et non 23 ou 25 heures d'horloge murale.
- Les fenêtres de plus de 400 jours, ou dont `since` est postérieur à `until`, sont refusées.
- Les API de vue d'ensemble du Desk (`api/ui.py`) acceptent les mêmes valeurs de `range`.

Chaque réponse qui lit une fenêtre renvoie ce qu'elle a réellement lu, en UTC :

```json [window]
"window": {"since": "2026-10-29T13:00:00Z", "until": "2026-10-30T13:00:00Z", "relative": "24h", "time_zone": "Europe/Paris"}
```

`time_zone` est celui du site. Les heures stockées sont dans ce fuseau. L'UI convertit avec lui,
jamais avec le fuseau du navigateur.

Dans la Wolf UI, la fenêtre est dans l'URL (`?range=7d` ou `?since=…&until=…`). Une plage
sélectionnée sur le graphique HTTP d'un tableau de bord, ou sur celui de l'explorateur de
métriques, devient un `since`/`until` explicite : les compteurs et le graphique du tableau de bord,
ainsi que les explorateurs d'événements et d'erreurs ouverts depuis celui-ci, sont lus avec elle.
**Back to a relative window** la retire.

### Périmètre

`site`, `bench` et `host` restreignent une requête aux enregistrements ayant ces valeurs.

::warning
**`bench` nécessite `host`.** Les noms de bench comme `frappe-bench` se répètent d'un hôte à
l'autre : un bench seul est donc ambigu et refusé.
::

### Accès

Un Wolf User restreint, c'est-à-dire qui a des lignes **Wolf User Scope**, obtient des comptages et
un inventaire portant sur les enregistrements qu'il peut voir, et `"restricted": true`.

::note
Un Wolf User **sans aucune** ligne Wolf User Scope n'est pas restreint : il voit tout, comme dans
le Desk. C'est la règle actuelle, conservée telle quelle.
::

## Vue d'ensemble

### `dodock_wolf.api.scope.get_counts`

Comptages exacts pour la vue d'ensemble et les tableaux de bord d'entité. Arguments : fenêtre et
périmètre.

```json [get_counts]
{
  "window": {...},
  "scope": {"host": "bench-01"},
  "restricted": false,
  "incidents": {
    "unresolved": 60, "unacknowledged": 40, "critical_unresolved": 7,
    "by_status": {"Open": 40, "Acknowledged": 20},
    "by_severity": {"info": 0, "warning": 53, "critical": 7},
    "sites_with_unresolved": 1, "unresolved_without_site": 5,
    "opened_in_window": 61, "resolved_in_window": 1,
    "basis": "..."
  },
  "events": {"records": 12, "occurrences": 140, "by_type": {"error": {"records": 3, "occurrences": 90, "by_severity": {...}}}, "basis": "..."},
  "agents": {"agent": {"fresh": 3, "stale": 1, "never_seen": 0, "disabled": 0}, "satellite": {...}, "silence_minutes": 5, "basis": "..."}
}
```

| Partie | Règle |
|---|---|
| `incidents` | `unresolved` compte les incidents Open et Acknowledged à l'instant présent, quelle que soit la fenêtre. `unacknowledged` ne compte que les Open. Les incidents fusionnés sont exclus. `unresolved_without_site` compte les incidents portant sur tout un hôte ou tout un bench, qui n'ont pas de site. `opened_in_window` et `resolved_in_window` utilisent `started_at` et `resolved_at`. |
| `events` | `records` sont les Wolf Events vus pour la première fois dans la fenêtre. `occurrences` additionne leur `count` déclaré. Un enregistrement dédoublonné continue de compter les répétitions, y compris celles postérieures à la fenêtre : `occurrences` n'est donc pas un nombre d'occurrences à l'intérieur de la fenêtre. |
| `agents` | Les agents sont des hôtes : `site` et `bench` ne les filtrent donc pas. Un satellite n'est pas un hôte et il est compté à part ; avec `host`, il est compté quand l'un de ses benches enregistrés tourne sur cet hôte. `fresh` signifie vu dans le seuil de silence des agents défini dans Wolf Settings, la même règle que l'indicateur en ligne de la vue d'ensemble du Desk. |

### `dodock_wolf.api.scope.get_inventory`

Les hôtes, benches et sites que l'appelant peut voir. Argument : `days`, la fenêtre de télémétrie
(par défaut 7, au plus 90).

```json [get_inventory]
{
  "hosts": [
    {"host": "bench-01", "sources": ["agent", "events", "metrics"], "last_seen": "2026-10-30T12:59:30Z",
     "benches": [{"bench": "frappe-bench", "host": "bench-01", "sources": [...], "last_seen": "...",
                  "sites": [{"site": "a.example.com", "sources": [...], "last_seen": "..."}]}],
     "sites": []}
  ],
  "unplaced_sites": [],
  "note": "Hosts and benches come from agent registrations and from telemetry in the window. ...",
  "days": 7,
  "restricted": false,
  "as_of": "2026-10-30T13:00:02Z"
}
```

`as_of` indique quand les enregistrements et la télémétrie ont été lus : ils sont mis en cache
quelques secondes (voir [Cache court](#cache-court)).

| Source | Signification |
|---|---|
| `agent`, `satellite` | Ce qu'un agent a déclaré lors de son enregistrement. |
| `events` | Selon leur dernière occurrence, si bien qu'un événement dédoublonné récurrent garde son site dans la liste. |
| `metrics` | Agrégats. |
| `incidents` | Ceux non résolus, quel que soit leur âge. |

Un enregistrement nomme tous les sites d'un bench ; un utilisateur restreint ne voit que ceux qui
lui sont accordés. Aucun type de source n'est complet à lui seul : un bench ajouté après
l'enregistrement de son agent apparaît dès qu'il envoie de la télémétrie, et un site silencieux
uniquement via l'enregistrement de son agent. L'UI affiche `sources` et `note` plutôt que de
présenter la liste comme complète.

- Un bench est toujours sous son hôte.
- `host.sites` contient les sites vus sur un hôte dont le bench est inconnu.
- `unplaced_sites` contient les sites vus sans hôte, par exemple un satellite sans information
  d'hôte. Ils ne sont pas rattachés à un hôte deviné.
- Les heures sont en UTC.

## Page d'incident

### `dodock_wolf.api.incident_view.list_incidents`

Les incidents que l'appelant peut voir, du plus récent au plus ancien.

| Argument | Signification |
|---|---|
| `status` | `unresolved` (par défaut), `resolved` ou `all`. |
| `site`, `bench`, `host` | Périmètre. |
| `limit` | Au plus 200. |
| `cursor` | Poursuit une page. |

Les pages suivent `(started_at, name)` : deux incidents démarrés à la même seconde ne sont ni
répétés ni sautés. Renvoie `incidents`, `paging` (`has_more`, `next_cursor`) et `time_zone`.

### `dodock_wolf.api.incident_view.get_incident`

L'en-tête de l'incident en un seul appel : titre, statut, gravité, périmètre, début,
acquittement, résolution et responsable, règle, silence, heures de notification et d'escalade,
liens de fusion et de scission, et fenêtre de la chronologie.

| Champ | Signification |
|---|---|
| `deployment` | Heure du déploiement qui précède l'incident, avec `available: false` quand la conservation a supprimé son événement mais que l'incident a gardé l'heure. |
| `event_records` | Wolf Events liés. `event_count` est le même nombre, comme sur **Wolf Incident**. |
| `event_occurrences` | Les occurrences qu'ils déclarent, répétitions comprises. Un nombre différent de `event_records`. |
| `can` | Les actions que l'appelant peut effectuer. |
| `regulatory` | Voir [Déclaration réglementaire](#declaration-reglementaire). |

Les Wolf Users lisent et commentent. Les Wolf Managers peuvent aussi acquitter, résoudre, prendre
l'incident, et :
- `merge` : l'incident n'est pas fusionné ;
- `split` : non fusionné, et au moins deux événements sont liés (un doit rester) ;
- `postmortem` : non fusionné, et soit résolu, soit en ayant déjà un (`postmortem` le nomme).

Chacun correspond à la vérification que fait l'action elle-même.

### `dodock_wolf.api.incident_view.get_timeline`

Une page de la chronologie, de la plus ancienne à la plus récente.

| Argument | Signification |
|---|---|
| `incident` | Le **Wolf Incident**. |
| `limit` | Par défaut 100, au plus 500. |
| `cursor` | Poursuit une page. |
| `families` | Sous-ensemble, séparé par des virgules, des familles ci-dessous. |

| Famille | Lignes |
|---|---|
| `evidence` | Wolf Events liés à l'incident, à tout moment. |
| `context` | Autres événements de son périmètre (le site, le même bench sur le même hôte, ou tout l'hôte) pendant sa fenêtre, si l'appelant peut les voir, ainsi que le déploiement qui le précède, même s'il est antérieur à la fenêtre. Quand l'incident a pris des événements d'autres périmètres (par IP ou utilisateur, ou via une règle de séquence), aussi les déploiements et les événements de santé (`error`, `cron_failure`, `worker_failure`, `host_metric_alert`) de ces périmètres dans la fenêtre : du site ; du bench sur son hôte ; pour un hôte, ses événements propres à l'hôte et les déploiements, crons et workers en échec de ses benches, pas les Error Logs de ses sites. Au plus 10 périmètres de ce type, les mêmes sur chaque page. Un incident sans site, bench ni hôte n'a que ce second type, dans le Desk aussi. Un utilisateur qui peut lire l'un de ces périmètres mais pas l'événement qui l'a amené peut quand même savoir, d'après ses lignes, que l'incident l'a atteint. |
| `activity` | Changements de statut, affectations, commentaires et notes, issus de l'historique Version et Comment de Frappe. |
| `delivery` | Tentatives de notification (**Wolf Delivery**). |

Chaque ligne a un `id` stable, une `family`, un `kind`, un `at` (UTC) et un `summary` en texte
brut. Ids : `event:<name>`, `activity:comment:<name>`, `activity:version:<name>:<field>`,
`delivery:<name>`, `deployment:<incident>`.

Par type :

| Type | Champs |
|---|---|
| Événements | `relation` : `linked`, `context` ou `preceding_change` (le déploiement qui précède l'incident, jamais qualifié de cause). `count`, `first_seen` et `last_seen` décrivent un enregistrement dédoublonné : une ligne, pas une ligne par occurrence. `details` est le payload de l'événement, à afficher comme texte. `source_label` indique qui l'a émis (`Wolf agent`, `Wolf site`, `Suricata`, `Wazuh`). `duplicate_of` nomme l'événement d'une autre source sur le même constat, vu en premier ([détecteurs qui se recoupent](/fr/security/wazuh-suricata#quand-les-détecteurs-se-recoupent) en mode `both`) ; l'identifiant de sa ligne est `event:<duplicate_of>`. |
| Activité | `user_name`. Les commentaires et notes arrivent en `text` brut, jamais en HTML à interpréter. |
| Livraisons | `channel`, `action`, `target`, `result` et `http_status`. `result` vaut `accepted` quand le point d'accès a accepté le message, ce qui ne signifie pas qu'une personne l'a lu. |

- Les lignes sont triées par heure, puis événements, activité et livraisons, puis id. Les lignes de
  même heure n'ont pas d'ordre causal.
- `paging.next_cursor` reprend après la dernière ligne. Les mêmes lignes reviennent une fois
  chacune, quelle que soit la taille de page.
- L'activité conserve les 200 modifications enregistrées et les 300 commentaires les plus récents.
  `truncated.activity_version` et `truncated.activity_comment` signalent l'existence d'éléments
  plus anciens.
- `window` est la fenêtre de l'incident : le début moins `padding_minutes`, jusqu'à sa résolution
  ou maintenant. C'est la même fenêtre que celle du Desk et du post-mortem.

### `dodock_wolf.api.incident_view.act`

POST `incident` et `action`, parmi `acknowledge`, `resolve` ou `assign_to_me`. Elle exécute la
méthode propre à l'incident, si bien que la permission d'écriture de Frappe s'applique, et renvoie
le nouveau `get_incident`.

L'état de l'incident est vérifié d'abord :
- acquitter nécessite un incident Open ;
- résoudre ou prendre nécessite un incident non résolu ;
- les incidents fusionnés refusent toute action.

Une page restée ouverte sur un incident périmé reçoit une erreur au lieu de le rouvrir.

### `dodock_wolf.api.incident_view.merge_preview`

Arguments : `source`, et facultativement `target`. Wolf Managers ayant la permission d'écriture
uniquement. Rien n'est écrit.

- `candidates` : là où la source peut aller. Ce sont des incidents non résolus et non fusionnés que
  l'appelant peut lire : les 50 plus récents (`more_candidates` indique s'il y en a davantage), ceux
  du site de la source d'abord, puis ceux de son bench.
- `preview`, pour une `target` :
  - `error` : le refus propre à la fusion (elle-même, un incident fusionné, pas de permission
    d'écriture) ou `null` ;
  - les `events` et `comments` qui seraient déplacés ;
  - `target_after` : gravité, début et statut, une fois que la cible couvre les deux ;
  - `source_after` : Resolved, fusionnée dans la cible.

La fusion elle-même est `dodock_wolf.api.incident.merge` (POST `source`, `target`), qui vérifie à
nouveau.

### `dodock_wolf.api.incident_view.split_preview`

Arguments : `incident`, et facultativement `events` (une liste JSON de noms de Wolf Events). Wolf
Managers uniquement. Rien n'est écrit.

- `events` : les événements liés, du plus ancien au plus récent, au plus 500 (`more_events`).
- `preview`, pour une sélection :
  - `error` : le refus propre à la scission (rien de coché, un événement non lié, tous cochés) ou
    `null` ;
  - `moved` et `kept` ;
  - `new_incident` : titre, gravité, début et statut. Il est Open, ou Resolved quand la source
    l'est. Il n'a pas de règle d'alerte : rien ne le résout donc de lui-même.

La scission elle-même est `dodock_wolf.api.incident.split` (POST `incident`, `events`, `title`). Le
post-mortem est créé par `dodock_wolf.api.incident.create_postmortem` et modifié dans le Desk.

## Tableaux de bord

### `dodock_wolf.api.dashboard.get_signals`

La valeur la plus récente de chaque série de signaux du périmètre (`site`, `bench` avec `host`,
`host`) : une série par métrique, hôte, bench, site et label. Chaque série a un `state` :

| État | Signification |
|---|---|
| `firing` | Une règle activée sur cette métrique s'applique à la série et a un incident ouvert pour son périmètre et, pour les règles groupées par label, pour son label (`incidents`). Une série en alerte dont les échantillons se sont arrêtés reste `firing`, avec `stale: true`. |
| `stale` | Les échantillons se sont arrêtés : aucun dans les 2 dernières heures, ou aucun pendant trois intervalles de collecte, au moins 5 minutes (sauvegardes : 30 min). L'ancienne valeur n'est pas présentée comme actuelle. Les cadences sont celles par défaut de l'agent : un agent réglé pour sonder TLS ou les sauvegardes moins souvent paraît `stale` plus tôt. |
| `watched` | Des règles s'appliquent (`rules` : agrégation, opérateur, seuil, fenêtre) et aucune n'a d'incident ouvert. |
| `unwatched` | Une valeur, mais aucune règle ne la surveille. Le tableau de bord n'invente pas de seuil. |

| Champ | Signification |
|---|---|
| `missing` | Signaux sans aucune série dans les 7 derniers jours : non collectés pour ce périmètre, non configurés, ou indisponibles ici. Ils ne sont jamais affichés comme zéro. |
| `counts` | États exacts par groupe, quelle que soit la limite de 300 séries. |
| `email` | Problèmes de file d'attente d'e-mails que le site a enregistrés sur lui-même au cours des dernières 24 heures. |
| `as_of` | Quand les séries ont été lues (voir [Cache court](#cache-court)). Les règles, incidents et états sont lus à chaque requête. |

Un utilisateur restreint voit ce que vérifie chaque règle, mais pas les filtres d'hôte, de bench ou
de site qu'elle nomme. La signification des métriques (unité, type, cadence) se trouve dans
[`wolf/catalog.py`](https://github.com/bthuner/dodock-wolf/blob/main/dodock_wolf/wolf/catalog.py).

### Cache court

`get_inventory` et `get_signals`, les deux lectures lentes de la vue d'ensemble, conservent ce
qu'elles lisent pendant `wolf_read_cache_seconds` : configuration du site, par défaut `30`
(l'intervalle d'envoi d'un agent), `0` le désactive. `get_inventory` met en cache ses
enregistrements et triplets de télémétrie, `get_signals` ses séries (valeur la plus récente et
dernière heure de contact).

::caution
La valeur en cache est lue **sans** conditions d'accès et elle est la même pour tous les appelants.
Chaque requête ne garde ensuite que les lignes que son appelant peut voir, selon la règle de
[`wolf/scopes.py`](https://github.com/bthuner/dodock-wolf/blob/main/dodock_wolf/wolf/scopes.py). Une
valeur en cache ne transmet jamais les autorisations d'un utilisateur à un autre.
::

- Les règles, les incidents ouverts et la file d'attente d'e-mails sont lus à chaque requête : l'état
  d'un signal suit immédiatement un incident.
- Une valeur est **fraîche** pendant `wolf_read_cache_seconds`. Plus ancienne, et jusqu'à 4 fois
  cette durée (2 min par défaut), elle est encore servie immédiatement, et un job en arrière-plan
  (dédoublonné, file `short`) la relit. Plus ancienne encore, ou absente, c'est la requête qui lit.
- Entre deux visites, le planificateur relit chaque minute les valeurs demandées au cours des
  10 dernières minutes (10 au plus par site) qui ne sont plus fraîches
  (`read_cache.refresh_active`). Il faut pour cela `scheduler_tick_interval` à 60 (voir
  [Installer le Wolf App](/fr/install/wolf-app)) : avec le tick par défaut de Dodock de 4 min, une
  visite après 2 minutes calmes lit elle-même.
- Une série qui démarre, ou une valeur qui change, apparaît au plus une ou deux minutes plus tard.
  `as_of` indique quand les données ont été lues. Une [mise à jour en direct](#mises-a-jour-en-direct)
  relance la lecture, et peut obtenir la valeur en cache.
- Une modification de `wolf_read_cache_seconds` prend effet en moins d'une minute : les workers web
  de Dodock gardent la configuration du site en mémoire jusqu'à 60 s.
- Il y a une valeur en cache par site et par périmètre (site, bench et hôte de `get_signals` ;
  `days` de l'inventaire) : un tableau de bord d'un autre périmètre a la sienne.

Effet mesuré : [Performance](/fr/reference/performance#le-cache-court).

### `dodock_wolf.api.dashboard.get_http`

Requêtes, 5xx et 502 par intervalle (bucket) sur la fenêtre. Arguments : les arguments communs de
fenêtre et de périmètre.

- Les valeurs sont additionnées sur l'ensemble des labels et lues à la résolution de la fenêtre
  (`resolution`).
- Seuls les intervalles complets sont lus (`window` ; `requested_window` est ce qui a été demandé) :
  l'intervalle encore en cours de remplissage s'affiche une fois clos, au lieu de dessiner une
  baisse de trafic.
- 502 fait partie de 5xx et n'y est jamais ajouté.
- Un intervalle sans échantillons vaut `null` : un trou, pas un zéro. `has_data` distingue
  « pas de données » de « zéro ».
- `deployments` liste les déploiements de la fenêtre demandée. Sur le tableau de bord d'un site,
  cela inclut les déploiements enregistrés pour tout son bench (sans site), comme les incidents les
  lient.

### `dodock_wolf.api.dashboard.get_monitoring`

Indique si Wolf lui-même fonctionne : la santé du site (règles, planificateur, file d'ingestion),
les marqueurs de progression des agrégats, chaque agent et satellite avec son état, son dernier
contact, son décalage d'horloge, sa version et son `setup` (la dernière exécution de
`wolf-agent doctor` par l'agent : `checked_at`, `failed`, `warnings` et les `problems` avec leur
correction), et le mode de ce site. Chaque partie est rapportée séparément.

::note
Un agent en ligne ne dit rien du canal de secours de son chien de garde (watchdog).
::

## Explorateurs

Les Wolf Events sont dédoublonnés : un enregistrement contient sa première heure (`first_seen`),
sa dernière heure (`last_seen`) et le nombre de répétitions qu'il a absorbées (`count`). Les listes
des explorateurs sont des listes d'enregistrements. Elles ne disent jamais combien de fois quelque
chose s'est produit dans une fenêtre quand un enregistrement chevauche le bord de la fenêtre, et
chaque réponse le précise dans `basis`.

Les recherches (`q`) portent sur une simple sous-chaîne du titre, de 100 caractères au plus : `%` et
`_` se correspondent à eux-mêmes, et il n'y a pas d'expression régulière.

### `dodock_wolf.api.explore.list_events`

Les enregistrements d'événements actifs dans la fenêtre (vus pour la première fois avant sa fin,
pour la dernière fois après son début), du plus récent au plus ancien, paginés par
`(first seen, name)`.

| Argument | Signification |
|---|---|
| `range`, `since`, `until` | Fenêtre. |
| `site`, `bench`, `host` | Périmètre. |
| `event_type`, `severity`, `category` | Filtres. |
| `q` | Sous-chaîne du titre. |
| `limit` | Au plus 200. |
| `cursor` | Poursuit une page. |
| `entity` | Événements de sécurité qui nomment une entité (ci-dessous). |

Les payloads ne figurent pas dans la liste : `get_event(name)` renvoie un enregistrement avec son
payload.

`entity` garde les événements de sécurité de toutes les sources (Wolf, Suricata, Wazuh) qui la
nomment : `ip:203.0.113.5`, `host:erp-01`, `site:erp.example.com` ou `user:jane@example.com`. Les
valeurs sont normalisées et résolues via les alias. Par exemple, `host:erp-01` trouve aussi les
alertes Wazuh de l'agent nommé `wazuh-erp01` quand un alias indique qu'il s'agit du même hôte.
`dodock_wolf.api.entities.find(entity, ...)` renvoie la même liste. La réponse reprend `entity`.

### `dodock_wolf.api.explore.list_error_groups`

Les groupes d'enregistrements d'erreur, par empreinte (fingerprint), qui ont un enregistrement
actif dans la fenêtre, du plus récent au plus ancien. La fenêtre et `q` choisissent les groupes.
Leurs chiffres couvrent tous les enregistrements du groupe que l'appelant peut voir, quel que soit
leur âge, comme sur la page du groupe, si bien qu'une erreur récurrente n'est pas présentée comme
nouvelle :
- `records`, et `records_in_window` ;
- `occurrences`, la somme des compteurs des enregistrements ;
- `first_seen` et `last_seen` ;
- le nombre de `sites`, et si certains enregistrements portent sur tout un hôte ;
- le nombre d'`incidents` liés ;
- le titre de l'enregistrement vu le plus récemment, qui représente le groupe.

Une empreinte inclut le site, sauf si l'agent envoie la sienne : la plupart des groupes concernent
donc un seul site.

### `dodock_wolf.api.explore.get_error_group`

Tous les enregistrements visibles d'un groupe, quel que soit leur âge :
- où ils se sont produits, par site, bench et hôte ;
- les incidents auxquels ils sont liés et que l'appelant peut lire (`incidents_not_visible` compte
  les autres) ;
- son enregistrement vu le plus récemment, avec le payload : la traceback représentative, le même
  enregistrement que celui affiché dans la liste ;
- ses 50 enregistrements vus le plus récemment.

Un utilisateur restreint ne voit que les enregistrements de ses sites, benches ou hôtes, et les
comptages portent sur ceux-ci.

## Explorateur de métriques

### `dodock_wolf.api.metrics.get_metric_catalog`

Toutes les métriques cataloguées
([`wolf/catalog.py`](https://github.com/bthuner/dodock-wolf/blob/main/dodock_wolf/wolf/catalog.py))
et les métriques personnalisées vues au cours des 7 derniers jours. Chacune a :

| Champ | Signification |
|---|---|
| `kind`, `unit` | Ce qu'est la valeur. |
| `level` | `host`, `bench` ou `site`. |
| `label_key` | `mount`, `queue`, `domain`, `db`, `of` ou `manager`. |
| `aggregations`, `group_bys` | Ce qu'elle permet. |
| `seen` | Si l'appelant a des données pour elle. |

- Les jauges se lisent en `avg`, `min`, `max` ou `last`.
- Les comptages par intervalle se lisent en `sum` (le total par intervalle de lecture), `avg` ou
  `max` (par intervalle d'envoi).
- Une métrique personnalisée se lit comme un niveau.
- Le regroupement suit le niveau de la métrique : une métrique d'hôte n'a ni bench ni site. Les
  métriques avec un label peuvent aussi se regrouper par `host_label`, tout comme une métrique
  personnalisée, dont le catalogue ne peut pas nommer les labels.

Le catalogue liste toutes les métriques que l'agent envoie, ce qu'un test unitaire vérifie par
rapport au code source de l'agent. `get_labels(metric, scope)` liste les valeurs de label d'une
métrique (au plus 100), y compris celles vues pour la première fois au cours de la dernière heure.

### `dodock_wolf.api.metrics.query_metric`

| Argument | Signification |
|---|---|
| `metric` | Nom de la métrique. |
| `aggregation` | Par défaut selon le type. |
| `group_by` | Par défaut `none`. |
| `label` | Valeur de label. |
| fenêtre et périmètre | Les arguments communs. |

Une combinaison que le catalogue n'autorise pas est refusée : une somme de niveaux de disque, la
dernière valeur d'un comptage par intervalle, une métrique d'hôte groupée par site.

La réponse lit des intervalles complets (`bucket_seconds` ; `window` est ce qui a été lu,
`requested_window` ce qui a été demandé) à une résolution assez fine pour la durée de la fenêtre et
qui remonte encore jusqu'à son début (`resolution`). Un zoom de deux heures sur la semaine dernière
lit les agrégats à la minute, car des échantillons bruts aussi anciens sont purgés (voir
[Stockage des métriques](/fr/reference/metric-storage)). Le résultat est exact entre échantillons
bruts et agrégats. Les groupes sont d'abord classés en SQL, et seuls ceux affichés sont lus par
intervalle.

Chaque élément de `series` a :

| Champ | Signification |
|---|---|
| `points` | Un par intervalle, `null` pour un intervalle sans échantillons (un trou, pas un zéro). |
| `value` | L'agrégation sur toute la fenêtre. |
| `samples`, `last_sample` | Nombre d'échantillons et échantillon le plus récent. |
| `stale` | Évalué uniquement quand la fenêtre atteint maintenant (`live`), et d'après l'échantillon le plus récent, pas le dernier intervalle complet (qui a jusqu'à un intervalle de retard). Dans une fenêtre passée, le dernier échantillon marque simplement la fin de la fenêtre. |

`groups` indique combien de groupes existent et lesquels, au nombre de `MAX_GROUPS` (20), sont
affichés, classés selon l'agrégation, du plus élevé au plus bas (du plus bas au plus élevé pour
`min`). `retention.clipped` vaut true quand la fenêtre commence avant les données conservées à cette
résolution (`kept_from`, la limite qu'applique la purge) : ces intervalles sont des trous.

## Mises à jour en direct

La Wolf UI reste à jour via le serveur socket.io propre à Frappe
([`dodock_wolf/wolf/live.py`](https://github.com/bthuner/dodock-wolf/blob/main/dodock_wolf/wolf/live.py),
[`frontend/src/services/live.js`](https://github.com/bthuner/dodock-wolf/blob/main/frontend/src/services/live.js)).
Le serveur ne pousse jamais de télémétrie. Il envoie une **invalidation**, l'événement
`wolf_invalidate`, et la page relit les données via les API ci-dessus, qui vérifient les permissions
comme d'habitude.

| Salle | Rejointe avec | Frappe vérifie | Message |
|---|---|---|---|
| `doc:Wolf Incident/<name>` | `doc_subscribe` | la permission de lecture sur cet incident (Wolf User Scope s'applique) | `{"kind": "incident", "incident": "<name>"}` |
| `doctype:Wolf Incident` | `doctype_subscribe` | la permission de lecture sur le DocType | `{"kind": "incidents"}` |
| `doctype:Wolf Event` | `doctype_subscribe` | la permission de lecture sur le DocType | `{"kind": "events"}` |

- **Envoyé quand** : un incident est créé, enregistré, mis à jour par le moteur (nouveaux
  événements liés, réouverture, résolution automatique, silence, escalade, affectation,
  post-mortem) ou supprimé ; un commentaire sur un incident est ajouté, modifié ou supprimé ; une
  livraison est enregistrée ; un événement est stocké.
- **Au plus un message par salle et par transaction**, après la validation (commit). Le suivi est
  remis à zéro au commit et au rollback : un job qui valide plusieurs fois annonce chaque
  transaction, et une transaction annulée n'annonce rien. Les messages de liste sont aussi limités
  à un toutes les 5 s par type. Un message retenu est marqué après le commit et envoyé par
  `flush_live_updates` (chaque minute) : une modification validée peut être retardée, jamais
  perdue.
- **Aucun nom dans les salles de liste** : un lecteur restreint apprend seulement que quelque chose
  a changé quelque part.
- **Démarrage** : `capabilities.realtime` donne `namespace` (`/<site>`), `port` (`socketio_port`,
  pour `bench start`), `dev_server` et `poll_seconds`. Derrière nginx, le socket utilise l'origine
  propre au site (`/socket.io` passe par le proxy, comme pour le Desk).

Ce que chaque page fait d'un message :

| Page | À la réception d'un message | Sans socket |
|---|---|---|
| Incident | En-tête rafraîchi. Les nouvelles lignes de chronologie sont ajoutées sans défilement, et un bouton « N new rows: show » mène le lecteur à la première. Les lignes chargées et les lignes dépliées restent. Au-delà de 500 lignes chargées, seul l'en-tête suit et les lignes attendent Refresh. | Interroge toutes les 60 s |
| Incidents | Rafraîchie, sauf si « Load more » a été utilisé : alors « Incidents changed · Refresh ». | Interroge, même règle |
| Vue d'ensemble et tableaux de bord | Rafraîchis au plus toutes les 10 s (les messages ne portent pas de périmètre ; les fenêtres relatives se déplacent). Également interrogés toutes les 60 s en direct, car les métriques ne sont pas annoncées. | Interroge |
| Events, Errors | Jamais réordonnés sous les yeux du lecteur : « New events recorded · Refresh » (les nouveaux événements peuvent ne pas correspondre aux filtres). | Pas d'interrogation : « Not live: refresh by hand » |

- Chaque page se resynchronise une fois quand le socket rejoint ses salles pour la première fois
  (ce qui a changé après sa première lecture est inconnu) et après chaque reconnexion (les messages
  envoyés hors connexion sont perdus).
- Une page qui ne se recharge pas d'elle-même affiche « Reconnected, changes may have been missed ·
  Refresh » après une reconnexion. Une interrogation ou la première connexion n'annonce jamais de
  changement.
- **Pause** retient les messages, et la page indique que des changements attendent, jusqu'à
  **Resume**.
- Chaque rafraîchissement, y compris celui du lecteur, passe par une seule file : jamais deux à la
  fois.
- L'interrogation ignore les onglets masqués.

## Sécurité

### `dodock_wolf.api.security.list_sites`

Les sites ayant un échantillon récent de `site_config_risks` ou de `backup_age_hours`, plus le site
Wolf lui-même (pas sur un satellite), filtrés selon les accès de l'appelant.

### `dodock_wolf.api.security.get_posture`

Argument : `site` (par défaut : le site Wolf). Un site que l'appelant ne peut pas voir donne un 403.

| Champ | Signification |
|---|---|
| `site` | Le site. |
| `local` | Le site Wolf : ses System Settings sont lisibles. |
| `hosts` | Hôtes du site. |
| `recent_hours` | Les échantillons d'agent plus anciens que cette valeur (3) ne sont pas utilisés. |
| `score` | Poids réussi sur poids total. Un contrôle inconnu compte comme non réussi. |
| `coverage`, `passed`, `failed`, `unknown` | Totaux des contrôles. |
| `checks` | `{id, label, weight, status, evidence, fix}`, `status` valant `pass`, `fail` ou `unknown`. |

La tâche horaire `record_security_scores` stocke le score dans la métrique `security_score`. Voir
[Sécurité](/fr/security).

## Déclaration réglementaire

`get_incident` renvoie `regulatory` : `null` quand aucune case n'est cochée, sinon
`{nis2, gdpr, reference, deadlines}`. Chaque échéance est
`{id, regime, label, due_at, done_at, status, estimated}`.

| `status` | Signification |
|---|---|
| `open` | Pas faite, pas d'échéance proche. |
| `due_soon` | Due dans les 6 h. |
| `overdue` | En retard. |
| `done` | Faite dans les délais. |
| `done_late` | Faite après l'échéance. |

### `dodock_wolf.api.compliance.get_report`

Argument : `incident`. Renvoie `{incident, markdown}` : un brouillon avec les faits, les échéances,
la chronologie (événements liés et commentaires, 100 de chaque au plus) et l'impact, la cause
racine, les enseignements et les actions du post-mortem. La permission de lecture sur l'incident
suffit. Rien n'est envoyé. Voir [Conformité](/fr/security/compliance).

## Actions de réponse

### `dodock_wolf.api.response.get_response`

Argument : `incident`.

|---|---|
| `proposals` | `{action, target, agent, host, bench, site, reason, label, executors}`, issus des événements de sécurité de l'incident, sans ceux déjà approuvés ou appliqués. Un blocage nomme l'hôte attaqué dans `host`, son Wolf Agent dans `agent` quand c'est lui qui l'applique, et `executors` (`wolf_agent`, `wazuh`). |

### `dodock_wolf.api.response.approve`

POST. Wolf Manager ou System Manager uniquement.

| Argument | Signification |
|---|---|
| `incident` | Le **Wolf Incident**. |
| `action` | `block_ip`, `disable_user`, `logout_sessions` ou `revoke_api_keys`. |
| `target` | IP ou utilisateur. |
| `host` | Pour `block_ip` : l'hôte attaqué, tel que proposé. |
| `agent` | Pour `block_ip`, à la place de `host` (anciens liens et pages) : le Wolf Agent qui l'applique. |
| `duration_hours` | Pour `block_ip` : de 1 à 168, pour le blocage du Wolf Agent. Un blocage Wazuh dure le délai de sa commande. |
| `reason` | Texte libre. |

Les cibles refusées produisent une erreur de validation, et rien n'est enregistré : une adresse
privée ou réservée, Administrator, Guest, vous-même.

Renvoie la **Wolf Response Action**. Les actions sur les utilisateurs reviennent `Applied` ou
`Failed`. Les blocages restent `Approved` jusqu'au rapport de l'agent (voir
[protocole](/fr/reference/protocol#actions-de-réponse) et
[Actions de réponse](/fr/agent/response-actions)).
