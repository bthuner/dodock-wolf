Tout le trafic est en HTTPS + JSON. Tous les horodatages sont des chaînes ISO-8601 en **UTC**
(`2026-10-29T02:00:13Z`). L'app les convertit dans le fuseau horaire système du site.

Les réponses suivent la convention de Frappe : la réponse se trouve sous la clé `message`.

| Point d'accès | Méthode | Authentification | Section |
|---|---|---|---|
| `/api/method/dodock_wolf.api.agent.register` | POST | jeton d'enregistrement | [Enregistrement](#enregistrement) |

## Enregistrement

```http [POST /api/method/dodock_wolf.api.agent.register]
POST /api/method/dodock_wolf.api.agent.register
Content-Type: application/json

{
  "registration_token": "<Wolf Settings → Registration Token>",
  "hostname": "bench-01",
  "kind": "agent",
  "agent_version": "0.1.0",
  "os": "Debian GNU/Linux 12",
  "benches": [{"name": "main", "path": "/home/frappe/frappe-bench", "sites": ["a.example.com"]}]
}
```

| Champ | Signification |
|---|---|
| `registration_token` | La valeur de **Wolf Settings → Registration Token**. |
| `hostname` | Le nom de l'hôte. Pour un satellite, le nom de son site. |
| `kind` | Facultatif. `agent` (par défaut), `satellite` ou `integration` (voir [Intégration Wazuh](#integration-wazuh)). |
| `agent_version` | Version de l'émetteur. |
| `os` | Chaîne du système d'exploitation. |
| `benches` | Liste de `{name, path, sites}`. Un satellite ajoute `host`. |

Réponse :

```json [Réponse]
{"message": {"agent_id": "WAG-0001", "agent_secret": "<random 40 chars>", "push_interval": 30}}
```

La réponse contient aussi `server_version`, la version du Wolf App.

Le secret n'est renvoyé qu'une fois. L'agent le stocke dans `/etc/wolf-agent/config.json`
(mode 0600). Le site Wolf ne conserve qu'une empreinte salée (`hmac-sha256$<salt>$<digest>` sur
**Wolf Agent**) et ne peut donc pas réafficher le secret. Deux moyens le remplacent :
- enregistrer à nouveau le même nom d'hôte ;
- **Rotate secret** dans le formulaire **Wolf Agent**, qui affiche une seule fois le nouveau secret.

### Satellites

Un satellite est un autre site Frappe qui exécute `dodock_wolf` en mode satellite (voir
[Tous les sites d'un bench](/fr/install/every-site)). Il s'enregistre avec `hostname` égal au nom
de son site et une entrée de bench portant son vrai `host` :

```json [Enregistrement d'un satellite]
{"registration_token": "...", "kind": "satellite", "hostname": "b.example.com", "agent_version": "0.1.0",
 "os": "Linux-6.1...", "benches": [{"name": "frappe-bench", "path": "/home/frappe/frappe-bench",
 "sites": ["b.example.com"], "host": "bench-01"}]}
```

### Refus

- Un nom d'hôte déjà enregistré avec un autre type est refusé.
- Un site en mode satellite refuse tout enregistrement : enregistrez-vous plutôt auprès de son site
  central.
- Un jeton d'enregistrement erroné est refusé.
- L'enregistrement est limité à 20 appels par heure.

## Envoi de télémétrie

```http [POST /api/method/dodock_wolf.api.ingest.push]
POST /api/method/dodock_wolf.api.ingest.push
Content-Type: application/json
X-Wolf-Agent-Id: WAG-0001
X-Wolf-Agent-Secret: <secret>

{
  "sent_at": "2026-10-29T02:00:30Z",
  "agent_version": "0.1.0",
  "hostname": "bench-01",
  "metrics": [
    {"metric_name": "cpu_usage", "value": 12.5, "timestamp": "...", "host": "bench-01",
     "bench": null, "site": null, "labels": {}}
  ],
  "events": [
    {"type": "error", "category": "http_502", "severity": "critical", "timestamp": "...",
     "host": "bench-01", "bench": "main", "site": "a.example.com", "source": "nginx",
     "title": "502 on GET /api/method/foo", "fingerprint": "sha1-of-stable-parts",
     "payload": {"route": "/api/method/foo", "status": 502, "count": 14, "sample_lines": ["..."]}}
  ]
}
```

### En-têtes

| En-tête | Valeur |
|---|---|
| `X-Wolf-Agent-Id` | `agent_id` reçu à l'enregistrement. |
| `X-Wolf-Agent-Secret` | `agent_secret` reçu à l'enregistrement. |

Les deux mêmes en-têtes authentifient le marqueur de déploiement, l'appel de statut et la route
Wazuh.

### Corps

| Champ | Signification |
|---|---|
| `sent_at` | Moment où la requête est envoyée, y compris pour les lots rejoués depuis la file locale (spool). Sert au [décalage d'horloge](#decalage-dhorloge). |
| `agent_version` | Version de l'agent. |
| `hostname` | Le nom de l'hôte. |
| `metrics` | Liste d'échantillons de métriques. |
| `events` | Liste d'événements. |
| `action_results` | Facultatif. Résultats des [actions de réponse](#actions-de-reponse). |

Un échantillon de métrique :

| Champ | Signification |
|---|---|
| `metric_name` | Voir [Noms des métriques](#noms-des-metriques). |
| `value` | Nombre. |
| `timestamp` | UTC. |
| `host`, `bench`, `site` | Périmètre. `null` là où il ne s'applique pas. |
| `labels` | Objet, par exemple `{"mount": "/"}` ou `{"queue": "default"}`. |

Un événement :

| Champ | Signification |
|---|---|
| `type` | Voir [Types d'événements](#types-devenements). |
| `category` | Sous-type plus fin au sein du type, comme `http_502`. |
| `severity` | `info`, `warning` ou `critical`. |
| `timestamp` | UTC. |
| `host`, `bench`, `site` | Périmètre. |
| `source` | Ce qui l'a produit : `nginx`, `sshd`, `supervisor`… |
| `title` | Une ligne. |
| `fingerprint` | Empreinte des parties stables de l'événement, utilisée pour dédoublonner. |
| `payload` | Objet contenant les détails, selon la catégorie. |

### Réponse

```json [Réponse]
{"message": {"metrics": 1, "events": 1, "rejected": [], "push_interval": 30, "health": {...},
             "clock_skew_seconds": 2, "clamped": 0, "queued": true, "actions": []}}
```

| Champ | Signification |
|---|---|
| `metrics`, `events` | Éléments acceptés. En mode asynchrone, éléments qui ont passé la validation et ont été mis en file d'attente. |
| `rejected` | Éléments refusés. |
| `push_interval` | Nombre de secondes que l'agent doit laisser entre deux envois. |
| `health` | Le heartbeat de Wolf lui-même (voir [Santé de Wolf](#sante-de-wolf-heartbeat)). `null` si le site n'a pas pu le calculer ; absent sur les serveurs plus anciens. |
| `clock_skew_seconds` | `sent_at` moins l'heure du serveur. |
| `clamped` | Horodatages ramenés à l'heure du serveur. |
| `queued` | `true` quand le lot a été mis en file d'attente, `false` quand il a été stocké pendant la requête. Absent sur les serveurs plus anciens : les agents ne doivent pas s'y fier. |
| `actions` | Actions de réponse approuvées pour cet agent et pas encore rapportées. Vide quand il n'y en a aucune. |

### Actions de réponse

`actions` contient les blocages qu'un Wolf Manager a approuvés pour cet agent et que celui-ci n'a
pas encore rapportés :

```json [actions]
[{"id": "WRA-00001", "action": "block_ip", "ip": "45.33.32.156", "seconds": 86400}]
```

L'agent envoie chaque résultat dans un envoi ultérieur :

```json [action_results]
"action_results": [{"id": "WRA-00001", "ok": true, "detail": "..."}]
```

Un id n'est accepté qu'une fois, et uniquement de la part de l'agent auquel il a été donné. Voir
[Actions de réponse](/fr/agent/response-actions) et [Sécurité](/fr/security).

### Mode d'ingestion

Se définit dans **Wolf Settings → Ingest Mode**.

| Mode | Comportement |
|---|---|
| `async` (par défaut) | L'app valide et normalise le lot pendant la requête, met les insertions en file d'attente pour un worker en arrière-plan et répond `"queued": true`. Le worker les insère et rattache les événements aux incidents ouverts quelques secondes plus tard. Un échec dans le worker n'est pas remonté à l'agent : il figure dans l'Error Log du site. |
| `sync` | Le lot est stocké pendant la requête et `queued` vaut `false`. Les erreurs de stockage font échouer la requête (HTTP 5xx) et l'agent réessaie. |

Si la file d'attente est injoignable en mode `async`, le lot est stocké comme en mode `sync`. Dans
les deux modes, la dernière heure de contact de l'agent et son décalage d'horloge sont enregistrés
pendant la requête, pour que les heartbeats n'attendent pas la file d'attente.

### Limite de débit

Les envois sont comptés par agent sur des fenêtres d'une minute : **Wolf Settings → Max Pushes Per
Minute**, par défaut `120`, `0` = désactivé. Au-delà de la limite, le serveur répond HTTP 429. Les
agents et les satellites traitent un 429 comme une erreur réseau : le lot reste dans la file locale
et est rejoué après un délai croissant.

### Nettoyage (scrubbing)

L'agent retire les adresses e-mail, identifiants, numéros de carte et IBAN des titres et payloads
des événements avant l'envoi (voir [Nettoyage (scrubbing)](/fr/agent/scrubbing)). Le serveur stocke
ce qu'il reçoit tel quel.

### Décalage d'horloge

- `sent_at` est horodaté au moment de l'envoi de la requête, y compris pour les lots rejoués depuis
  la file locale.
- Le serveur enregistre `sent_at - server time` comme `clock_skew_seconds` de l'agent (positif =
  agent en avance, affiché sur **Wolf Agent**) et le renvoie. L'agent journalise un avertissement
  au-delà de 60 s.
- Les horodatages de métriques et d'événements situés dans le futur au-delà de **Wolf Settings →
  Max Clock Skew** (par défaut 300 s, `0` = désactivé) sont ramenés à l'heure du serveur et comptés
  dans `clamped`.
- Les fenêtres des règles et les graphiques ignorent aussi les lignes horodatées plus d'une minute
  dans le futur.

### Codes de statut et limites

| Réponse | Comportement de l'agent |
|---|---|
| HTTP 401 / 403 | Identifiants erronés : l'agent s'arrête et journalise. |
| HTTP 429 | Limite de débit dépassée : traité comme une erreur réseau. |
| HTTP 5xx ou erreur réseau | L'agent garde le lot dans sa file locale sur disque et réessaie avec un délai croissant. |

Au plus 5000 métriques et 1000 événements par requête. L'agent découpe les lots plus gros.

### Satellites

Les satellites utilisent le même point d'accès avec leurs identifiants de satellite.

- Ils n'envoient aucune métrique.
- Au plus 100 événements par requête.
- Chaque événement a des `host`, `bench`, `site`, `fingerprint` et `count` explicites. Les doublons
  vus avant la transmission sont fusionnés en un seul événement.
- Un corps vide envoyé chaque minute leur sert de heartbeat.

| Réponse | Comportement du satellite |
|---|---|
| 401 / 403 | Nouvel essai dans 15 minutes. |
| Autre 4xx (sauf 408 / 429) | Le lot est abandonné. |
| 5xx ou erreur réseau | Nouvel essai après 1, 2, 4, 8, puis 15 minutes. |

### Enrichissement à l'ingestion

- **Réputation d'IP.** Quand la réputation d'IP est activée, un événement de sécurité dont l'`ip`
  du payload figure sur une liste de blocage téléchargée reçoit
  `reputation: {"listed": true, "lists": [...]}` et un cran de gravité supplémentaire.
- **MITRE ATT&CK.** Les payloads de sécurité peuvent porter `attack_techniques`, une liste
  d'identifiants de techniques (`T1110`, `T1552.001`). L'app ajoute `mitre_attack`, une liste de
  `{id, name, tactic}` qui fusionne ces identifiants avec la correspondance propre à la catégorie
  (voir [Sécurité](/fr/security)).
- **Entités.** Chaque événement `security` reçoit `payload.entities`, quelle que soit sa source :
  `{"ip": [...], "host": [...], "site": [...], "user": [...]}`, normalisé et résolu via les lignes
  **Wolf Entity Alias**. Les agents ne l'envoient pas : le site le calcule.

| `hsts_max_age_days` | jours | host, bench, site, `labels.domain` : max-age de `Strict-Transport-Security` dans la première réponse à `HEAD /` sur la connexion du contrôle TLS, 0 sans l'en-tête ; aucun échantillon quand aucune réponse HTTP n'est revenue ; toutes les heures |
| `app_version` | numéro de version | host, bench, `labels.app` : `__version__` de `apps/<app>/<app>/__init__.py` sous la forme majeure × 10⁶ + mineure × 10³ + correctif (15.100.0 → 15100000) ; les versions de développement (`16.0.0-dev`) ne sont pas envoyées ; toutes les heures (`versions.interval`) |
| `site_setting` | valeur | host, bench, site, `labels.setting` : une valeur des System Settings lue dans la base de données du site (`enable_two_factor_auth`, `enable_password_policy`, `minimum_password_score`, `allow_consecutive_login_attempts`, `allow_guests_to_upload_files` ; non définie → 0) et `system_manager_2fa` (le `two_factor_auth` du rôle System Manager) ; toutes les heures (`site_settings.interval`) |
| `exposed_services` | nombre | host : ports du bench (MariaDB/Postgres, Redis du bench, socket.io, gunicorn) à l'écoute sur toutes les interfaces ou une adresse publique, d'après `/proc/net/tcp{,6}` ; toutes les 10 min |
| `integrity_files` | nombre | bench (ou hôte, pour les chemins `/etc`) : fichiers sous surveillance d'[intégrité](/fr/security/detection#intégrité-des-fichiers) (code des apps, configurations de site, configuration nginx et supervisor) ; toutes les 15 min |
| `integrity_unreadable` | nombre | bench (ou hôte) : fichiers ou dossiers surveillés que l'agent n'a pas pu lire, gardés à leur référence ; toutes les 15 min |
| `site_config_risks` | nombre | host, bench, site : `developer_mode`, `allow_tests`, un `host_name` en HTTP simple, `allow_cors: "*"` dans la configuration de site fusionnée ; toutes les 10 min |
| `security_score` | 0–100 | site : écrit par l'app (toutes les heures), pas par l'agent ; voir [Sécurité](/fr/security) |
| `user_export_bytes` | octets par heure | site, `labels.user` : octets de réponse des exports et lectures de listes d'un utilisateur sur l'heure écoulée, écrit par l'app (toutes les heures) ; voir [Sécurité](/fr/security) |
| `db_threads_connected` | connexions | host, bench (quand un seul bench utilise le serveur), `labels.db` (`host:port`) |
| `db_connections_used_percent` | % | idem : `Threads_connected` / `max_connections` |
| `db_slow_queries` | requêtes par intervalle d'envoi | idem : augmentation de `Slow_queries` |
| `db_replication_lag_seconds` | s | idem : `Seconds_Behind_Master`, uniquement sur un réplica et avec REPLICATION CLIENT |
| `db_replication_running` | 0/1 | idem : les deux threads du réplica tournent |
| `bench_processes_down` | processus | host, bench, `labels.manager` : processus supervisor en STOPPED/EXITED/BACKOFF/FATAL/UNKNOWN, ou unités systemd `failed` / en boucle de redémarrage |

Les agents plus anciens que ces signaux ne les envoient pas. L'app accepte n'importe quel nom de
métrique : aucune modification côté serveur n'est nécessaire pour les recevoir ; les règles
prédéfinies ont seulement besoin que les échantillons existent.

## Marqueur de déploiement

```http [POST /api/method/dodock_wolf.api.ingest.deployment]
POST /api/method/dodock_wolf.api.ingest.deployment
X-Wolf-Agent-Id: WAG-0001
X-Wolf-Agent-Secret: <secret>

{"bench": "main", "site": null, "note": "bench update", "source": "manual", "timestamp": "...",
 "silence_minutes": 15}
```

Équivaut à envoyer un seul événement `deployment`. `wolf-agent mark-deployment` l'appelle (voir
[Commandes](/fr/agent/commands)).

| Champ | Signification |
|---|---|
| `bench`, `site` | Périmètre du déploiement. |
| `note` | Texte libre. |
| `source` | Par exemple `manual`. |
| `timestamp` | UTC. |
| `silence_minutes` | Facultatif. Entier positif : ouvre aussi une fenêtre de maintenance. |

`silence_minutes` a été ajouté après la v1 et reste rétrocompatible : les apps plus anciennes
l'ignorent, et les agents l'omettent sauf si `--silence` est fourni. Quand c'est un entier positif,
l'app crée un **Wolf Silence** à partir de maintenant pour ce nombre de minutes, plafonné à 24 h,
dont le périmètre est l'hôte de l'agent plus le bench et le site indiqués.

- Les incidents correspondant au silence s'ouvrent et se mettent à jour quand même, pour que la
  chronologie reste complète.
- Leurs notifications sont retenues.
- Les incidents encore ouverts à la fin de la fenêtre sont alors notifiés.

Réponse :

```json [Réponse]
{"message": {"event": "<Wolf Event name>", "silence": "WSIL-00001", "silence_until": "2026-10-29 02:15:00"}}
```

`silence` et `silence_until` (fuseau horaire du site) ne sont présents que lorsqu'un silence a été
créé.

::warning
Un agent qui a demandé un silence et ne reçoit pas de clé `silence` en retour dialogue avec une app
qui ne gère pas les silences, et doit émettre un avertissement.
::

## Santé de Wolf (heartbeat)

```http [GET|POST /api/method/dodock_wolf.api.ingest.status]
GET /api/method/dodock_wolf.api.ingest.status
X-Wolf-Agent-Id: WAG-0001
X-Wolf-Agent-Secret: <secret>
```

Réponse : `{"message": {"agent": "WAG-0001", "push_interval": 30, "health": {...}}}`.

Le même objet `health` revient avec chaque envoi : l'agent n'a donc pas besoin d'interroger
`status`. Cet appel sert à `wolf-agent check` et aux scripts. Il est en lecture seule : il ne met
pas à jour la dernière heure de contact de l'agent.

```json [health]
{
  "ok": false,
  "problems": ["alert rules not evaluated for 12 min; scheduler disabled (pause_scheduler)"],
  "checked_at": "2026-10-29T02:12:30Z",
  "server_version": "0.1.0",
  "rules": {"last_evaluated": "2026-10-29T02:00:01Z", "age_seconds": 749},
  "scheduler": {"enabled": false, "reason": "pause_scheduler",
                "last_job_run": "2026-10-29T02:00:00Z", "age_seconds": 750},
  "queues": {"lengths": {"short": 0, "default": 3, "long": 0}, "workers": 2,
             "ingest_queue": "short", "ingest_backlog_seconds": null}
}
```

| Champ | Signification |
|---|---|
| `rules.last_evaluated` | Le `last_evaluated` le plus récent parmi les **Wolf Alert Rules** activées (le moteur de règles tourne à chaque tick du planificateur) ; `null` si aucune règle n'a encore tourné. |
| `scheduler.enabled` / `reason` | `false` avec `maintenance_mode`, `pause_scheduler`, `disable_scheduler` ou `enable_scheduler unset in System Settings`. |
| `scheduler.last_job_run` | Le `Scheduled Job Type.last_execution` le plus récent, horodaté quand un worker démarre un job. |
| `scheduler.tick_seconds` | Secondes entre deux ticks du planificateur (scheduler) de Frappe, donc entre deux évaluations des règles : 240 sur Frappe 15 et Dodock sauf si `scheduler_tick_interval` est défini ; `null` sur un Frappe sans ce paramètre. Informatif, jamais un problème. |
| `*.age_seconds` | `now - timestamp` côté serveur, si bien que le décalage d'horloge de l'agent n'a pas d'importance. **Négatif** quand l'heure stockée est dans le futur, ce qui arrive après un changement de fuseau horaire du système et bloque le planificateur jusqu'à cette heure. |
| `queues` | Longueurs des files d'attente RQ et nombre de workers du bench, ou `{"error": "..."}` si Redis est injoignable. |
| `queues.ingest_backlog_seconds` | Depuis combien de temps le plus ancien job de la file d'ingestion (`ingest_queue`) attend ; `null` quand elle est vide. Les envois mis en file d'attente reçoivent une réponse avant d'être stockés : c'est donc le seul signe que la télémétrie n'arrive pas. |
| `ok` / `problems` | La lecture propre du serveur, avec un seuil de 5 minutes. |

Deux situations sont des problèmes :
- **obsolescence** : `abs(age) >= stale threshold` sur `rules`, ou sur `scheduler` quand aucune
  règle n'est activée ;
- **retard d'ingestion** : `ingest_backlog_seconds >= stale threshold`.

L'état du planificateur et des files d'attente est un contexte ajouté au texte d'obsolescence.
L'agent applique son propre seuil (`watchdog.stale_minutes`) aux âges bruts plutôt que de se fier
à `ok`.

Tant que les règles sont obsolètes, chaque envoi enregistre aussi un événement
`host_metric_alert` / `scheduler_stalled` sur le site, incrémenté plutôt que dupliqué pendant
15 minutes. La règle prédéfinie **Scheduler stalled** le transforme en incident dès que le
planificateur tourne à nouveau. Un site bloqué ne peut pas alerter sur lui-même : l'alerte en
direct est donc émise par le chien de garde (watchdog) de l'agent via son propre canal de secours
(voir [Chien de garde (watchdog)](/fr/agent/watchdog)).

## Intégration Wazuh

```http [POST /api/method/dodock_wolf.api.wazuh.alert]
POST /api/method/dodock_wolf.api.wazuh.alert
X-Wolf-Agent-Id: WAG-0005
X-Wolf-Agent-Secret: <secret>
Content-Type: application/json

<one Wazuh alert, as Wazuh writes it in alerts.json>
```

| Aspect | Règle |
|---|---|
| Identifiants | Un **Wolf Agent** enregistré avec `"kind": "integration"`, via le même [enregistrement](#enregistrement). Il n'est jamais signalé comme silencieux, puisqu'il n'envoie que lorsque Wazuh a une alerte. |
| Ce que Wolf conserve | L'alerte devient un événement `hids_alert`, traité comme par le lecteur `alerts.json` de l'agent. Le groupe `dodock_wolf` (les alertes de Wazuh sur l'export de Wolf lui-même) et le groupe `sca` ne sont pas stockés, et la réponse en donne la raison : `{"stored": false, "reason": ...}`. |
| Répétitions | La même règle et le même sujet dans un délai de 10 minutes incrémentent le compteur de l'événement. |

| Émetteur | [`agent/wazuh/custom-dodock-wolf`](https://github.com/bthuner/dodock-wolf/blob/main/agent/wazuh/custom-dodock-wolf), le script qu'exécute le démon d'intégration de Wazuh. |

## Liens d'action sur les incidents

Les alertes par e-mail, Raven et webhook pour les incidents non résolus portent des liens signés :

```http [GET /api/method/dodock_wolf.api.actions.incident_action]
GET /api/method/dodock_wolf.api.actions.incident_action
    ?incident=WINC-00012&action=ack|resolve&expires=<unix seconds>[&actor=<email>]&sig=<hex>
```

| Paramètre | Signification |
|---|---|
| `incident` | Le **Wolf Incident**. |
| `action` | `ack` ou `resolve`. |
| `expires` | Secondes Unix. |
| `actor` | L'adresse du destinataire dans les e-mails (un e-mail par destinataire). Absent pour Raven et les webhooks. |
| `sig` | HMAC-SHA256 sur `wolf-incident-action\n<incident>\n<action>\n<expires>\n<actor>`, avec une clé dérivée de l'`encryption_key` du site. |

Les liens expirent après **Wolf Settings → Action Link Hours** (par défaut 24, `0` les désactive).

Un GET affiche seulement une page de confirmation. Son bouton envoie les mêmes paramètres en POST,
et seul le POST acquitte ou résout : les scanners de liens ne peuvent donc pas agir sur un
incident. L'incident enregistre `acknowledged_by` / `resolved_by` comme l'utilisateur connecté,
sinon l'`actor`, sinon `link`.

Où apparaissent les liens :

| Canal | Forme |
|---|---|
| Webhook | `incident.actions = {"ack": "...", "resolve": "..."}`, vide une fois résolu |
| Slack | Boutons Block Kit |
| Mattermost | Liens en pièce jointe (attachments) |
| ntfy | En-tête `Actions` |
| Matrix, Gotify, SMS | URL de l'incident uniquement |

Les résumés horaires sont envoyés aux webhooks sous cette forme :

```json [Corps du webhook de résumé]
{"text": "...", "digest": [{"incident", "kind", "severity", "title", "at", "url"}]}
```

### Liens de réponse

Un lien par action que Wolf propose sur l'incident, jusqu'à 5 :

```http [GET /api/method/dodock_wolf.api.actions.response_action]
GET /api/method/dodock_wolf.api.actions.response_action
    ?incident=WINC-00012&action=block_ip|disable_user|logout_sessions|revoke_api_keys&target=<ip or user>
    [&agent=<Wolf Agent>&hours=<1..168>]&expires=<unix seconds>[&actor=<email>]&sig=<hex>
```

`sig` est un HMAC-SHA256 sur
`wolf-response-action\n<incident>\n<action>\n<target>\n<agent>\n<hours>\n<expires>\n<actor>`
avec la même clé.

::caution
Seul un Wolf Manager ou un System Manager connecté peut confirmer (POST), selon les règles du
panneau Response.
::

| Canal | Forme |
|---|---|
| E-mail (un par destinataire), Raven, Matrix, Gotify, ntfy | Liens dans le texte et le HTML de l'alerte |
| Webhook | `incident.responses = [{"label", "url"}]` |
| Slack | Boutons |
| Mattermost | Liens |
| SMS | Aucun |

## Canaux natifs

Chaque canal natif est un constructeur pur dans
[`dodock_wolf/wolf/channels/`](https://github.com/bthuner/dodock-wolf/blob/main/dodock_wolf/wolf/channels/)
qui convertit une notification au format documenté du service. Les docstrings des modules citent
les pages de référence. Voir [Canaux](/fr/alerts/channels) pour la configuration.

| Canal | Requête |
|---|---|
| Slack | `POST <webhook>` `{"text", "attachments": [{"color", "fallback", "blocks": [section, actions]}]}` |
| Mattermost | `POST <webhook>` `{"attachments": [{"fallback", "color", "pretext", "title", "title_link", "text", "fields", "footer"}]}` |
| Matrix | `PUT <homeserver>/_matrix/client/v3/rooms/<room>/send/m.room.message/wolf-<attempt>` (jeton Bearer) `{"msgtype": "m.text", "body", "format": "org.matrix.custom.html", "formatted_body"}` |
| ntfy | `POST <server>/<topic>`, corps = texte, en-têtes `Title` (RFC 2047 quand ce n'est pas de l'ASCII), `Priority`, `Tags`, `Click`, `Actions`, `Authorization: Bearer` facultatif |
| Gotify | `POST <server>/message` (`X-Gotify-Key`) `{"title", "message", "priority", "extras": {"client::display", "client::notification": {"click": {"url"}}}}` |
| SMS | Le modèle configuré, une requête par numéro |
| PagerDuty | `POST <events url>` `{"routing_key", "event_action", "dedup_key": "<incident>", "payload": {"summary", "source", "severity", "component", "group", "class", "custom_details"}, "client", "client_url", "links"}` (payload au déclenchement uniquement) |

Actions d'événement PagerDuty :

| Notification Wolf | `event_action` |
|---|---|
| `fired`, `reopened`, `escalated` | `trigger` |
| Acquittement | `acknowledge` |
| Résolution | `resolve` |
| Test | `trigger`, puis `resolve` |

### Wolf Delivery

Chaque requête est enregistrée comme un **Wolf Delivery** :

| Champ | Signification |
|---|---|
| `incident`, `alert_rule` | Ce qui a été notifié. |
| `at` | Quand. |
| `channel_type` | Slack, Matrix, PagerDuty… |
| `target` | La destination sans secrets : hôte, salon, numéros de téléphone masqués. |
| `kind`, `action`, `digest` | Ce qui a été envoyé. |
| `ok`, `http_status` | Le résultat. |
| `error` | L'erreur, sans les secrets ni les chemins et paramètres des URL. |

Les résumés des canaux natifs sont regroupés selon un SHA-256 des paramètres du canal, et
l'élément de résumé garde une référence à la ligne du canal plutôt qu'un quelconque secret.
