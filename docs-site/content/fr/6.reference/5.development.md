## État

MVP, testé sur un bench Dokos (Dodock 5.18), sur MariaDB 10.6 et sur Postgres 17 (voir
[`ci/db_smoke.py`](https://github.com/bthuner/dodock-wolf/blob/main/ci/db_smoke.py)).

## Pile de démo

La pile de démo de [`dev/demo`](https://github.com/bthuner/dodock-wolf/tree/main/dev/demo) fait
tourner un bench Dokos avec la Wolf App et son agent, nginx et un récepteur de webhooks
(`docker compose logs catcher`).

### Suricata et Wazuh

Le profil `ids` fait tourner un vrai Suricata (avec ET Open) sur le réseau du bench et un vrai
manager Wazuh qui lit son journal nginx, chacun avec l'agent Wolf qui le lit. `ids_scenario.py`
envoie ensuite un attaquant : la détection web de Wolf, Suricata et Wazuh le signalent chacun,
dans un seul incident.

```bash [dev/demo]
docker compose --profile ids up -d --build
python3 ids_scenario.py
```

## Wolf UI

L'interface opérateur à `/wolf` est une app Vue construite sur [frappe-ui](https://ui.frappe.io)
dans [`frontend/`](https://github.com/bthuner/dodock-wolf/blob/main/frontend/)
([#19](https://github.com/bthuner/dodock-wolf/issues/19)).

- Le Desk conserve les DocTypes de configuration et reste utilisable pour tout ce que la Wolf UI
  n'affiche pas encore.
- Ses vues sont ajoutées une par une. Une vue qui n'est pas encore réalisée le dit et renvoie vers
  le Desk.
- Elle réutilise la session Frappe : les invités sont envoyés vers la page de connexion, les
  utilisateurs sans le rôle Wolf User ou Wolf Manager reçoivent un 403.

Des captures d'écran, en thème clair et sombre, toutes prises sur le bench de démonstration après
son scénario de 2 h du matin, se trouvent dans
[`docs/screenshots`](https://github.com/bthuner/dodock-wolf/blob/main/docs/screenshots/README.md).

```bash [frontend/]
cd frontend
yarn install
yarn dev        # Vite sur le port du bench + 80 (8080 pour 8000), avec proxy vers le bench
yarn test       # tests unitaires et de composants (Vitest)
yarn build      # écrit dodock_wolf/public/frontend et dodock_wolf/www/wolf.html
yarn e2e        # tests navigateur de ce build (Playwright + axe), après `yarn build`
```

::note
Node 20.19 ou version ultérieure est requis. Le résultat du build n'est pas commité :
`bench build --app dodock_wolf` le produit sur le bench.
::

### Tests navigateur

Les tests navigateur (`frontend/e2e/`) servent le build de production comme le ferait un bench
(`e2e/server.mjs`) et répondent à chaque appel d'API de la page (`e2e/api.js`) : aucun Frappe n'est
donc nécessaire.

Chaque vue doit :
- s'afficher sans erreur dans la console ni appel resté sans réponse ;
- passer axe sans aucun constat WCAG 2 A/AA grave ou critique, en thème clair comme en thème
  sombre.

La navigation au clavier, la réduction des animations, l'acquittement d'un incident et le
déplacement du focus clavier sont vérifiés aussi.

`e2e/states.spec.js` fait passer chaque vue par les états chargement, vide, vide après filtrage,
erreur, interdit, partiel, obsolète et déconnecté. Une vue n'affirme jamais « rien » avant d'avoir
lu, ou après un échec de lecture, et un refus indique ce qui ne peut pas être vu.

Les tests nécessitent Chromium : lancez `npx playwright install chromium`, ou faites pointer
`WOLF_CHROMIUM` vers une installation existante.

Les API que lit l'UI sont décrites dans [API de l'UI](/fr/reference/ui-api).

## Vérifications de la CI

Chaque pull request et chaque push sur `main` exécute
[`.github/workflows/ci.yml`](https://github.com/bthuner/dodock-wolf/blob/main/.github/workflows/ci.yml) :

| Job | Environnement |
|---|---|
| Lint (ruff, shellcheck) | |
| Tests de l'app | Python 3.12 |
| Tests de l'agent | Python 3.9 et 3.14 |
| Tests et build de la Wolf UI | Node 20.19 et 24 |
| Tests navigateur de la Wolf UI | Playwright + axe |
| Intégration avec un bench | MariaDB 10.6 et Postgres 16 |

Pour lancer les mêmes vérifications en local :

```bash [racine du dépôt]
pip install ruff==0.17.3                             # les règles ruff sont dans pyproject.toml
ruff check .
shellcheck agent/install.sh ci/integration.sh
python3 -m unittest discover -s tests -t .
python3.9 -m unittest discover -s agent/tests        # l'agent doit continuer de fonctionner sous 3.9
```

### Job d'intégration

Le job d'intégration installe ce checkout dans l'image Dokos publique, crée un site et lance
[`ci/db_smoke.py`](https://github.com/bthuner/dodock-wolf/blob/main/ci/db_smoke.py), qui exerce
chaque chemin SQL de Wolf.

::tabs
  :::tabs-item{label="MariaDB"}
  ```bash [racine du dépôt]
  docker network create wolf-ci
  docker run -d --name db --network wolf-ci -e MARIADB_ROOT_PASSWORD=admin mariadb:10.6 \
    --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
  docker run -d --name redis --network wolf-ci redis:6.2-alpine
  docker run --rm --network wolf-ci --entrypoint bash -v "$PWD:/src:ro" \
    registry.gitlab.com/dokos/dokos:latest /src/ci/integration.sh mariadb
  ```
  :::
  :::tabs-item{label="Postgres"}
  Démarrez `postgres:16` sous le nom `db` avec `-e POSTGRES_PASSWORD=admin`, et passez `postgres` à
  `integration.sh` au lieu de `mariadb`. Le conteneur `redis` et le réseau sont les mêmes.
  :::
  :::tabs-item{label="Bench existant"}
  ```bash [sites/]
  ../env/bin/python /path/to/ci/db_smoke.py <site>
  ```
  :::
::

Pour ajouter le test de charge à la même exécution du conteneur, voir
[Performance](/fr/reference/performance#dans-le-conteneur-de-la-ci).

## Ce site de documentation

Le site utilise Nuxt 4 + Nuxt UI 4 + Nuxt Content 3, dans `docs-site/`.

```bash [docs-site/]
nvm use            # Node 24 (.nvmrc)
yarn install
yarn dev           # http://localhost:3000, le français sur /fr
yarn generate      # site statique dans .output/public
```

- Les pages anglaises sont dans `content/en/`, servies à `/`. Les pages françaises sont dans
  `content/fr/`, servies à `/fr`, avec les mêmes noms de fichiers.
- Le préfixe numérique d'un fichier ou d'un dossier ordonne les pages et disparaît de l'URL.
- Chaque page anglaise a une jumelle française au même chemin, si bien que le sélecteur de langue
  mène à la même page.

Le plan des pages, le front matter, les composants et le ton sont décrits dans
[`docs-site/CONTRIBUTING.md`](https://github.com/bthuner/dodock-wolf/blob/main/docs-site/CONTRIBUTING.md).
