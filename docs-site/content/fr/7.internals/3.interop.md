Les applications ne partagent aucune base de données. Chaque lien ci-dessous est une requête HTTPS, sauf mention contraire.

## Les appels

### Contrôle

| De → vers | Quoi | Authentifié par |
|---|---|---|
| Console → Central | Tout ce que fait une personne | Session Frappe, puis une capacité |
| Central → Atlas | `{region}/api/atlas/…` : les machines et leurs actions, les images, les métriques, les hôtes | Jeton `atlas-admin:<region>`, 5 minutes, `tenant=*`, plus `X-Tenant-ID: <team's tenant number>` |
| Atlas → Central | `vm.state` et `vm.state.deleted` vers `central.api.state_delivery.receive` | HMAC-SHA256 du corps, avec un secret que Central a défini par `PUT /api/atlas/webhooks` |
| Central → Cargo | `cargo.object_storage.api.bucket.*`, les images one-click, `webhooks.configure` | En-tête `X-Cargo-Access-Token` : jeton `atlas-cargo:<region>`, 5 minutes |
| Cargo → Central | `storage` ou `telemetry` est `Available` ou `Not Available`, et à quelle adresse | HMAC, comme Atlas. Cargo ne détient aucun identifiant de Central |
| Cargo → Atlas | Loue des machines, définit leurs métadonnées et leur pare-feu, en prend des instantanés pour en faire des images, enregistrements DNS | Jeton `atlas-admin:<region>` en tant que locataire 0, portée `*`, **365 jours**, donné à l'installation |
| Atlas → Cargo | Un bucket pour les propres images d'Atlas | Jeton `atlas-cargo:<region>`, 5 minutes |
| Atlas → les hôtes | `metald`, port 9000, toutes les 10 secondes | TLS mutuel, une autorité privée par région |
| Central → le proxy | `PATCH` et `DELETE` sur `/v1/sites/<name>` et `/v1/domains/<domain>` | Jeton `atlas-proxy:<region>`, portée `site:* domain:*` |
| Central → la passerelle WireGuard | `/v1/peers` | Jeton `atlas-wg-gateway:<region>` |
| Central → Pilot | `https://admin-vm-<label>.<region domain>/api/v1/…` : connexion au site, renommage, domaines, applications, réglages | Jeton signé avec la clé Pilot de Central, audience = l'identifiant de ce bench, portée `bench` ou `site`, 5 minutes. **Par le proxy public**, pas par le réseau privé |
| Pilot → Central | `central.api.pilot.*`, `report_pilot_event`, la facturation, les jetons GitHub | En-tête `X-Pilot-Token`, lu dans les métadonnées de la machine à chaque appel, jamais écrit sur le disque |
| Un site → Pilot → Central | `GET` ou `POST /api/v1/sites/<site>/central/<method>` sur la boucle locale, pour une liste d'autorisation : `heartbeat`, `get_team_identity_token`, `email_oauth.*`, `billing_api.*` | Le `pilot_auth_token` du site, puis `X-Pilot-Token` |
| Le programme de domaines de Cargo → Central | `central.api.pilot.domain_records`, `register_domain`, `deregister_domain` | `X-Pilot-Token` (le programme est sur le serveur ; Pilot le lance) |

### Télémétrie

| De → vers | Quoi | Authentifié par |
|---|---|---|
| Pilot → Datum | Huit métriques et les événements de mise à jour ([la liste](/fr/internals/customer-server#ce-qui-quitte-le-serveur)) | Jeton `atlas-datum:<region>` signé par Central, 7 jours, `resource_id` = l'identifiant Atlas de la machine |
| `metald` → Datum | `system_*` et `metal_*` de chaque hôte. Un identifiant de machine n'est jamais une étiquette | Jeton signé par Atlas, 7 jours, renouvelé chaque jour à 03:30 |
| Vector → Datum | Le journal systemd et les métriques machine des hôtes, des machines de service et des machines de Cargo | Idem, ou un jeton de Cargo |
| Atlas → Datum | `atlas_*`, ses Error Logs, `bmc_*` | Jeton signé par Atlas, 5 minutes |
| Cargo → Datum | `cargo_*`, ses Error Logs | Jeton signé par Cargo, 7 jours |
| Central → Datum | `central_*`, ses Error Logs, vers **une seule** région | Jeton signé par Central |
| Datum → ClickHouse | Des insertions, sur la boucle locale | Un mot de passe ClickHouse |

### Lecture et alertes

| De → vers | Quoi | Authentifié par |
|---|---|---|
| Beacon → ClickHouse | Du SQL par `https://telemetry-read-svc.<region domain>` | Authentification Basic, utilisateur `beacon`, lecture seule |
| Beacon → Atlas | `GET /api/atlas/beacon/resources`, chaque minute | Une clé d'API Frappe. Atlas ne donne cette route qu'à l'identité de Central, et traite un System Manager comme Central : Beacon détient donc une **clé System Manager sur l'Atlas de chaque région** (déduit des deux extrémités du code) |
| Beacon → GitHub | Les fichiers de règles du dépôt de chaque producteur | Un jeton GitHub facultatif |
| Beacon → Twilio, messagerie instantanée, e-mail | Des appels et des messages | Une clé d'API Twilio ; le secret dans l'adresse du webhook de messagerie instantanée |
| Twilio → Beacon | Le statut de l'appel | Un HMAC dans l'adresse de rappel |
| Central → ClickHouse | Les rapports de facturation et l'investigateur de l'opérateur, par une source de données Insights | Un mot de passe ClickHouse |
| Atlas → ClickHouse | Le SQL en lecture seule de l'investigateur | Un mot de passe ClickHouse |

Le graphique d'un serveur dans la console de Central ne vient **pas** de Datum : Central demande à Atlas (`…/virtual-machines/<id>/metrics`).

## Clés

| Clé | Détenue par | Signe |
|---|---|---|
| Clé du plan Atlas (Ed25519) | Central | Chaque jeton destiné à une région : `atlas-admin`, `atlas-proxy`, `atlas-cargo`, `atlas-wg-gateway`, `atlas-datum` |
| Clé Pilot (Ed25519) | Central | Les jetons pour l'Admin d'un serveur, et les jetons d'identité d'équipe |
| Clé OIDC (RS256) | Central | La connexion à Warpgate et aux outils internes |
| Clé de région (Ed25519) | Chaque Atlas | Les cinq mêmes audiences, pour sa propre région |
| Clé Cargo (Ed25519) | Chaque Cargo | Les jetons Datum et les jetons de ses machines |
| Secret du site (HS256) | Chaque bench (`bench.toml`) | Les sessions Admin et le `pilot_auth_token` de chaque site |

Aucune rotation n'est implémentée pour aucune des clés Ed25519.

### La chaîne des clés publiques

Chaque vérificateur récupère ses clés auprès de la couche au-dessus de lui :

1. **Central** publie ensemble sa clé Pilot et sa clé du plan Atlas à `central.api.jwks.get_jwks`.
2. **Atlas** les récupère toutes les 5 minutes et les publie avec sa propre clé à `/api/atlas/jwks.json`. Le proxy, la passerelle WireGuard et Cargo vérifient les jetons avec ce jeu.
3. **Cargo** ajoute sa propre clé et publie les trois à `cargo.api.jwks.get_jwks`.
4. **Datum** est configuré avec l'adresse de Cargo, et rien d'autre.

Datum fait donc confiance à Central et à Atlas à travers Cargo, et le Pilot d'un client fait confiance à Central directement (les clés arrivent avec les métadonnées de la machine, puis depuis l'adresse de Central).

Comme un même jeu porte les clés de deux plans, chaque vérificateur doit vérifier l'audience et la portée, pas la signature seule. Pilot vérifie la signature et l'audience, pas l'émetteur.

## Jetons

| Jeton | Signé par | Audience | Durée de vie | Porte |
|---|---|---|---|---|
| Appel à une région | Central | `atlas-admin:<region>` | 5 min | `scope=*`, `tenant=*` |
| Route du proxy | Central | `atlas-proxy:<region>` | 5 min | `scope="site:* domain:*"` |
| Appel à Cargo | Central ou Atlas | `atlas-cargo:<region>` | 5 min | Cargo ne vérifie aucune portée : tout jeton valide peut appeler toutes les méthodes |
| Écriture Datum, pour un Pilot | Central | `atlas-datum:<region>` | 7 jours | `resource_id`, `access=["write"]` |
| Écriture Datum, pour un hôte | Atlas | `atlas-datum:<region>` | 7 jours | Idem |
| Jeton de Cargo pour Atlas | Atlas | `atlas-admin:<region>` | 365 jours | `tenant=0`, `scope=*` |
| Jeton de Cargo pour le proxy | Atlas | `atlas-proxy:<region>` | 365 jours | Seulement les sites dont le nom finit par `-svc` |
| Jeton d'une machine de Cargo | Cargo | `cargo:machine` | Sans expiration | Honoré tant que l'enregistrement de la machine dit Running |
| Appel à l'API Admin | Central | L'identifiant du bench | 5 min | `scope=bench`, `sub=admin` |
| Connexion au site | Central | L'identifiant du bench | 5 min | `scope=site`, le site |
| Ouvrir le bench | Central | L'identifiant du bench | Durée de la session (60 min par défaut) | Usage unique |
| Identité d'équipe | Central | Une adresse que le site choisit | 5 min | `sub=<team>`, `team_name`, `hosts` (les adresses des sites du serveur) |
| Console web | Atlas (aléatoire, pas un JWT) | — | 30 s | Usage unique, dans le fragment de l'adresse |
| `X-Pilot-Token` | Central (aléatoire, pas un JWT) | — | Jusqu'à ce que la machine soit supprimée ou que le personnel de Frappe le révoque | Central en conserve le SHA-256 |
| `pilot_auth_token` | Le bench | — | 365 jours | `scope=site`, un seul site |

Il n'y a de liste de révocation nulle part. Le jeton Datum de 7 jours d'un serveur supprimé est valide jusqu'à son expiration, et Pilot ne renouvelle qu'à l'expiration (quand il reste 24 heures ou moins).

## Les secrets en route vers une machine

Central transmet le `user_data` du client (16 Kio au plus) à cloud-init sans le modifier et le stocke sur la `Resource Action` : sa propre spécification dit donc qu'il ne doit contenir aucun secret de longue durée.

Les secrets de la plateforme elle-même passent par les **métadonnées de la machine**, le service à `169.254.169.254` à l'intérieur de la machine :

| Attribut | Contient | Appliqué par Pilot à |
|---|---|---|
| `pilot-central` | L'adresse de Central, le `X-Pilot-Token`, l'adresse des clés, l'identifiant d'audience du bench, une première copie des clés | Rien : lu à chaque appel |
| `pilot-common-site-config` | `fc_team`, les réglages SMTP d'une boîte aux lettres mutualisée, les clés IA pour un essai | `sites/common_site_config.json`, une fois |
| `pilot-common-config` | Le contact Let's Encrypt, `telemetry.endpoint` | `common_config.toml`, une fois |
| `pilot-config` | Les clés du bucket de sauvegarde `[s3]`, quand l'offre inclut du stockage | `bench.toml`, une fois |

Les clés SSH prennent le même chemin : Atlas sert les clés autorisées depuis les métadonnées à chaque connexion, si bien que le `~/.ssh/authorized_keys` d'une image ne contient rien (l'Admin de Pilot peut tout de même y écrire).

## Là où les régions rencontrent le client

| Nom | Où TLS se termine | Ce que le serveur reçoit |
|---|---|---|
| `<site>.<region domain>` | Au proxy, avec le certificat générique de la région | Du HTTP simple sur le port 80, depuis l'adresse privée du proxy, avec `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` |
| Un domaine personnalisé | Sur le serveur | Le flux TLS sur le port 443, transmis selon le SNI, avec un en-tête PROXY protocol v2. Pilot détient le certificat ; les défis HTTP-01 arrivent sur le port 80 |
| `admin-vm-<label>.<region domain>` | Au proxy | L'Admin de Pilot |

Un 502 ou un 504 que le proxy produit lui-même (serveur arrêté, en veille, injoignable) n'atteint jamais les journaux du serveur. Le proxy le compte, de façon agrégée, sans série par site.

Les serveurs d'une équipe dans une région partagent un réseau IPv6 privé (`fdaa:<region>:<tenant>::/64`), séparé des autres équipes en eBPF sur les hôtes. Il ne traverse pas les régions. Les machines de service de la plateforme y sont joignables.
