Tout ce qui est ici est prévu ou à vérifier, pas construit. Les décisions sont suivies dans [#136](https://github.com/bthuner/dodock-wolf/issues/136) et dans les trois revues [#133](https://github.com/bthuner/dodock-wolf/issues/133) (Datum), [#134](https://github.com/bthuner/dodock-wolf/issues/134) (Central) et [#135](https://github.com/bthuner/dodock-wolf/issues/135) (Beacon).

## Le constat qui tient

Aucune application de Frappe Cloud v2 ne lit l'intérieur d'un bench. Central n'a ni journal, ni erreur par site, ni signal de sécurité d'aucune sorte. Datum reçoit d'un serveur client huit métriques et les événements de mise à jour. Beacon ignore par conception un site isolé en échec. Atlas voit une machine depuis sa bordure.

Sur le serveur d'un client, le Wolf Agent est donc le seul collecteur de ceci : les 5xx par site, les tracebacks Frappe, les échecs du planificateur (scheduler) et des workers, les connexions Frappe et les changements de rôles, SSH et sudo, les attaques vues dans nginx, l'intégrité des fichiers, les connexions sortantes. C'est le terrain que [#136](https://github.com/bthuner/dodock-wolf/issues/136) a choisi.

## Ce que cette lecture corrige dans les revues

| La revue disait | Le code dit |
|---|---|
| Central fusionne `fc_team` dans le `common_site_config.json` du serveur (#134) | Central le met dans les métadonnées de la machine (`pilot-common-site-config`) ; c'est **Pilot** qui le fusionne une fois, au premier démarrage. Le code de Pilot ne nomme jamais `fc_team` |
| L'API Pilot de Central, c'est `heartbeat`, `datum_token`, `register_domain`, `get_team_identity_token`, `report_pilot_event` (#134) | Ce sont plus de 40 méthodes : aussi `config`, `get_server_access`, `storage_regions`, `domain_records`, `deregister_domain`, environ 28 méthodes de facturation, l'OAuth des boîtes aux lettres, les jetons de dépôt GitHub. `report_pilot_event` est dans `central.notification.api` et n'accepte que des types d'événement fixes |
| `get_team_identity_token` est difficile à atteindre pour une application (#134) | Un site l'atteint déjà : `POST /api/v1/sites/<site>/central/central.api.pilot.get_team_identity_token` sur `pilot_endpoint`, avec le `pilot_auth_token` du site lui-même. Central répond par un jeton de 5 minutes pour n'importe quelle audience que le site nomme |
| Le pare-feu par défaut autorise le trafic sortant (#134) | Le pare-feu est désactivé par défaut : tout est autorisé, en entrée comme en sortie |
| Les `server_metrics` sont des échantillons pris depuis l'extérieur de la machine (#134) | En partie : un agent invité dans chaque image ajoute la charge, la mémoire, l'usage du système de fichiers racine et l'état du système |
| Sur un serveur client, Pilot envoie un signal de vie, le nombre de sites, le statut des sauvegardes, `pilot_database_up`, le disque, les événements de mise à jour (#133) | Aussi `pilot_central_requests_last_5_minutes`, et `pilot_site_backup_failed` avec le **nom du site**. Les événements de mise à jour portent le site et jusqu'à 8 192 caractères de sortie |
| Datum accepte les jetons de Central, d'Atlas ou de Cargo (#133) | Oui, et il apprend les trois clés depuis l'adresse de **Cargo** uniquement |
| Les documents de Datum disent RSA/ECDSA (#133) | `docs/tokens.md` dit maintenant Ed25519. Un commentaire dans `CLAUDE.md` dit encore le contraire |
| Lire Datum demande une politique de ligne sur `resource_id` (#133) | Il n'y a aucune politique de ligne : un lecteur voit toute la région |
| Le pont vers Beacon : `POST /api/resource/Beacon Incident` avec une clé Responder, puis `page_on_call` (#135) | Confirmé, avec deux mises en garde. `page_on_call` appelle l'astreinte à **n'importe quelle** gravité. Et le contrôleur ne donne une valeur par défaut à `visibility` et à `status` que lorsqu'ils sont vides : une clé Responder peut donc probablement créer un incident Public (déduit) |

| Les serveurs d'essai se mettent en veille quand ils sont inactifs (#134) | Et ils sont **verrouillés** : ni SSH, ni console, ni Admin tant que l'essai n'est pas converti |

## Ce qu'il faut construire, du moins cher au plus cher

### 1. Reconnaître un serveur Frappe Cloud v2

| Signal | Où | Lu par |
|---|---|---|
| `[central] enabled = true` | `~/pilot/benches/common_config.toml` | L'agent à la découverte (root) |
| `fc_team` | `sites/common_site_config.json` | Idem |
| `[telemetry] endpoint` est défini | `common_config.toml` | Idem. Ne jamais lire `token` |

Rapporter `platform: frappe-cloud-v2` et l'identifiant de l'équipe dans l'enregistrement et dans l'inventaire. Ne pas utiliser `pilot_endpoint` : un Pilot auto-hébergé l'écrit aussi.

### 2. Rester silencieux sur ce que fait la plateforme

- Ne pas lever « agent silencieux » pour un serveur qui peut se mettre en veille. Le cas est étroit : un serveur payant est créé sans mise en veille sur inactivité, et un serveur d'essai est verrouillé, donc il n'a pas d'agent. Étiqueter un serveur en veille ; ne pas appeler l'astreinte pour lui.
- Une connexion root depuis `172.16.0.x` ou sur `ttyS0` est la console web, lancée depuis Central par un membre de l'équipe. La montrer comme telle ; elle mérite toujours d'être montrée.
- Le HTTP sortant vers `internal-telemetry-svc.<region domain>` et le HTTPS vers Central, c'est Pilot. Ce n'est pas de l'exfiltration.
- Les requêtes qui arrivent du réseau du proxy portent le client dans `X-Forwarded-For` ; celles d'un domaine personnalisé arrivent avec un en-tête PROXY protocol. Attribuer d'après ceux-ci, et seulement quand le pair est dans `fdaa:<region>::/64`.
- Pilot qui redémarre le bench après 900 secondes d'inactivité, ou qui se redémarre lui-même à 00:00 UTC, n'est pas un crash.

### 3. Les signaux que cette lecture ajoute

| Signal | Pourquoi | Source |
|---|---|---|
| Un processus autre que Pilot lit `169.254.169.254` | La réponse contient le `X-Pilot-Token` du serveur. Du code qui aurait pris la main sur un site le voudrait | Les connexions sortantes ; l'agent ne doit jamais faire cette requête lui-même |
| `[telemetry] token`, les clés `[s3]`, le mot de passe SMTP et `ai_keys` sont dans des fichiers que l'utilisateur du bench lit | Ils ont leur place dans la liste des secrets que le nettoyage (scrubbing) n'envoie jamais et que l'intégrité des fichiers surveille | `common_config.toml`, `bench.toml`, `common_site_config.json` |
| Une nouvelle clé SSH ne laisse aucun changement de fichier | Sur ces serveurs, les clés viennent des métadonnées à chaque connexion. Surveiller `authorized_keys` ne voit que les clés ajoutées dans l'Admin de Pilot ; `auth.log` reste le signal | `auth.log` |
| Les sessions et les connexions Admin | Pilot les conserve, avec l'adresse, dans `logs/audit_<year>_<week>.jsonl`. Un accès Admin est un accès shell en tant qu'utilisateur du bench | Un nouveau lecteur dans l'agent |
| Le mot de passe Administrator d'un serveur neuf | Probablement partagé par tous les serveurs d'une même image jusqu'à son changement (à vérifier). La règle prédéfinie *Admin login from new IP* compte le plus dans la première heure d'un serveur | Règle existante |
| La mise à jour automatique de Pilot | Elle remplace l'arborescence de Pilot depuis une version GitHub sans signature. Un changement des fichiers de Pilot en dehors de 00:00 UTC mérite une ligne | L'intégrité des fichiers |

### 4. Recevoir les événements de Pilot sans Frappe Cloud

Pilot publie chaque événement du bench (`site_down`, `task_failed`, `backups_failing`, `resource_limit_breached`…) vers chaque entrée `[[webhook_endpoints]]`, signé en HMAC-SHA256 (`X-Pilot-Signature-256`). Cela fonctionne aussi sur un Pilot auto-hébergé. Un point d'entrée Wolf qui les accepte donnerait les déploiements et les échecs de sauvegarde sans que l'utilitaire root `wolf-pilot-export` lise les dossiers de tâches. C'est le nouveau pont le moins cher, et il ne demande rien à Frappe.

### 5. Enregistrer un site sans secret partagé

Le jeton d'identité d'équipe rend concret le prototype de #134 :

1. La Wolf App sur le site d'un client appelle son propre Pilot avec `pilot_auth_token`, et demande un jeton dont l'audience est l'adresse du site Wolf hébergé.
2. Central renvoie un jeton de 5 minutes signé avec sa clé Pilot : `sub` est l'équipe, `hosts` les adresses des sites du serveur.
3. Le site Wolf hébergé le vérifie avec `central.api.jwks.get_jwks` : la signature, `aud` égal à sa propre adresse, `scope=team-identity`, `exp`, et que l'hôte de l'appelant est dans `hosts`.

Cela prouve « ce site appartient à l'équipe T sur Frappe Cloud » sans aucun secret saisi par une personne. Il faut le `pilot_auth_token` du site : cela tourne donc dans la Wolf App, pas dans l'agent.

### 6. Montrer les incidents de la plateforme comme contexte

`GET /api/method/beacon.api.status.get_status` sur le domaine de la page de statut est ouvert et mis en cache 60 secondes. L'interroger régulièrement permet à un incident Wolf de dire « la plateforme signale un incident sur cette région depuis 01:52 ». Cela n'ouvre aucun incident Wolf. C'est le seul signal de Beacon qu'un client peut lire.

### 7. Un canal Beacon

Comme prévu dans #135, pour un Dokos qui aurait son propre Beacon, ce qui n'est pas le cas aujourd'hui : Beacon a besoin d'un Datum, d'un ClickHouse et d'un Atlas par région. Le garder derrière les deux mises en garde ci-dessus (ne jamais appeler l'astreinte en dessous de critical ; ne jamais définir `visibility`).

### Bloqué, et pourquoi

| Idée | Bloquée par |
|---|---|
| Écrire les constats de Wolf dans Datum | Datum accepte trois émetteurs, et un client n'en détient aucun. Le dépôt n'a pas de licence |
| Lire Datum | Les mots de passe ClickHouse sont ceux du personnel de Frappe, et un lecteur voit toute la région |
| Lire les événements d'un serveur (redimensionnement, redémarrage, instantané) depuis Central | Ni jeton client ni webhook sortant. `Activity Event` n'existe que dans la console |
| Signaler une alerte Wolf à Central | `report_pilot_event` appartient à l'identifiant de Pilot et accepte des types d'événement fixes. Utiliser le jeton de Pilot depuis Wolf serait une usurpation d'identité |
| Installer l'agent à la création du serveur | `user_data` est stocké en clair sur la `Resource Action` : aucun jeton d'enregistrement ne peut y aller, sauf s'il est de courte durée et à usage unique |

Les demandes à Frappe restent celles de [#114](https://github.com/bthuner/dodock-wolf/issues/114) et de #134 : un jeton d'équipe en lecture seule ou un webhook sortant des événements d'activité ; un moyen pour une application de transmettre une alerte.

## Ce qu'un client doit savoir sur la plateforme

Lu dans le code, non signalé à Frappe, et non vérifié sur une région en fonctionnement. Ce sont des propriétés d'une plateforme jeune, utiles quand Dokos écrit son propre registre des risques pour un locataire sur Frappe Cloud v2.

- **Les noms des sites et la sortie des mises à jour atteignent la télémétrie de la plateforme**, où le lecteur de Beacon et Insights voient toute la région.
- **Le personnel de Frappe peut lire le disque d'un serveur** (instantané, mode de secours) et sa console série. C'est vrai de n'importe quel hôte ; ici, c'est explicite dans le code.
- **Le jeton Datum de 7 jours d'un serveur supprimé reste valide** jusqu'à son expiration. Il ne fait qu'écrire.
- **La mise à jour automatique de Pilot n'est pas signée.** Quiconque peut publier une version de `frappe/pilot` exécute du code en tant qu'utilisateur du bench sur chaque serveur à 00:00 UTC.
- **Le marketplace fusionne tout seul une nouvelle application** quand le contrôle automatisé passe. N'importe quel bench peut installer tout ce qui s'y trouve.
- **Un seul jeu de clés sert deux plans** chez Central, et Pilot ne vérifie pas l'émetteur d'un jeton. La sécurité repose sur les audiences.
- **Beacon détient une clé System Manager sur l'Atlas de chaque région** pour lire une seule liste (déduit).
- **Aucune rotation de clés** n'est implémentée pour les clés de signature, et plusieurs jetons de la plateforme durent 365 jours.
- **Le client SSH de Cargo ne vérifie pas les clés d'hôte** ; il s'en remet au réseau privé.

## À vérifier sur un vrai serveur

Dokos déplace ses clients hébergés vers son propre locataire Frappe Cloud v2. Le premier serveur là-bas doit répondre à ceci :

- [ ] Les chemins : `/home/frappe/pilot/benches/default-bench`, `logs/` ou `logs/workload/` (le bench est-il en bac à sable sur Ubuntu 26.04 ?), le format du journal nginx et ce que contient `$pilot_client_addr` pour un nom de la région et pour un domaine personnalisé.
- [ ] Le mode lite : quels fichiers de journaux existent, et où les échecs du planificateur (scheduler) sont écrits.
- [ ] `wolf-agent discover` en root : le bench, les sites (nom du dossier face au nom public), les domaines.
- [ ] Les marqueurs : `[central]`, `[telemetry]`, `fc_team`, et qu'aucun fichier ne contient le `X-Pilot-Token`.
- [ ] `auth.log` pour une clé venant de la console, une session de console web (SSH et série), et le « ouvrir le bench » de Central.
- [ ] Le HTTPS sortant vers le site Wolf avec le pare-feu désactivé, puis activé. Le réseau privé entre deux serveurs de l'équipe.
- [ ] Si un serveur payant se met jamais en veille, et ce que fait la file locale (spool) de l'agent pendant un gel.
- [ ] Si les mots de passe Admin et Administrator diffèrent entre deux serveurs d'une même image.
- [ ] Un instantané pendant que l'agent suit les journaux.
- [ ] `[[webhook_endpoints]]` vers un récepteur de test : les événements et leurs corps.
- [ ] Le jeton d'identité d'équipe, depuis un site, pour une audience de test.
- [ ] Le `get_status` de la page de statut : sa forme, et si l'on peut y distinguer une région.
