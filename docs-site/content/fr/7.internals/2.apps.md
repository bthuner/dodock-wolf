## Central

Une application Frappe 16 et une console Vue (`/dashboard`) sur **un site global unique**. Elle possède l'identité, les équipes, les capacités, le catalogue, la facturation, la liste des régions et les services gérés. Elle n'atteint une région que par `central/integrations/`.

**Stocke.**

| Objet | DocTypes |
|---|---|
| Équipes et droits | `Team` (avec un `tenant_id` immuable sur 32 bits ; 0 est réservé à la plateforme), `Team Member`, `Team Role`, `Capability` (18, sur deux plans : `central` et `atlas`) |
| Régions | `Region` : l'adresse d'Atlas, le domaine du proxy, un secret de webhook pour Atlas et un pour Cargo, la source de données de télémétrie |
| Clés | `Central SSO Settings` : trois clés de signature (voir [Appels et confiance](/fr/internals/interop#clés)) |
| Serveurs | `Virtual Machine` (l'enregistrement d'un serveur côté Central), `Resource Action` (une ligne par création, démarrage, arrêt, redimensionnement, suppression), `Pilot Credential`, `VM Snapshot`, `Team SSH Key`, `Firewall Ruleset`, `WireGuard Device` |
| Sites et routes | `Site` (seulement le site intégré à une image d'essai), `Site Domain` (une route du proxy par nom d'hôte) |
| Facturation | Environ 55 DocTypes : `Plan`, `Subscription`, `Invoice`, `Usage Day`, `Usage Rollup`, `Credit Wallet`… |
| Fil d'activité | `Activity Event` (conservé 365 jours), `Team Notification`, 49 `Notification Event Type` |

Il n'y a **ni DocType Bench ni enregistrement de déploiement**. Ce que fait tourner un serveur est l'affaire de Pilot.

**Accepte.**

| De | Entrée | Authentifié par |
|---|---|---|
| Une personne | La console et `central.api.{servers,sites,snapshots,teams,ssh_keys,wireguard,firewall_rulesets,activity,…}` | Une session Frappe, puis une capacité |
| Pilot | `central.api.pilot.*`, `central.notification.api.report_pilot_event`, environ 28 `central.billing.api.billing_api.*`, `central.api.email_oauth.*`, `central.api.integrations.github.*` | En-tête `X-Pilot-Token` : 48 caractères hexadécimaux ; Central n'en stocke que le SHA-256. L'équipe et le serveur viennent toujours de l'identifiant, jamais de la requête |
| Atlas et Cargo | `central.api.state_delivery.receive` | `X-FC-Source`, `X-FC-Region`, `X-Frappe-Webhook-Signature` (HMAC-SHA256 avec un secret par région et par émetteur) |
| N'importe qui | `central.api.jwks.get_jwks` | Rien : des clés publiques |
| Un service facturé à l'usage | `central.billing.api.metering.report` | `X-Central-Service`, `X-Central-Signature` (HMAC) |
| Grove | `central.api.grove.datum_token` | `X-Grove-Token` |
| Les passerelles de paiement, GitHub | Leurs webhooks | Leurs propres signatures |

**Appelle.** Atlas, le proxy, la passerelle WireGuard et Cargo de chaque région ; Pilot sur chaque serveur, à travers le proxy ; Datum d'une région, pour ses propres erreurs et jauges ; Grove ; Stripe, Razorpay, PayPal ; GitHub ; un site Helpdesk pour les tickets de support. Central n'est sur le réseau privé d'aucune région et n'ouvre jamais de session SSH vers un serveur.

**À un client, elle donne** la console : les serveurs (créer, démarrer, arrêter, redémarrer, redimensionner, renommer, supprimer, mode de secours), les jeux de règles de pare-feu, les adresses publiques, les appareils WireGuard, les clés SSH, une console web, les instantanés, « ouvrir le bench » et « se connecter au site en tant qu'Administrator », les buckets, les clés IA, la facturation, les rôles d'équipe. Elle ne donne aucune page de jetons d'API et n'envoie aucun webhook à un client. Une clé d'API Frappe ordinaire d'un membre d'équipe fonctionne bien sur `central.api.*` (`suite_cloud` s'appuie dessus), mais rien dans la console n'en délivre.

## Atlas

Le gestionnaire de machines virtuelles d'**une région avec un fournisseur** (AWS, Scaleway ou du matériel générique). Un monodépôt :

| Partie | Quoi | Tourne |
|---|---|---|
| L'application Atlas | Site Frappe 16, API REST sous `/api/atlas` | Un site par région, lui-même dans une machine virtuelle sur un hôte |
| `metald` | Démon Go : Firecracker, ZFS, espaces de noms réseau, eBPF | Sur chaque hôte physique |
| `atlas-guest-agent` | Binaire Go statique | **Dans chaque image de machine virtuelle** |
| Le proxy | OpenResty et un démon de contrôle | 1 à 5 machines de service |
| Réseau privé WireGuard, routeur IPv6, passerelle WireGuard | Programmes eBPF et Python | Hôtes et machines de service |

**Stocke.** `Virtual Machine`, `Virtual Machine State`, `Virtual Machine Image`, `Metal Server`, `Public IP Pool`, `Proxy Server`, `Cargo Server`, `SSH Task`, `Investigation` et `Atlas Settings` (l'identifiant de la région, le domaine et le certificat génériques, la clé de signature de la région, les clés de Central). Sur chaque hôte, `metald` conserve le `config.json` de la machine, son `status.json` et 7 jours d'échantillons à 10 secondes.

**Accepte.** `Authorization: Bearer`, un jeton Ed25519 avec l'audience `atlas-admin:<region>`, la portée `*`, une revendication `tenant` (`*` pour Central, un nombre sinon) et l'en-tête `X-Tenant-ID`. Routes : `virtual-machines` et leurs actions (`start`, `stop`, `pause`, `resume`, `restart`, `resize`, `snapshot`, mode de secours, `console-token`), `…/metrics`, `images`, `public-ips`, `webhooks`, `beacon/resources`, `hosts/<id>/access`, `dns-records`, `investigations`, et le `jwks.json` public. Un locataire ne détient jamais de jeton Atlas : Central appelle pour lui. L'enregistrement d'un autre locataire répond 404.

**Appelle.** `metald` sur chaque hôte (TLS mutuel, port 9000, toutes les 10 secondes) ; Central (le webhook d'état, et les clés de Central toutes les 5 minutes) ; Cargo (un bucket pour ses propres images) ; Datum ; les hôtes et les machines de service en SSH ; Route 53 ; ACME ; les contrôleurs de gestion du matériel.

**Aussi dans Atlas.** Un bastion Warpgate pour l'accès du personnel de Frappe aux hôtes (connexion par Central, autorisations de 24 heures au plus) ; un « investigateur » LLM avec du SQL en lecture seule sur Datum et du SSH vers les hôtes, sans accès aux machines des clients ; des machines « dormeuses » qui sont gelées quand aucune requête n'arrive ; le mode de secours ; la migration à chaud.

## Cargo

Un site Frappe par région, sur une machine de la plateforme (locataire 0) qui est elle-même un bench Pilot. Trois modules :

- **Image Builder.** Il construit les images Pilot (Base, Site, Apps) et les images de services one-click. Une construction est une machine virtuelle qu'il loue à Atlas, provisionne en SSH, arrête, puis dont il prend un instantané. Les **étiquettes de l'instantané sont le passage de relais** : `purpose=pilot`, `pilot_version`, `frappe_version`, `has_site`, `app`. Central trouve les images Pilot par étiquette dans Atlas ; Cargo n'en parle jamais à Central.
- **Object Storage.** Il fait tourner la grappe Garage (S3) de la région et crée les buckets et les clés quand Central le demande. Un bench parle ensuite S3 directement à `https://s3-svc.<region domain>`.
- **Telemetry.** Il installe et fait tourner l'**hôte Datum et ClickHouse** de la région, et publie le jeu de clés auquel Datum fait confiance.

**Accepte.** En-tête `X-Cargo-Access-Token` : un jeton Ed25519 avec l'audience `atlas-cargo:<region>`, signé par Central ou par l'Atlas de la région. Méthodes : `cargo.api.webhooks.configure`, `cargo.object_storage.api.bucket.*`, deux méthodes `one_click_image`. Publique : `cargo.api.jwks.get_jwks`. Pour ses propres machines : `cargo.api.telemetry.datum_token` avec `X-Cargo-Machine-Token`.

**Appelle.** Atlas, en tant que locataire 0, avec un jeton qu'Atlas lui a donné à l'installation (portée `*`, 365 jours) ; Central, avec un seul webhook qui dit si `storage` et `telemetry` sont disponibles et à quelle adresse ; Datum ; ses propres machines en SSH ; GitHub pour les versions de Pilot et les têtes de branche de Frappe.

Un locataire ne parle jamais à Cargo.

## Pilot

« Frappe Server Manager », le successeur de `bench` : une CLI Python, une API Admin Flask (environ 300 routes) et une interface Admin Vue. Il tourne dans chaque serveur sous un seul utilisateur sans privilèges (`frappe`), dans `~/pilot`. Il n'a pas de base de données propre : `bench.toml` par bench, `common_config.toml` par hôte, des dossiers de tâches, des journaux JSON.

C'est une seule base de code pour deux cas. L'interrupteur est **`[central] enabled`** dans `common_config.toml`.

| Comportement | Auto-hébergé | Frappe Cloud v2 |
|---|---|---|
| Benches, sites, applications, interface Admin, tâches, bac à sable, nginx, certificats, sauvegardes vers S3, métriques locales, pings de disponibilité, webhooks, alertes par e-mail, le registre du marketplace, mise à jour automatique de Pilot | Oui | Oui |
| Télémétrie vers Datum | Seulement avec `[telemetry] endpoint` et `token` définis à la main | Jeton récupéré auprès de Central et renouvelé |
| Alertes vers Central, le verrou d'essai, dépôts GitHub privés par Central, facturation dans les Cloud Settings du site | Non | Oui |
| Central se connecte à l'Admin | Seulement avec `[admin] jwks_url` défini à la main | Défini au premier démarrage |
| Routage d'un nouveau domaine | Une vérification DNS et un certificat local | Un programme de l'image de Cargo demande à Central |

**Accepte.** L'API Admin avec un cookie de session (le mot de passe Admin du bench, TOTP facultatif), un jeton de 5 minutes signé par Central (vérifié avec les clés de Central et l'audience du bench ; portée `bench`), ou le jeton du site lui-même (`pilot_auth_token`, HS256, 365 jours, portée `site`). Et le service de métadonnées de la machine, par lequel arrivent l'identifiant de Central et les premiers réglages.

**Appelle.** Central (`X-Pilot-Token`) ; Datum ; `github.com/frappe/marketplace` (git, au plus une fois par heure) ; les versions de `github.com/frappe/pilot` pour sa propre mise à jour (00:00 UTC, activée par défaut, sans somme de contrôle ni signature au-delà de TLS) ; le bucket S3 ; Let's Encrypt ; tout `[[webhook_endpoints]]` que l'opérateur ajoute.

Le détail de ce qui est sur le serveur et de ce qui le quitte : [Dans un serveur client](/fr/internals/customer-server).

## Datum

Un processus FastAPI par région (deux workers sur `127.0.0.1:8000`, derrière Caddy), sur un hôte que Cargo installe, à côté de ClickHouse. **Il ne fait qu'écrire.** Il n'y a aucune route de lecture.

| Route | Corps |
|---|---|
| `POST /v1/ingest` | Échantillons JSON `{metric, value, ts, labels}` |
| `POST /v1/ingest/remote` | Prometheus remote write v1 |
| `POST /v1/logs/ingest` | Lignes de journal |
| `POST /v1/traces` | OTLP sur HTTP (aucune application de ces dépôts n'envoie de traces) |
| `GET /health` | Ouverte |

**Authentification.** Un jeton Ed25519 avec l'audience `atlas-datum:<region>`, un `resource_id` (apposé sur chaque ligne) et `access` contenant `write`. Trois émetteurs sont acceptés, distingués par le préfixe de l'identifiant de clé : `central:`, `atlas:<region>:`, `cargo:<region>:`. Limites : 12 requêtes par 60 secondes par ressource et par route, dans chaque worker ; 10 000 échantillons, lignes ou spans par requête. Ni file d'attente ni nouvelle tentative du côté de Datum.

**Tables** (base de données `datum`) : `samples` (15 jours pour `system_*`, 90 jours sinon), `samples_recent` (2 jours), `samples_5m` (90 jours), `logs` (30 jours), `traces` (7 jours), et des statistiques de volume quotidiennes.

**Trois adresses**, toutes servies par Caddy sur l'hôte Datum :

| Adresse | Mène à | Utilisée par |
|---|---|---|
| `https://telemetry-svc.<region domain>` | Datum | Les émetteurs hors du réseau privé (Central) |
| `http://internal-telemetry-svc.<region domain>` | Datum, en HTTP simple sur le réseau privé | Pilot sur les serveurs clients, les machines de Cargo. C'est l'adresse que Cargo rapporte à Central |
| `https://telemetry-read-svc.<region domain>` | L'interface HTTP de ClickHouse | Beacon (utilisateur `beacon`), Insights (utilisateur `insights`) |

**L'« agent Datum »** est Vector 0.59.0 avec une configuration fixe, installé en root par Atlas ou Cargo sur les **hôtes, les machines de service et les machines de Cargo** : les métriques de l'hôte, le journal systemd à partir du niveau warning, le `error.log` de nginx. Il n'est pas installé sur les serveurs clients.

Le dépôt n'a **aucun fichier de licence**. Trois consommateurs (l'Admin de Pilot, Cargo, Atlas) importent son paquet `datum_client` depuis la branche `main`.

## Beacon

Une application Frappe 16 sur **un site global unique**, hors des régions qu'elle surveille. Sa page d'accueil est la page de statut. **Elle ne fait que tirer** : elle n'a ni agent ni API d'ingestion.

**Entrées.**

| Entrée | Comment |
|---|---|
| Règles, niveaux de service, graphiques | Des fichiers dans le dépôt de chaque producteur (`beacon/rules/*.sql`, `*.http`, `*.tls`, `beacon/services/*.sql`, `beacon/charts/*.sql`), lus par l'API de GitHub à la tête d'une branche, **seulement quand un administrateur appuie sur Sync Definitions**. Chaque nouvelle requête est exécutée une fois avant que quoi que ce soit ne soit enregistré |
| Télémétrie | Du SQL sur le ClickHouse de chaque région, en tant qu'utilisateur `beacon` (lecture seule, 20 secondes, 100 000 lignes, `SELECT` sur `datum.*`). Aucune politique de ligne n'existe : `beacon` lit les lignes de tous les locataires de la région |
| L'arbre des ressources | `GET /api/atlas/beacon/resources` sur l'Atlas de chaque région, chaque minute : Atlas, les hôtes, chaque machine virtuelle (celles des clients comprises, avec son hôte pour parent), les machines de service, Cargo |
| Contrôles HTTP et TLS | Faits depuis le site Beacon, chaque minute, sur les adresses de la plateforme seulement |

**Ce que déclarent les producteurs.**

| Producteur | Règles | Niveaux de service | Ce qu'ils surveillent |
|---|---|---|---|
| Atlas | 36 | 5 (`servers`, `proxy`, trois services réseau ; 99,9 %) | Les hôtes, `metald`, le proxy, le réseau privé, les certificats |
| Cargo | 21 | 1 (`object-storage`, 99,9 %) | Les constructions d'images, Garage, et Datum lui-même |
| Central | 10 | 3 (`dashboard-api` 99,9 %, `server-actions` 99 %, `billing` déclaré) | Les erreurs d'API, les paiements, les actions bloquées |
| Pilot | 5 | 1 (`sites` 99,9 %, masqué sur la page de statut) | Les seules règles qui lisent les données des serveurs clients |

**De l'alerte à la personne.** Règle → Alerte (Pending, Firing, Resolved) → Incident, regroupé selon l'arbre des ressources. Chaque incident est publié sur un webhook de messagerie instantanée. Les incidents High et Critical envoient aussi un e-mail et appellent les intervenants par Twilio, l'un après l'autre (le suivant après 2 minutes pour Critical, 5 pour High ; un nouveau tour toutes les 15 minutes). Répondre à l'appel acquitte. Les niveaux de service lèvent des alertes de consommation (burn) sur deux fenêtres (14,4× sur 1 heure et 5 minutes ; 6× sur 6 heures et 30 minutes ; 1× sur 3 jours et 6 heures, qui n'appelle jamais l'astreinte).

**À un client, elle donne** la page de statut publique, un flux RSS par incident et un abonnement par e-mail. Rien d'autre : ni compte, ni API.

## Autour des six

| Dépôt | Quoi | Lien avec les six |
|---|---|---|
| `cloudtoolkit` (AGPL-3.0) | Des pipelines durables et un client SSH, tirés du moteur de workflows de Press | Seul Cargo en dépend |
| `marketplace` | Le registre de 132 applications installables, un JSON par application | Pilot le clone pour `get-app` ; Cargo lit la copie de Pilot pour choisir les applications d'une image d'inscription. Une nouvelle application qui passe le contrôle automatisé est fusionnée toute seule |
| `one-click-templates` | Redis, MariaDB, Prometheus et Grafana en serveurs prêts à l'emploi | Cargo construit chacun en image Atlas ; Central écrit les réponses du client dans `/etc/one-click/inputs.env` par cloud-init. Ces serveurs n'ont pas de Pilot |
| `grove`, `pathway` (MIT) | Une plateforme d'inférence IA : un plan de contrôle Frappe et une passerelle Go | Central crée les équipes et les clés dans Grove, lit l'usage chaque heure pour le facturer, et signe des jetons Datum pour les machines de Grove. Les machines de Grove viennent d'AWS et de RunPod, pas d'Atlas |
| `suite_cloud` (AGPL-3.0) | Serveurs de messagerie de Frappe Suite | Un client de Central comme un autre : il crée des serveurs avec la clé d'API d'un membre d'équipe et pilote Pilot. Ses grappes de messagerie sont hors de Frappe Cloud v2 |
