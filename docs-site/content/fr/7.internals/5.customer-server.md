Un serveur client est une machine virtuelle Firecracker qui démarre une image construite par Cargo, avec un accès SSH root pour le client. Cette page décrit ce à quoi doit s'attendre un outil qui tourne sur ce serveur. Rien de tout cela n'a encore été vérifié sur un serveur en fonctionnement : la liste de ce qu'il faut vérifier est dans [Notes pour Wolf](/fr/internals/wolf#à-vérifier-sur-un-vrai-serveur).

## Ce qui s'y trouve

### Venant d'Atlas, dans chaque image

| Quoi | Détail |
|---|---|
| `atlas-guest-agent` | `/usr/local/lib/atlas/atlas-guest-agent`. Quatre unités socket, `atlas-guest-agent-{usage,freeze,grow,reboot}.socket`, sur les ports vsock 100000 à 100003 : l'hôte demande l'usage, gèle les systèmes de fichiers avant un instantané, agrandit le disque, redémarre. Un pare-feu dans la machine ne peut pas bloquer vsock |
| `atlas-metadata.service` | Interroge le service de métadonnées (`169.254.169.254`) toutes les 250 ms : nom d'hôte, adresse privée, MTU, routes. Avance l'horloge après un gel de la machine |
| Clés SSH depuis les métadonnées | `/etc/ssh/sshd_config.d/90-atlas-mmds.conf` : sshd lance `atlas-guest-agent authorized-keys` à chaque connexion. Une clé ajoutée dans la console ne modifie aucun fichier sur le serveur |
| cloud-init | `/etc/cloud/cloud.cfg.d/99-atlas-datasource.cfg`, source de données `Atlas` ; une console série sur `ttyS0` |
| Réseau | `eth0`, une IPv6 privée `fdaa:<region>:<tenant>::<machine>`, MTU 1380, IPv4 vers Internet par le NAT de l'hôte |

### Venant de l'image Pilot de Cargo

| Quoi | Détail |
|---|---|
| Utilisateur | `frappe`, uid 1000. Tous les autres utilisateurs ordinaires de l'image Ubuntu sont supprimés |
| Pilot | `/home/frappe/pilot`, à une version fixe |
| Bench | `/home/frappe/pilot/benches/default-bench`, sur MariaDB (`~/pilot/databases/mariadb/run/mysqld.sock`), `restart_idle_seconds = 900` |
| Site | `site.local` sur les images Site et Apps. Il est atteint par l'alias `*.<region domain>` : **le nom du dossier du site n'est pas son nom public** |
| Admin | Domaine `admin.local`, atteint sous `admin-vm-<label>.<region domain>` |
| nginx | Activé, sans TLS pour les noms de la région |
| Le programme de domaines | `/usr/bin/bench-domain-provider` |
| Unités | `pilot-vm-memory.service` (zswap, 1 Go de swap), `pilot-prewarm.service`, `pilot-grow-file-system@.service` |

Une image ne contient ni jeton, ni réglage de télémétrie, ni clé SSH, ni trace d'une équipe. Chaque construction génère un mot de passe Admin aléatoire et un mot de passe Administrator aléatoire dans la machine de construction. Le script de construction ne les renouvelle pas : ils sont donc probablement identiques sur tous les serveurs démarrés depuis une même image, jusqu'à ce que quelque chose les change (déduit, à vérifier).

### Venant de Pilot, comme sur tout hôte Pilot

- Des unités **utilisateur** systemd de `frappe` : `<bench>.target`, `<bench>-web` (avec son socket), `<bench>-socketio`, `<bench>-worker_pool…`, les deux Redis, `<bench>-admin`, `<bench>-central-bootstrap` ; et `pilot-monitor.service`, `pilot-mariadb.service`, `pilot-certificates.timer`. Le défaut est le « mode lite » : un seul processus pour le web, le temps réel et les tâches.
- `/etc/nginx/conf.d/00-pilot.conf`, `/etc/logrotate.d/pilot` (500 Mo, `copytruncate`), des règles sudo pour nginx et certbot.
- Des journaux dans `<bench>/logs/`, et les journaux de Frappe lui-même dans `<bench>/logs/workload/` sur un bench en bac à sable. Les unités écrivent dans des fichiers à cet endroit, pas dans le journal systemd.
- `<bench>/logs/nginx-access.log`, dans le format propre à Pilot : `$pilot_client_addr [$time_local] "$request_method $uri" $status "$host" $request_time`. Seul le `location /` des sites est journalisé : ni `/assets`, ni `/files`, ni `/socket.io`.
- Des signaux locaux : `logs/uptime.json.log`, `logs/audit_<year>_<week>.jsonl` (les sessions et les connexions Admin, avec l'adresse), `tasks/<id>/`, `~/pilot/system/logs/system-stats.log`, `updates_<year>_<week>.jsonl`, `central-requests_<year>_<week>.jsonl`.
- Ni pare-feu d'hôte ni fail2ban. Le `[firewall]` de Pilot est une liste d'autorisation et de refus dans nginx.

La prise en charge de Pilot par Wolf lit déjà cette disposition : voir [Benches Pilot](/fr/install/pilot).

### Venant de Central, au premier démarrage

Par les attributs de métadonnées ([le tableau](/fr/internals/interop#les-secrets-en-route-vers-une-machine)) :

| Marqueur | Fichier |
|---|---|
| `[central] enabled = true`, `bootstrapped = true`, `[[central.hostname_aliases]]` | `~/pilot/benches/common_config.toml` |
| `[telemetry] endpoint`, `token` | Même fichier. Le jeton est un jeton d'écriture Datum de 7 jours, en clair |
| `[admin] jwks_url`, `jwks_audience` | Même fichier |
| `fc_team` (l'identifiant de l'équipe), les réglages SMTP d'une boîte aux lettres mutualisée, `ai_keys` pour un essai | `sites/common_site_config.json` |
| Les clés `[s3]` du bucket de sauvegarde, quand l'offre inclut du stockage | `bench.toml` |
| `pilot_endpoint`, `pilot_auth_token`, `cloud_server_url` | Chaque `site_config.json` |

`pilot_endpoint` n'est **pas** un signe de Frappe Cloud v2 : un Pilot auto-hébergé en production l'écrit aussi. `[central] enabled` et `fc_team` en sont.

::caution
`http://169.254.169.254/latest/meta-data/attributes/pilot-central` renvoie le `X-Pilot-Token` du serveur à tout processus hors du bac à sable du bench. Avec lui, un processus peut demander à Central les moyens de paiement de l'équipe, un jeton Datum ou un jeton de dépôt GitHub. Un outil sur le serveur ne doit jamais le lire. Un processus qui le fait est un signal qui mérite une alerte.
::

## Ce qui quitte le serveur

Tout ce que Pilot envoie à Datum, d'après `pilot/core/server/monitoring_datum.py` :

| Signal | Toutes les | Étiquettes |
|---|---|---|
| `pilot_sites` | 60 s | `state` : `up`, `down`, `app_error`, `maintenance` |
| `pilot_info` (le signal de vie) | 5 min | `version` |
| `pilot_database_up` | 5 min | — |
| `system_filesystem_size_bytes`, `system_filesystem_available_bytes` | 5 min | `mountpoint`, `device`, `type` |
| `pilot_central_requests_last_5_minutes` | 5 min | `method`, `result` |
| `pilot_site_backups` | 5 min | `status` |
| `pilot_site_backup_failed` | 5 min | **`site` : le nom du site** |
| Les événements de mise à jour, en lignes de journal | 5 min | `app`, `repository`, les versions, `status`, `phase`, **`site`**, et jusqu'aux 8 192 derniers caractères de la sortie d'une tâche en échec |

Et vers Central : les types d'événement de [Un client est prévenu](/fr/internals/flows#un-client-est-prévenu), avec un message.

**Ce qui reste sur le serveur** : les métriques de CPU, de mémoire, de charge, de réseau et de MariaDB (Pilot les collecte toutes les 10 secondes, dans des fichiers locaux uniquement) ; le journal systemd ; les journaux d'accès et d'erreurs de nginx ; tous les journaux du bench ; les échecs du planificateur (scheduler) et des workers ; `auth.log` ; l'Error Log, l'Activity Log et l'Access Log de Frappe.

Le contrat de télémétrie de Beacon dit « la machine virtuelle d'un locataire n'envoie aucune métrique machine » et « un site n'est jamais une valeur d'étiquette ». La première affirmation tient. La seconde non : une sauvegarde en échec envoie le nom du site, et une mise à jour en échec envoie le site et sa sortie.

## Ce que la plateforme voit de l'extérieur

Sans rien dans le bench de la machine, par l'hôte et l'agent invité :

- le temps CPU, la mémoire (depuis le périphérique balloon), la taille, l'usage et les E/S du disque, les octets et les paquets réseau à l'interface de la machine, avec des compteurs des ICMP, UDP, TCP SYN et TCP RST envoyés ;
- la charge moyenne, `/proc/meminfo`, l'usage du système de fichiers racine et `systemctl is-system-running`, depuis l'agent invité ;
- si la machine répond à un ping, chaque minute ;
- la sortie de la console série (128 Kio conservés, même si personne ne regarde) ;
- au proxy : le nombre et la durée des requêtes pour les noms de la région, de façon agrégée.

Le personnel de Frappe qui a accès à un hôte peut prendre un instantané du disque ou le monter en mode de secours. La plateforme ne voit pas à l'intérieur du TLS d'un domaine personnalisé, et ne lit ni journal ni liste de processus de la machine.

## Comment un serveur se comporte

| Comportement | Conséquence pour un outil sur le serveur |
|---|---|
| **Veille.** Un serveur d'essai (et celui d'une équipe de préproduction) est gelé quand aucune requête n'arrive pendant un moment, et se réveille sur du trafic. Les connexions sortantes ne le maintiennent pas éveillé. Les serveurs payants sont créés avec `sleep_after_idle_seconds: 0` | Un minuteur s'arrête et reprend avec un saut de l'horloge. Le silence n'est pas une panne |
| **Verrou d'essai.** Tant qu'un essai gratuit est ouvert : ni SSH, ni console web, ni Admin de Pilot | Rien ne peut être installé |
| **Démarrage à chaud.** Les images Base et Apps reprennent depuis un instantané mémoire | L'identifiant de démarrage, l'identifiant de machine et les heures de début des processus peuvent être partagés entre les serveurs d'une même image (déduit). Le journal systemd démarre presque vide |
| **Instantané.** Les systèmes de fichiers sont gelés jusqu'à 30 secondes | Un lecteur de journaux voit une pause dans les écritures |
| **Redémarrage sur inactivité.** En mode lite, le processus du bench redémarre après 900 secondes sans travail | Ce n'est pas un crash |
| **Pare-feu.** Désactivé par défaut, ce qui autorise tout dans les deux sens. Une fois activé, un sens sans règle bloque les nouvelles connexions | Le HTTPS sortant d'un agent a alors besoin d'une règle |
| **Connexions par la console.** La console web se connecte en root depuis une adresse côté hôte (`172.16.0.x`) avec une clé temporaire, ou sur `ttyS0` | Une connexion root inhabituelle que le client a lancée |
| **Mise à jour automatique.** Pilot se met à jour à 00:00 UTC et redémarre chaque Admin | Les chemins peuvent changer d'une version à l'autre |
| **Adresses dans les journaux.** Pour les noms de la région, nginx voit l'adresse privée du proxy ; le client est dans `X-Forwarded-For`. Pour un domaine personnalisé, il arrive dans l'en-tête PROXY protocol | Ne vous fiez à ceux-ci que depuis le réseau du proxy, `fdaa:<region>::/64` |
