Lancez les commandes en tant qu'utilisateur `wolf-agent`, propriétaire de la configuration :
`sudo -u wolf-agent wolf-agent <command>`.

Options globales : `--config PATH` (ou `$WOLF_AGENT_CONFIG`), `-v`.

| Commande | Rôle |
|---|---|
| `register --url URL --token TOKEN [--bench PATH]...` | Enregistre l'hôte, découvre les benches, écrit la configuration. |
| `run` | La boucle du démon. C'est ce que lance systemd. |
| `discover [--bench PATH]` | Affiche ce que trouve la découverte des benches. |
| `check [--from-start] [--status] [--bench PATH]` | Collecte une fois et affiche la charge utile JSON. Rien n'est envoyé. L'état du chien de garde part sur stderr. `--status` demande aussi au site son état de santé. |
| `doctor [--json] [--offline]` | Vérifie ce que l'hôte donne à l'agent et ce qu'il faut corriger : l'enregistrement et le site Wolf, chaque log, bench, Redis de file d'attente et log nginx, l'export Pilot, le log d'authentification ou le journal, les actions de réponse, le démon. Lecture seule. Sort avec le code 1 quand une vérification échoue. Voir [Vérifier un hôte](#vérifier-un-hôte). |
| `mark-deployment --bench NAME [--site S] [--note TEXT] [--silence 15m]` | Place un marqueur de déploiement sur la chronologie Wolf. `--silence` ouvre aussi une fenêtre de maintenance qui coupe les notifications pour ce bench ou ce site. |
| `test-fallback` | Envoie un message de test via les canaux de secours du [chien de garde](/fr/agent/watchdog). |

### Obsolètes

La prise en charge de Press v1 et les métriques de ressources de l'hôte ont été retirées en 0.2.
Leurs options restent acceptées, pour que les anciens scripts, unités et configurations continuent
de fonctionner : chacune écrit `removed in 0.2: ignored` sur stderr et ne fait rien.

| Option ou commande | Depuis la 0.2 |
|---|---|
| `--platform` sur `register`, `discover` et `check` | Ignorée : les benches sont découverts comme d'habitude. |
| `mark-deployment --source press` | Enregistré comme `manual`. |
| `refresh` | Ne fait rien et sort avec le code 0. |
| `collect_host_metrics` dans la configuration | Ignorée : l'agent ne mesure plus les ressources de l'hôte. `run` écrit l'avertissement dans son journal, `check` l'affiche sur stderr, `doctor` la liste, `register` retire la clé. |

Un hôte encore sous Press v1 reste en [v0.1.0](/fr/getting-started#rester-en-v010).

## Marquer un déploiement

```bash [deploy.sh]
sudo -u wolf-agent wolf-agent mark-deployment --bench frappe-bench --site erp.example.com \
  --note "ERPNext v15.42 + custom app 2.3" --silence 15m
```

Le marqueur est un événement `deployment`. Les règles avec **Exiger un déploiement récent** ne se
déclenchent qu'après un déploiement, et les incidents sont liés au dernier déploiement de leur
périmètre. Le texte passé avec `--note` est envoyé tel quel, sans [nettoyage](/fr/agent/scrubbing).

Les tâches Pilot, ainsi que `bench migrate` sur les sites qui exécutent la Wolf App, sont
marquées automatiquement.

## Vérifier un hôte

```bash [hôte]
sudo -u wolf-agent wolf-agent doctor
```

Lancez-la avec l'utilisateur de l'agent : root lit ce que le démon ne peut pas lire, et masquerait des problèmes. Chaque ligne vaut **ok**, **WARN**, **FAIL** ou `--` (pour information), avec la correction après un avertissement ou un échec :

```text
logs
  ok   18 log file(s) readable
  --   9 not written yet (read once they appear): bench-1/frappe.web.log ...

platform
 FAIL  Pilot wolf: cannot read /var/lib/wolf-pilot-export/wolf.json
        fix: systemctl restart wolf-pilot-export.service (it sets the wolf-agent group)
```

Elle vérifie les fichiers que le démon suivrait et les benches à partir desquels il travaille, pas seulement la configuration. `--json` affiche les vérifications sous forme de liste, `--offline` n'appelle pas le site Wolf. Rien n'est écrit, et le code de sortie vaut 1 quand une vérification échoue, ce qui permet d'en faire une étape d'un script d'installation.

Le démon lance les mêmes vérifications toutes les heures (`setup_checks`) et les envoie avec un push : la page **Supervision** de la Wolf UI affiche la configuration de chaque hôte, ses problèmes et leurs corrections, et la règle prédéfinie *Host setup problem* ouvre un incident tant qu'une vérification échoue.

## Voir la charge utile

```bash [hôte]
sudo -u wolf-agent wolf-agent check --from-start | jq '.events[] | {type, category, title}'
```

`--from-start` lit les journaux depuis le début au lieu des positions enregistrées, ce qui sert à
tester un parseur sur un fichier existant. `check` n'envoie jamais rien et ne déplace jamais les
positions.
