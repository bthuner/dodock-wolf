Wolf propose, un Wolf Manager approuve chaque action d'un second clic, et rien ne s'exécute tout
seul. Chaque approbation donne une ligne **Wolf Response Action** (qui, quand, quoi, résultat ; en
lecture seule pour tous) et un commentaire sur l'incident.

| Action | Proposée pour | Appliquée par |
|---|---|---|
| **Block IP for N hours** (de 1 à 168, 24 par défaut) | les adresses publiques des événements de sécurité de l'incident, de toute source (Wolf, Suricata, Wazuh), pour l'hôte attaqué | le Wolf Agent de cet hôte, à son prochain envoi, s'il y est autorisé (voir ci-dessous), et/ou la [réponse active de Wazuh](#réponse-active-de-wazuh) ; et [CrowdSec](#crowdsec) s'il est configuré |
| **Disable user**, **log out all sessions**, **revoke API keys** | les utilisateurs nommés par les propres événements de sécurité du site (connexions échouées, nouvelle IP ou nouveau pays, rôle attribué, clé d'API générée) | le site Wolf, immédiatement |

- Approuvez depuis le panneau **Response** de l'incident dans le Wolf UI, ou depuis le lien signé
  de l'alerte (jusqu'à 5 par alerte). Le lien ne fait qu'afficher la proposition : un invité est
  renvoyé vers la page de connexion, seul un Wolf Manager ou un System Manager connecté voit le
  bouton, et seul son POST agit. Un e-mail transféré ne peut pas agir à lui seul, et un lien rouvert
  indique que l'action a déjà été effectuée.
- Seul ce que Wolf a proposé à partir des propres événements de l'incident peut être approuvé :
  l'API refuse toute autre action, cible ou hôte.
- Administrator, Guest et le compte de l'approbateur lui-même sont refusés. Seul un System Manager
  peut agir sur un System Manager. Les actions sur les utilisateurs ne s'appliquent qu'au site Wolf.
- Les blocages passent à *Expired* une fois leur durée écoulée (vérification toutes les heures).

## Blocage sur les hôtes

L'agent ne fait rien tant que vous ne l'y autorisez pas sur cet hôte.

::caution
L'agent refuse les adresses privées, de boucle locale et réservées, ainsi que les durées de plus
d'une semaine, quoi que le site envoie. Il lance la commande sous forme de liste d'arguments, jamais
via un shell. Sans `response.enabled`, chaque action revient en *Failed* avec la raison : le manager
sait ainsi qu'elle n'a pas été appliquée.
::

### Mise en place

::note
Un agent installé avant ce correctif a `NoNewPrivileges=yes` dans `/etc/systemd/system/wolf-agent.service`, ce qui empêche `sudo` : aucun blocage n'a jamais été appliqué. Relancez `install.sh`, ou supprimez cette ligne, puis `systemctl daemon-reload && systemctl restart wolf-agent`.
::

::tabs
  :::tabs-item{label="nftables"}
  ```bash [hôte]
  install -m 0755 -o root -g root agent/wolf-block.sh /usr/local/sbin/wolf-block
  echo 'wolf-agent ALL=(root) NOPASSWD: /usr/local/sbin/wolf-block' > /etc/sudoers.d/wolf-block
  chmod 0440 /etc/sudoers.d/wolf-block
  ```

  Dans la configuration de l'agent :

  ```json [/etc/wolf-agent/config.json]
  "response": {"enabled": true}
  ```

  Redémarrez l'agent. `wolf-block` ajoute l'adresse à un set nftables (`inet wolf`, `blocked4` /
  `blocked6`) dont les entrées expirent d'elles-mêmes. `nft list table inet wolf` les affiche.
  :::

  :::tabs-item{label="fail2ban"}
  Là où fail2ban gère déjà le pare-feu, `wolf-block-fail2ban` bannit dans une jail dédiée (`wolf`),
  avec votre action de bannissement habituelle :

  ```bash [hôte]
  cp agent/fail2ban/wolf.local /etc/fail2ban/jail.d/wolf.local && fail2ban-client reload
  install -m 0755 -o root -g root agent/wolf-block-fail2ban.sh /usr/local/sbin/wolf-block-fail2ban
  install -d -m 0700 /var/lib/wolf-block   # les expirations ; accessible en écriture depuis l'unité de l'agent
  echo 'wolf-agent ALL=(root) NOPASSWD: /usr/local/sbin/wolf-block-fail2ban' > /etc/sudoers.d/wolf-block
  chmod 0440 /etc/sudoers.d/wolf-block
  # un redémarrage perd les débannissements planifiés : purger ceux qui ont expiré toutes les 5 minutes
  echo '*/5 * * * * root /usr/local/sbin/wolf-block-fail2ban --sweep >/dev/null' > /etc/cron.d/wolf-block-fail2ban
  ```

  Dans la configuration de l'agent :

  ```json [/etc/wolf-agent/config.json]
  "response": {"enabled": true, "command": ["sudo", "-n", "/usr/local/sbin/wolf-block-fail2ban", "{ip}", "{seconds}"]}
  ```

  `fail2ban-client get wolf banip` liste les adresses. `fail2ban-client set wolf unbanip IP` en lève
  une avant l'heure. Sans la jail, le script refuse et le signale, et l'action revient en *Failed*.
  :::
::

Les chemins sont relatifs à une copie locale du dépôt.

### Commande personnalisée

`response.command` remplace la commande. `{ip}` et `{seconds}` sont renseignés.

### Fonctionnement des durées avec fail2ban

fail2ban n'a pas de durée par bannissement : chaque bannissement reçoit le `bantime` de la jail.
Celui de la jail est le plus long blocage que Wolf demande (7 jours), et le script débannit chaque
adresse à la fin de sa propre durée :

- un timer systemd transitoire (`wolf-unban-<ip>-<time>`) lance `fail2ban-client set wolf unbanip` ;
- chaque expiration est aussi écrite dans `/var/lib/wolf-block/fail2ban.state`, et `--sweep`
  débannit celles qui sont échues.

Les timers ne survivent pas à un redémarrage, et fail2ban restaure ses bannissements après un
redémarrage. Sans la ligne cron, un blocage pourrait durer jusqu'aux 7 jours de la jail. Le script
purge aussi à chaque bannissement.

## Réponse active de Wazuh

Avec **Block With** sur `wazuh` ou `both` (**Wolf Settings → Blocking**), un blocage approuvé passe
par la réponse active de Wazuh sur l'agent Wazuh de l'hôte attaqué, via l'API du manager Wazuh. C'est
la même approbation, les mêmes liens signés, le même journal : seul change celui qui applique le
blocage.

| Block With | Qui applique un blocage approuvé |
|---|---|
| `wolf_agent` (par défaut) | le Wolf Agent de l'hôte attaqué, comme ci-dessus |
| `wazuh` | la réponse active de Wazuh sur l'agent Wazuh de cet hôte |
| `both` | chacun des deux : deux lignes **Wolf Response Action**, une par exécutant |

Un blocage est proposé pour l'hôte attaqué, pas pour l'agent qui a envoyé l'alerte : une alerte
Wazuh ou Suricata, lue sur l'hôte du manager ou de la sonde, ou envoyée par l'intégration, concerne
l'hôte qu'elle nomme. L'événement de tout autre agent concerne l'hôte de cet agent, quoi qu'indique
son `host` : un agent ne peut pas diriger un blocage vers une autre machine. Avec
`wolf_agent`, un hôte sans Wolf Agent ne reçoit pas de proposition de blocage ; avec `wazuh` ou
`both`, si.

::steps{level="3"}

### Définir une commande temporisée sur le manager Wazuh

Wolf lance une commande *nommée*, que Wazuh retire de lui-même à la fin de son délai. Ajoutez un
bloc `<active-response>` pour `firewall-drop` avec le délai voulu, sur une règle qui ne se
déclenche jamais pour qu'il ne s'exécute qu'à la demande de Wolf, puis redémarrez le manager :

```xml [ossec.conf]
<active-response>
  <disabled>no</disabled>
  <command>firewall-drop</command>
  <location>local</location>
  <rules_id>999999</rules_id>
  <timeout>86400</timeout>
</active-response>
```

Wazuh nomme la commande avec son délai : `firewall-drop86400` (listée dans
`/var/ossec/etc/shared/ar.conf`). Ce délai est la durée du blocage ; les heures choisies à
l'approbation ne valent que pour le blocage du Wolf Agent. Un script (`!firewall-drop`) est refusé :
Wazuh ne le retire jamais.

### Créer un utilisateur d'API Wazuh

Un utilisateur autorisé à lire les agents et à lancer des commandes de réponse active
(`agent:read`, `active-response:command`).

### Renseigner Wolf Settings → Blocking

| Champ | Valeur |
|---|---|
| **Block With** | `wazuh` ou `both` |
| **Wazuh Active Response Command** | `firewall-drop86400` |
| **Wazuh API URL** | `https://wazuh-manager:55000`. `http://` uniquement vers la même machine (`127.0.0.1`, `localhost`) : le mot de passe part à chaque connexion. Changer l'URL redemande le mot de passe. |
| **Wazuh API User**, **Wazuh API Password** | l'utilisateur ci-dessus |
| **Verify Wazuh TLS Certificate** | activé, sauf si le manager a un certificat auto-signé sur un réseau de confiance |
::

- Wolf trouve l'agent Wazuh par les noms de l'hôte (son nom d'hôte Wolf, ses
  [alias](/fr/security/wazuh-suricata#alias)), puis par une adresse qu'un seul agent Wazuh possède :
  des hôtes derrière un même NAT partagent la leur. Le manager (`000`) n'exécute jamais de blocage. Quand aucun agent ne correspond, l'action est *Failed* avec la raison :
  ajoutez un Wolf Entity Alias et approuvez à nouveau.
- L'action est *Applied* ou *Failed* immédiatement, avec la réponse de Wazuh, et journalisée comme
  les autres. Elle est enregistrée avant l'appel à Wazuh : un blocage appliqué par Wazuh a toujours
  sa ligne.
- Avec `both`, chaque exécutant a sa propre durée (les heures demandées pour le Wolf Agent, le délai
  de la commande pour Wazuh) et sa propre ligne. Quand la moitié Wazuh échoue, elle seule est
  proposée à nouveau pendant que la moitié du Wolf Agent attend son agent.
- Testé avec un manager et un agent Wazuh 4.9.2 : l'adresse a été bloquée par iptables sur l'agent,
  et Wazuh a retiré la règle à la fin du délai.

## CrowdSec

Avec une Local API (LAPI) CrowdSec, les blocages approuvés atteignent chaque bouncer de cette LAPI
(pare-feu, nginx, Cloudflare), et Wolf et CrowdSec partagent leurs détections. Désactivé par défaut ;
s'exécute chaque minute, sur le site central uniquement.

::steps{level="3"}

### Créer les identifiants

```bash [hôte CrowdSec]
cscli bouncers add dodock-wolf   # affiche la clé du bouncer : décisions entrantes
cscli machines add dodock-wolf --password '<long random password>'  # détections et blocages sortants
```

### Renseigner Wolf Settings → CrowdSec

| Réglage | Défaut | Effet |
|---|---|---|
| **Use CrowdSec** | désactivé | active l'intégration |
| **Local API URL**, **Bouncer API key**, **Machine ID**, **Machine password** | | la LAPI et les identifiants ci-dessus |
| **Send detections** | activé | les événements de sécurité avec une IP, d'une gravité égale ou supérieure à **Minimum severity sent** (`warning`), deviennent des alertes LAPI avec le scénario `dodock-wolf/<category>`. Les événements passés ne sont pas rejoués. |
| **Let CrowdSec decide on detections** | désactivé | désactivé : les alertes portent `remediation: false`, CrowdSec les enregistre (`cscli alerts list`) et ne décide rien. Activé : les profils de CrowdSec décident ; le profil par défaut bannit l'IP pendant 4 h, sans approbation humaine. |
| **Apply approved blocks** | activé | un **Block IP** approuvé part vers la LAPI sous la forme d'une décision `ban` pour la durée approuvée (origine `dodock-wolf`). |

::

**Décisions entrantes** : Wolf lit les décisions de la LAPI (la liste complète au premier passage
puis toutes les heures, les changements entre-temps), y compris les propres détections de CrowdSec,
les bannissements `cscli` et la blocklist communautaire quand la LAPI est enrôlée. Un événement de
sécurité dont l'IP fait l'objet d'une décision reçoit `payload.crowdsec` (type, origin, scenario,
until) et monte d'un niveau de gravité. Les propres blocages de Wolf sont marqués mais leur gravité
n'est pas relevée.

L'agent applique toujours son propre blocage quand son module de réponse est actif, et le
commentaire de l'incident indique ce qui a été envoyé, et où. Testé avec CrowdSec 1.6.4.
