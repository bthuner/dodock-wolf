Les alertes Wolf sont envoyées par le site Wolf. Quand ce site, sa base de données ou son
planificateur (scheduler) est en panne, personne n'en serait averti. L'agent surveille donc le site
et alerte via son propre **canal de secours**, qui ne passe pas par le site. C'est le chien de garde
(watchdog).

## Quand il alerte

Chaque réponse à un envoi contient le `health` du site ([protocole](/fr/reference/protocol)).
L'agent déclare une panne quand :

- les envois échouent depuis `stale_minutes` : le site, un proxy ou la base de données est en panne ;
- le site indique que ses règles d'alerte (ou, sans règle active, ses tâches planifiées) n'ont pas
  tourné depuis `stale_minutes` : planificateur arrêté ou en pause, aucun worker, Redis en panne, ou
  heures enregistrées décalées dans le futur par un changement de fuseau horaire ;
- des envois en file d'attente attendent un worker depuis `stale_minutes`. En mode d'ingestion
  `async`, le site répond avant de stocker : les envois semblent réussir alors que rien n'est stocké.

Il envoie une alerte par panne, puis un avis de rétablissement quand les envois fonctionnent et que
les règles tournent de nouveau. L'état est conservé dans `<spool_dir>/watchdog-state.json` : un
redémarrage ne répète pas l'alerte et n'oublie pas la panne. Une livraison échouée est retentée
chaque minute.

Si le site rejette les identifiants de l'agent, une dernière alerte part avant que l'agent ne
s'arrête.

## Canaux

Les deux sont optionnels. Quand les deux sont configurés, les deux sont utilisés.

```json [/etc/wolf-agent/config.json]
"watchdog": {
  "enabled": true,
  "stale_minutes": 5,
  "webhook_url": "https://chat.example.com/hooks/xxxx",
  "smtp": {"host": "smtp.example.com", "port": 587, "starttls": true,
           "from": "wolf@example.com", "to": ["ops@example.com"],
           "user": "wolf", "password": "…"}
}
```

::field-group
  :::field{name="webhook_url" type="string"}
  Envoie en POST `{"text": "..."}`, que les webhooks entrants de Slack, Mattermost et Rocket.Chat
  acceptent.
  :::

  :::field{name="smtp" type="object"}
  `host`, `port` (25 par défaut ; 587 avec `starttls`, 465 avec `ssl`), `from`, `to` (liste ou
  valeurs séparées par des virgules), `starttls` (activé par défaut pour le port 587), `ssl`, `user`,
  `password`, `verify_tls`.
  :::

  :::field{name="stale_minutes" type="number"}
  `5` par défaut.
  :::
::

Sans canal, le chien de garde se contente d'écrire dans le journal au niveau ERROR.
`"enabled": false` le désactive.

```bash [hôte]
sudo -u wolf-agent wolf-agent test-fallback   # après avoir modifié la configuration
sudo -u wolf-agent wolf-agent check           # affiche l'état du chien de garde sur stderr
```

::tip
Faites pointer le canal de secours vers un canal qui ne dépend pas de l'hôte du site Wolf : un autre
relais de messagerie, ou un webhook de messagerie instantanée.
::

## Sur la chronologie après coup

Tant que ses règles sont en retard, le site enregistre un événement `scheduler_stalled` à chaque
envoi. La règle prédéfinie **Scheduler stalled** le transforme en incident dès que le planificateur
tourne de nouveau : la panne apparaît ainsi sur la chronologie Wolf.
