**Wolf Settings → SIEM export (syslog)** (désactivé par défaut) envoie les événements de sécurité
de Wolf et son journal signé à un collecteur syslog. Chaque minute, les événements qui
correspondent aux filtres, ainsi que chaque entrée signée du journal, partent en syslog RFC 5424
(facility `local0`) contenant du JSON OCSF ou du CEF.

## Paramètres

| Paramètre | Valeurs | Défaut |
|---|---|---|
| **Export to a SIEM** | activé / désactivé | désactivé |
| **Collector host** | un nom d'hôte ou une adresse. Avec TLS, il doit figurer dans le certificat du collecteur | |
| **Port** | | `514` |
| **Transport** | `tcp`, `tls` (RFC 5425), `udp` (RFC 5426) | `tcp` |
| **Verify the collector's certificate** | activé / désactivé (TLS) | activé |
| **Collector CA file** | un fichier PEM d'une autorité de certification privée, absolu ou relatif au site (`private/files/collector-ca.pem`). Vide : les autorités du système | |
| **Framing** | `octet-counting` ou `newline` (TCP et TLS, RFC 6587) | `octet-counting` |
| **Message header** | `rfc5424` ou `none` | `rfc5424` |
| **Format** | `ocsf` ou `cef` | `ocsf` |
| **Minimum severity** | `info`, `warning`, `critical` | `warning` |
| **Event types** | séparés par des virgules : `security`, `error`, `cron_failure`, `worker_failure`, `host_metric_alert`, `deployment` | `security` |
| **Send the journal** | envoie aussi chaque entrée signée du journal (seq, empreinte, mac) | activé |

Pour tester un collecteur, un Wolf Manager peut faire un POST sur `dodock_wolf.api.siem.send_test`.
Il envoie un message `wolf_test` avec les paramètres actuels, même quand **Export to a SIEM** est
désactivé :

```bash
curl -X POST -H "Authorization: token <api_key>:<api_secret>" \
  https://wolf.example.com/api/method/dodock_wolf.api.siem.send_test
```

### Format

- **OCSF** : JSON, Detection Finding (classe 2004). Techniques ATT&CK dans `finding_info.attacks` ;
  site, bench et payload de Wolf sous `unmapped`. La correspondance est la lecture que fait Wolf du
  schéma, pas un profil certifié.
- **CEF** : ATT&CK dans `cs4`, listes de [réputation d'IP](/fr/security/journal#listes-de-réputation-dip)
  dans `cs5`.

### En-tête du message

- `rfc5424` : un en-tête syslog avant chaque message : priorité, horodatage, le site comme nom
  d'hôte, `dodock-wolf` comme application, la catégorie de l'événement comme MSGID.
- `none` : le JSON ou le CEF brut, pour les collecteurs qui décodent eux-mêmes le message, comme le
  décodeur JSON de Wazuh et l'entrée CEF de Graylog.

### Transport et tramage

- Préférez TCP ou TLS. UDP envoie un datagramme par message, coupé à 8 Ko. Wolf ne peut pas savoir
  si le collecteur a reçu quoi que ce soit, le curseur avance donc quand même.
- `octet-counting` fait précéder chaque message de sa longueur. rsyslog, syslog-ng et l'entrée
  Syslog de Graylog le lisent.
- `newline` envoie un message par ligne ; un saut de ligne à l'intérieur d'un message devient une
  espace. Wazuh et l'entrée CEF de Graylog en ont besoin.

### TLS

- Le certificat du collecteur est vérifié par rapport aux autorités du système, ou à
  **Collector CA file**.
- Python 3.13 et versions ultérieures vérifient strictement : l'autorité doit avoir
  `basicConstraints=CA:TRUE` et `keyUsage=keyCertSign`, et le certificat du serveur doit avoir un
  Authority Key Identifier.

::caution
Désactiver la vérification du certificat fonctionne, mais toute personne sur le chemin peut alors
lire l'export.
::

## Livraison

- Un curseur n'avance qu'une fois un lot envoyé. Un collecteur indisponible retarde l'export ; rien
  n'est sauté.
- Un échec au milieu d'un lot peut envoyer un message deux fois : la livraison est « au moins une
  fois ».
- Les événements de moins de 2 minutes attendent l'exécution suivante, pour qu'une transaction
  validée un peu après son insertion ne soit pas sautée.
- Les payloads partent tels qu'ils sont stockés (déjà [nettoyés](/fr/agent/scrubbing) par
  l'agent), coupés à 4 Ko.
- Les entrées du journal donnent au SIEM une copie externe de la chaîne : une ancre que Wolf ne
  peut pas réécrire. Voir [Journal infalsifiable](/fr/security/journal#journal-infalsifiable).

## Collecteurs

Chaque recette a été testée contre le vrai collecteur (novembre 2026).

| Collecteur | Format | En-tête du message | Transport | Tramage | Ce que vous obtenez |
|---|---|---|---|---|---|
| rsyslog 8.2404 | OCSF ou CEF | `rfc5424` | UDP, TCP ou TLS | `octet-counting` (TCP/TLS) | messages écrits tels qu'envoyés ; le MSGID est la catégorie de l'événement |
| manager Wazuh 4.9.2 | OCSF | `none` | TCP | `newline` | une alerte Wazuh par constat, niveau selon la gravité |
| Graylog 6.1, entrée CEF | CEF | `none` | TCP | `newline` | chaque champ extrait (adresse source, ATT&CK, site, gravité) |
| Graylog 6.1, entrée Syslog | OCSF ou CEF | `rfc5424` | UDP, TCP ou TLS | `octet-counting` | messages stockés, JSON non découpé en champs |

::tabs
  :::tabs-item{label="rsyslog"}
  ```text [rsyslog.conf]
  module(load="imptcp")                     # TCP, à comptage d'octets ou par ligne
  input(type="imptcp" port="514")
  module(load="imtcp" StreamDriver.Name="gtls" StreamDriver.Mode="1" StreamDriver.AuthMode="anon")
  input(type="imtcp" port="6514")           # TLS (les DefaultNetstreamDriver* globaux pointent vers le certificat)
  module(load="imudp")
  input(type="imudp" port="514")
  ```

  Les paramètres Wolf par défaut fonctionnent : `rfc5424`, `octet-counting`, OCSF ou CEF.
  :::

  :::tabs-item{label="Wazuh"}
  1. Sur le manager, ajoutez une entrée syslog à `/var/ossec/etc/ossec.conf` :

     ```xml [ossec.conf]
     <remote>
       <connection>syslog</connection>
       <port>514</port>
       <protocol>tcp</protocol>
       <allowed-ips>WOLF_SITE_ADDRESS/32</allowed-ips>
     </remote>
     ```

  2. Copiez le [fichier de règles](https://github.com/bthuner/dodock-wolf/blob/main/docs/siem/wazuh_dodock_wolf_rules.xml)
     dans `/var/ossec/etc/rules/` et redémarrez le manager. Il nécessite Wazuh 4.6 ou version
     ultérieure.
  3. Configurez Wolf ainsi : format `ocsf`, en-tête du message `none`, transport `tcp`, tramage
     `newline`.

  | Constat Wolf | Règle Wazuh | Niveau |
  |---|---|---|
  | info | 100901 | 3 |
  | warning | 100902 | 7 |
  | critical | 100903 | 12 |
  | entrée du journal | 100910 | 3 |

  Les champs OCSF deviennent des champs Wazuh : `src_endpoint.ip`, `finding_info.title`,
  `finding_info.attacks`, `unmapped.site`, etc.

  Ne fonctionne pas avec Wazuh :

  - l'en-tête RFC 5424 : Wazuh ne l'analyse pas, seule une règle générique se déclenche ;
  - CEF : Wazuh n'a pas de décodeur pour ce format ;
  - les trames à comptage d'octets : elles sont abandonnées ;
  - TLS : l'entrée syslog de Wazuh n'en a pas. Placez un relais local (rsyslog, stunnel) devant
    quand le réseau entre Wolf et Wazuh n'est pas de confiance.
  :::

  :::tabs-item{label="Graylog"}
  **Pour obtenir des champs** : créez une entrée **CEF TCP**, puis configurez Wolf ainsi : format
  `cef`, en-tête du message `none`, transport `tcp`, tramage `newline`.

  - L'entrée extrait `sourceAddress`, `deviceHostName` (le site), `mitre_attack`, `site`,
    `severity`, `event_class_id` (la catégorie) et les `digest` / `mac` du journal.
  - `source` est l'adresse du site Wolf.
  - L'en-tête RFC 5424 perturbe cette entrée : `source` devient `-`.

  **Pour seulement stocker** : les entrées Syslog TCP, UDP ou TLS acceptent les paramètres par
  défaut (`rfc5424`, `octet-counting`). Graylog garde le MSGID et le tiret des données structurées
  au début de `message` et ne découpe pas le JSON. Ajoutez un extracteur JSON ou une règle de
  pipeline si vous choisissez cette voie.
  :::

  :::tabs-item{label="UniSOC et autres"}
  UniSOC n'a pas été testé, faute d'instance. Tout collecteur qui accepte du syslog RFC 5424, du
  CEF ou des lignes JSON devrait fonctionner avec l'une des combinaisons ci-dessus.
  :::
::

::note
Quand Wolf exporte vers un manager Wazuh que le Wolf Agent lit aussi, les alertes de Wazuh sur
l'export de Wolf lui-même (groupe `dodock_wolf`) sont toujours écartées, pour que rien ne revienne
en boucle. Voir [Wazuh et Suricata](/fr/security/wazuh-suricata).
::
