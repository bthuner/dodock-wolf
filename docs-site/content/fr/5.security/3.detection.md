Le Wolf Agent effectue sa propre détection web et hôte à partir des journaux qu'il suit déjà. Il
n'a besoin ni de Wazuh, ni de Suricata, ni d'aucun paquet supplémentaire. Tous les constats sont
des événements `security`, nettoyés sur l'hôte avant leur envoi (voir
[Nettoyage (scrubbing)](/fr/agent/scrubbing)).

## Attaques web depuis nginx

L'agent lit les mêmes journaux d'accès nginx que pour `http_5xx` et `http_502`. Rien à activer :
dès que l'agent suit le journal nginx d'un bench, la détection des attaques web fonctionne. Les
chemins des journaux se définissent par bench dans `nginx_access_log` (voir
[Configuration](/fr/agent/configuration)).

### Ce qui compte comme un sondage

Une requête est un sondage quand elle :

- cherche des secrets : `.env`, `.git/`, `.git-credentials`, `.npmrc`, `docker-compose.yml`,
  `site_config.json`, clés, dumps ;
- cherche des panneaux CMS et d'administration (`wp-login.php`, `phpmyadmin`…) ;
- cherche des équipements de bordure connus pour leurs failles : Fortinet, Palo Alto GlobalProtect,
  Ivanti, Citrix, Cisco ASA, F5, Exchange, Confluence et Struts, GeoServer, Jenkins ;
- tente une traversée de chemin, une injection SQL, de commande ou de template, ou un XSS ;
- vient d'un User-Agent de scanner (sqlmap, nuclei, ffuf, dirsearch, katana, LeakIX…).

Les chemins d'équipements sont comparés au chemin seul, depuis sa racine : un DocType, une page web
ou une chaîne de requête peut très bien nommer Jenkins ou Citrix.

Deux règles Frappe ne comptent qu'en rafale, car un appel isolé est normal : depuis un client, sur
deux minutes,

- 10 appels aux points d'entrée invités qui disent si un compte existe ou prennent un identifiant
  hors de la page de connexion (`frappe_auth_abuse`, `/api/method` et `/api/v2/method`) :
  réinitialisation du mot de passe, lien de connexion, inscription, confirmation de suppression des
  données personnelles, le point d'entrée de jeton OAuth2 (dont l'octroi par mot de passe contournait
  l'authentification à deux facteurs avant un correctif ; un jeton de rafraîchissement dans l'URL
  n'est pas compté), les connexions LDAP et par clé ou jeton ;
- 20 appels à `/api/method`, `/api/resource` ou `/api/v2` répondus par 403, sur au moins 5 méthodes
  (`frappe_api_forbidden`) : des méthodes essayées sans le droit de les appeler. Le 401 est laissé
  de côté : il signifie aussi une session expirée, comme après un déploiement.

À côté des autres sondages d'un client dans la même minute, ces appels sont listés avec eux.
Les connexions échouées sur la page de connexion sont le [signal](/fr/security/site-signals)
propre au site. Une injection SQL dans un
en-tête ou dans le corps d'une requête n'apparaît pas dans un journal d'accès :
[Suricata](/fr/security/wazuh-suricata#suricata) les voit.

Les cibles encodées en URL sont décodées deux fois avant la comparaison.

### Événements

| Catégorie | Gravité | Signification |
|---|---|---|
| `web_attack_probe` | warning, critical dès qu'un client envoie 50 sondages ou plus | un événement par (site, client) et minute (heure du log), avec les règles touchées, les statuts, jusqu'à 10 cibles et les identifiants ATT&CK |
| `web_sensitive_file_exposed` | critical | un fichier contenant des secrets a reçu une réponse 2xx. Le fichier a probablement fuité |

### Ce qui n'est pas un sondage

- Les pièces jointes (`/files`, `/private/files`) et les téléchargements de sauvegardes autorisés
  (`/backups`).
  Les ressources statiques et les pièces jointes ne sont pas vérifiées pour les noms de CMS ou
  d'équipements (Font Awesome fournit un `joomla.svg`).
- Un 2xx sous une route qui répond à tout sous-chemin par une page (`/app/`, `/wolf/`, `/api/`…)
  n'est pas compté comme un fichier servi.

### L'adresse du client

Le client est `$remote_addr`. Quand `$remote_addr` est un proxy de boucle locale ou privé, l'agent
prend l'adresse publique la plus à droite de la liste `X-Forwarded-For` journalisée après lui :
celle que votre proxy a ajoutée. Les entrées les plus à gauche sont écrites par le client et ne
sont pas dignes de confiance.

### Règles prédéfinies

| Règle prédéfinie | Se déclenche quand |
|---|---|
| *Web attack scan* | 100 requêtes `web_attack_probe` ou plus en 10 min, par site (warning) |
| *Sensitive file served* | n'importe quel `web_sensitive_file_exposed` (critical). Changez les secrets |

## Signaux d'intrusion sur l'hôte

L'agent lit `/var/log/auth.log`, `/var/log/secure`, ou le journal systemd :

```bash
journalctl -o short-iso -t sshd -t sshd-session -t sudo -t useradd -t usermod -t gpasswd -t chsh
```

`sshd-session` couvre OpenSSH 9.8 et versions ultérieures. Le format `short-iso` conserve
l'horodatage réel de chaque ligne.

Le paramètre `auth_log` choisit la source : `null` la détecte automatiquement, un chemin impose un
fichier, `"journal"` impose journalctl, `false` le désactive. L'installateur ajoute l'utilisateur
`wolf-agent` aux groupes `adm` et `systemd-journal` quand ils existent, afin qu'il puisse lire ces
journaux sans être root.

| Catégorie | Signification | Gravité | Règle prédéfinie |
|---|---|---|---|
| `ssh_failed_login` | connexions SSH échouées, agrégées par IP source et par minute (heure du log) | warning, critical à partir de 20 dans un même événement | *SSH brute force* : 20 ou plus en 10 min, par hôte (critical) |
| `ssh_root_login` | une connexion root | warning | aucune |
| `ssh_login_after_failures` | une connexion réussie depuis une adresse qui a échoué 5 fois ou plus dans l'heure précédente. Les compteurs d'échecs survivent aux intervalles d'envoi | critical | *SSH login after brute force* |
| `sudo_failure` | mauvais mots de passe sudo, utilisateurs absents des sudoers | warning | *Repeated sudo failures* : 3 ou plus en 10 min, par hôte |
| `account_created` | `useradd` crée un compte local ; ou un compte reçoit un shell de connexion (`usermod -s`, `chsh`) ou l'UID 0 (`usermod -u 0`, critique) | warning | *New system account* |
| `service_account_created` | `useradd` crée un compte avec un UID système (1-999) et sans shell de connexion (exactement `/usr/sbin/nologin`, `/sbin/nologin`, `/bin/false`, `/usr/bin/false`) : ce qu'un paquet ajoute pour son service. Enregistré, aucun preset ne déclenche d'alerte dessus | info | — |
| `admin_group_change` | un utilisateur est ajouté à `sudo`, `wheel`, `admin`, `root`, `adm`, `docker` ou `lxd` | critical | *User added to admin group* |

::tip
*New system account* se déclenche aussi lors d'un provisionnement planifié. Ouvrez un
**Wolf Silence** pour l'hôte pendant que vous le provisionnez.
::

## Exposition et risques de configuration du site

Toutes les `exposure.interval` (600 s par défaut), l'agent vérifie ce qu'exposent un hôte et ses
sites.

### Services du bench exposés

`exposed_services`, par hôte, compte les ports du bench à l'écoute sur toutes les interfaces ou sur
une adresse publique dans `/proc/net/tcp{,6}` :

| Service | Port |
|---|---|
| MariaDB | 3306 |
| Postgres | 5432 |
| Redis | 6379, 11000, 12000, 13000, ou les ports `redis_*` propres au bench |
| socket.io | 9000 |
| gunicorn | 8000 ou `webserver_port` |

Ajoutez des ports avec `exposure.ports`, une table associant un port à un nom de service. Une
adresse de réseau local n'est pas comptée.

::note
Un socket à l'écoute ne prouve pas qu'il est joignable : un pare-feu peut encore bloquer ce qui est
compté.
::

### Risques de configuration du site

`site_config_risks`, par site, compte ces éléments dans `site_config.json` :

- `developer_mode` ;
- `allow_tests` ;
- un `host_name` en HTTP simple ;
- `allow_cors: "*"`.

### Événements et règles prédéfinies

L'agent n'envoie les événements `service_exposed` et `insecure_site_config` que lorsque l'ensemble
qu'il trouve change. Tous deux sont étiquetés T1190.

| Règle prédéfinie | Se déclenche quand |
|---|---|
| *Bench service exposed* | `exposed_services` supérieur à 0, par hôte (critical). Redis n'a pas de mot de passe par défaut |
| *Development settings in production* | `site_config_risks` supérieur à 0, par site (warning) |

Les deux métriques alimentent aussi le [score de sécurité](/fr/security/compliance#score-de-sécurité).

## Intégrité des fichiers

Toutes les `integrity.interval` (900 s par défaut), l'agent compare ce qui compose un bench avec sa
référence :

| Surveillé | Ce que signifie un changement |
|---|---|
| chaque app sous `apps/<app>/` (sans `.git`, `node_modules`, `public/dist` et les autres sorties `dist`/`build`, `*.egg-info`, les caches ni les fichiers compilés `.pyc` et `.mo`) | avec le commit git de l'app inchangé : du code modifié hors déploiement (un web shell, un fichier patché), **critical**. Avec un nouveau commit : un déploiement, **info**, avec les deux commits, ou **warning** s'il a ajouté du Python dans un dossier `www/`. Sans dépôt git (une installation depuis une archive, une image sans `.git`), Wolf ne peut pas trancher : **warning**, en le disant |
| `sites/common_site_config.json`, chaque `sites/<site>/site_config.json` | **warning**. Seuls les noms des clés ajoutées, modifiées ou supprimées sont envoyés, jamais leurs valeurs |
| le `config/` du bench (les fichiers nginx et supervisor qu'il génère, sans `pids/`), `/etc/nginx` et `/etc/supervisor` | **warning** : quelqu'un a peut-être redirigé le trafic ou lancé un processus |

- Chaque analyse ne recalcule l'empreinte que de ce qui a changé de taille ou de date de
  modification ; toutes les `integrity.full_scan_interval` (24 h), elle recalcule tout, si bien qu'un
  fichier dont la taille et la date ont été remises en place est tout de même repéré.
- Tant que git tient un verrou dans une app (un pull ou un checkout en cours), l'app est jugée à
  l'analyse suivante : un déploiement n'est pas pris pour une altération à mi-chemin.
- Les fichiers de plus de 32 Mo sont comparés par taille et date uniquement, et une passe s'arrête
  après 200 000 fichiers ; le reste garde sa référence jusqu'à la passe suivante.
- La première analyse d'un chemin constitue sa référence et ne déclenche rien. La référence est
  gardée dans le répertoire de la file locale (`integrity-state.json`, mode 0600) : un redémarrage
  ne masque pas ce qui a changé entre-temps. `wolf-agent check` ne la modifie jamais. Les valeurs des
  configurations de site sont gardées sous forme de HMAC, avec une clé propre à cette installation
  (`integrity.key`, 0600).
- Un bench ou un site que la découverte ne voit plus pendant un temps garde sa référence 7 jours.
  Une app retirée de `apps/`, un site ou un chemin de configuration disparu est signalé une fois,
  comme supprimé (warning).
- Un fichier ou un dossier que l'agent ne peut pas lire garde sa référence au lieu d'être compté
  comme supprimé : `integrity_unreadable` les compte.
- Une configuration de site réécrite avec les mêmes clés et valeurs ne déclenche rien.
- Événements : `bench_code_changed` (par app) et `bench_config_changed` (par fichier ou chemin
  serveur), avec jusqu'à 20 chemins de chaque sorte (ajoutés, modifiés, supprimés). Marqués T1505.003
  et T1565.001 ; un déploiement n'a pas de technique. `integrity_files` compte ce qui est surveillé,
  par bench et pour les chemins propres à l'hôte.
- `integrity.server_paths` remplace `/etc/nginx` et `/etc/supervisor`, par exemple sur un hôte dont
  le serveur web est ailleurs. L'utilisateur de l'agent doit pouvoir lire ce qu'il surveille ; les
  fichiers illisibles sont ignorés.

| Règle prédéfinie | Se déclenche quand |
|---|---|
| *Bench code changed outside a deployment* | un événement `bench_code_changed` en critical, par bench (critical) |
| *Bench or server config changed* | un événement `bench_config_changed`, par hôte (warning) |

## Connexions sortantes

Sans Suricata, l'agent remarque tout de même un bench qui se connecte à un nouvel endroit : un
indice léger de commande et contrôle ou d'exfiltration, pas une inspection des paquets. Toutes les
`outbound.interval` (60 s), il lit `/proc/net/tcp` et `/proc/net/tcp6` et garde les connexions
établies qui :

- appartiennent à l'utilisateur d'un bench, le propriétaire du dossier du bench. Savoir quel
  processus tient une socket demanderait root : des benches qui partagent un utilisateur partagent
  un même registre, et tout ce que lance cet utilisateur (une session SSH, un `git push`) compte comme
  venant du bench. Un bench appartenant à root est ignoré ;
- partent d'un port local sur lequel rien n'écoute : le bench est le client, il ne répond pas à un
  visiteur ;
- vont vers une adresse publique. Les pairs privés, de bouclage ou link-local (MariaDB, Redis, une
  API du réseau local) sont exclus, sauf avec `outbound.include_private`.

Une destination est le réseau distant (/24 en IPv4, /48 en IPv6) et le port : l'adresse suivante
d'un CDN n'est pas nouvelle. Pendant `outbound.learn_days` (7) après la première fois que l'agent voit
l'utilisateur d'un bench, chaque destination est apprise sans bruit. Ensuite :

- une nouvelle destination sur un port inhabituel est signalée une fois en `bench_new_outbound`
  (**warning**), 20 au plus par analyse ; les autres sortent aux analyses suivantes ;
- une destination sur un port habituel (web, mail avec 2525, IMAP et POP, DNS, NTP, SSH et git,
  LDAP ; ajoutez les vôtres avec `outbound.usual_ports`) est seulement comptée dans
  `bench_new_outbound_usual`, car les clouds changent d'adresse toute la journée.
  `outbound.report_usual_ports` les signale aussi, en **info**.

Une destination non revue pendant 30 jours est oubliée. Le registre est dans le répertoire de la file
locale (`outbound-state.json`, 0600). `bench_outbound_destinations` compte les destinations vues à
chaque échantillon.

L'événement nomme la destination dans `remote_ip` et `remote_port`, pas dans `ip` : un partenaire que
le bench appelle n'est pas la partie distante d'une attaque. Elle se recherche par entité et passe
par les [listes de réputation d'IP](/fr/security/journal#listes-de-réputation-dip), qui relèvent une
destination connue comme malveillante, mais elle ne regroupe jamais d'incidents par IP, n'alimente
pas de règle de séquence, ne part pas vers CrowdSec comme attaquant et ne reçoit pas de proposition
de blocage.

**Les benches en conteneur** (Docker, Podman) ont leur propre réseau. L'agent les trouve sans
root : le cgroup de chaque conteneur le nomme (`/proc/<pid>/cgroup`), le dossier qu'il monte depuis
l'hôte (`/proc/<pid>/mountinfo`, par exemple le `sites/` du bench, sur le même système de fichiers)
dit de quel bench il s'agit, et la table TCP propre au conteneur (`/proc/<pid>/net/tcp`) donne ses
connexions. Plusieurs conteneurs d'un même bench forment un seul registre, et un conteneur sur le
réseau de l'hôte n'est pas compté deux fois. L'événement indique `seen_by: container`.

**Derrière un proxy sortant**, les connexions vont au proxy, pas aux vraies destinations : l'agent lit
alors le journal d'accès du proxy. `/var/log/squid/access.log` est lu s'il existe ;
`outbound.proxy_logs` en désigne d'autres (un chemin, ou `[{"path": "...", "format": "squid"}]`) ;
pour un proxy qui tourne dans un conteneur, donnez le chemin de son journal sur l'hôte. Seul le format
natif de Squid est lu. Chaque requête nomme son hôte et son port de destination (`remote_host`),
toutes, pas un échantillon, et l'adresse du client dit quel bench l'a faite : l'adresse d'un
conteneur, ou celle de l'hôte lui-même (tous ses benches). Les autres clients d'un proxy partagé, comme
les machines du réseau local, sont laissés de côté. L'événement indique `seen_by: proxy`.

::warning
Le dossier des journaux de Squid n'est lisible que par le groupe `proxy` sur Debian et Ubuntu.
L'installeur y ajoute l'utilisateur de l'agent ; sur un hôte préparé à la main, lancez
`sudo usermod -aG proxy wolf-agent` puis redémarrez l'agent. D'ici là, l'agent journalise qu'il ne peut
pas lire le journal.
::

**Chaque nouvelle connexion, pas un échantillon.** Lue depuis `/proc`, une connexion ouverte et
fermée entre deux échantillons est manquée : la plupart des appels de webhook ou d'API durent moins
d'une seconde. Aucune interface du noyau ne liste les connexions passées sans root : cette seule étape
est donc privilégiée, et facultative. L'outil `wolf-outbound-log` ajoute une table nftables qui
journalise chaque **nouvelle** connexion TCP sortante des utilisateurs des benches (`output`, avec leur
uid) et des conteneurs derrière un pont Docker, Podman ou CNI (`docker0`, `br-*`, `podman*`, `cni*` ;
`forward`, avec leur adresse). L'agent lit ces lignes dans le journal du noyau (`journalctl -t kernel`,
en reprenant après un redémarrage, sinon `/var/log/kern.log`), relance l'outil quand les utilisateurs
des benches changent, et marque ces événements `seen_by: kernel`.

```bash [en root]
install -m 0755 -o root -g root agent/wolf-outbound-log.sh /usr/local/sbin/wolf-outbound-log
echo 'wolf-agent ALL=(root) NOPASSWD: /usr/local/sbin/wolf-outbound-log' > /etc/sudoers.d/wolf-outbound-log
chmod 0440 /etc/sudoers.d/wolf-outbound-log
systemctl restart wolf-agent
```

L'agent l'utilise dès qu'il est là (`outbound.kernel_log`, `"auto"`). Il refuse l'uid 0.

- Toutes les règles partagent une même limite : 50 nouvelles connexions par seconde pour tout l'hôte,
  pour que le journal ne puisse pas être inondé ; au-delà, seul ce qu'un échantillon de `/proc` voit
  est compté. L'UDP (DNS, NTP) n'est pas journalisé, ni les destinations privées, de bouclage et
  link-local (`outbound.include_private` ne s'applique pas ici).
- Repérer les nouvelles connexions active le suivi de connexions (conntrack) pour le trafic de l'hôte.
- Les destinations que seul ce journal voit ont leur propre semaine d'apprentissage, à partir de la
  première application de l'outil : l'installer sur un hôte appris depuis longtemps ne déclenche pas
  une rafale d'alertes.
- `nft list table inet wolf_outbound` montre les règles et leurs compteurs. `"kernel_log": false` fait
  retirer la table par l'agent ; pour désinstaller, lancez `wolf-outbound-log --off`. Sans l'outil, ou
  quand sudo refuse, l'agent le signale une fois et continue d'échantillonner `/proc`.

| Règle prédéfinie | Se déclenche quand |
|---|---|
| *Bench connects somewhere new* | un événement `bench_new_outbound` en warning (un port inhabituel), par hôte (warning) |

## Désactiver la détection

| Pour désactiver | Définir dans la configuration de l'agent |
|---|---|
| Les signaux du journal d'authentification | `"auth_log": false` |
| Les vérifications d'exposition | `"exposure": false` |
| L'intégrité des fichiers | `"integrity": false` |
| Les connexions sortantes | `"outbound": false` |

La détection des attaques web suit les journaux nginx : elle s'arrête pour un bench dont l'agent ne
suit pas le journal nginx.
