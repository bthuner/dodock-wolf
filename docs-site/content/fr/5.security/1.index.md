Dodock Wolf détecte les attaques contre un site Frappe, son bench et ses hôtes. Il les corrèle
avec les signaux de santé (5xx, crons en échec, déploiements) dans les mêmes incidents. Chaque
constat de sécurité est un **Wolf Event** de type `security` avec une `category`, par exemple
`ssh_login_after_failures` ou `permission_change`.

Wolf seul constitue le socle. Aucune fonction de sécurité n'a besoin de Wazuh ni de Suricata.
Quand ils tournent sur vos hôtes, le Wolf Agent lit aussi leurs alertes.

## Origine de chaque signal

| Source | Prérequis | Ce qu'elle voit | Page |
|---|---|---|---|
| Site Wolf | le Wolf App installé sur le site | connexions échouées et privilégiées, attributions de rôles, Server et Client Scripts, exécutions de la System Console, modifications de permissions, System Settings affaiblis, clés API, Webhooks, exports de données, leurres (honeytokens) | [Signaux du site](/fr/security/site-signals) |
| Wolf Agent : nginx | journaux d'accès nginx suivis par l'agent | sondages à la recherche de secrets, de panneaux CMS, traversées de chemin, injections, scanners ; fichiers secrets servis | [Détection](/fr/security/detection) |
| Wolf Agent : journal d'authentification | `/var/log/auth.log`, `/var/log/secure` ou le journal systemd | force brute SSH suivie d'une connexion, connexions root, échecs sudo, nouveaux comptes, modifications des groupes d'administration | [Détection](/fr/security/detection#signaux-dintrusion-sur-lhôte) |
| Wolf Agent : exposition | `/proc/net/tcp{,6}` et `site_config.json` | services du bench à l'écoute au-delà de la boucle locale, paramètres de développement en production | [Détection](/fr/security/detection#exposition-et-risques-de-configuration-du-site) |
| Suricata (facultatif) | Suricata écrivant un journal EVE sur l'hôte | alertes d'IDS réseau (`network_ids_alert`) | [Wazuh et Suricata](/fr/security/wazuh-suricata) |
| Wazuh (facultatif) | un manager Wazuh | alertes d'IDS hôte (`hids_alert`) | [Wazuh et Suricata](/fr/security/wazuh-suricata) |

Les signaux qui n'existent qu'à l'intérieur d'un site (connexions, scripts, permissions) sont
captés par le Wolf App de ce site. Pour les voir sur tous les sites d'un bench, installez l'app
sur chacun d'eux et passez-les en mode satellite : voir [Tous les sites d'un bench](/fr/install/every-site).

## Étiquettes MITRE ATT&CK

À l'ingestion, chaque événement `security` reçoit une liste `mitre_attack` dans son payload : un
`{id, name, tactic}` par technique. Wolf fusionne la technique associée à la catégorie de
l'événement avec les identifiants de techniques envoyés par l'agent. Les alertes Suricata et
Wazuh portent les techniques de la règle qui s'est déclenchée. Les événements transmis par les
satellites conservent les leurs.

Les étiquettes accompagnent l'événement jusqu'à l'[export SIEM](/fr/security/siem-export) : OCSF
les place dans `finding_info.attacks`, CEF dans `cs4`.

## Alertes et réponse

Chaque signal a une règle d'alerte prédéfinie. Les règles prédéfinies sont installées sans
canal : elles ouvrent des incidents mais ne notifient personne tant que vous n'ajoutez pas de
canal. Voir [Règles prédéfinies](/fr/alerts/presets).

Sur un incident de sécurité, un Wolf Manager peut approuver une réponse : bloquer une IP sur
l'hôte, désactiver un utilisateur, fermer ses sessions ou révoquer ses clés API. Rien ne
s'exécute sans cette approbation. Voir [Actions de réponse](/fr/agent/response-actions).
