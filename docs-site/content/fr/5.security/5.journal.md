## Journal infalsifiable

Wolf enregistre les modifications liées à la sécurité dans **Wolf Journal Entry** et les chaîne
avec un HMAC. Modifier, supprimer ou réordonner une entrée casse la chaîne.

### Ce qui est enregistré

Chaque entrée est écrite dans la même transaction que la modification :

- les événements de sécurité (leur payload, sous forme d'empreinte SHA-256) ;
- les décisions sur les incidents : statut, responsable, fusion, les champs NIS2, DORA et RGPD,
  résolution automatique et réouverture ;
- les actions de réponse et leurs résultats ;
- les commentaires sur les incidents ;
- les modifications des Wolf Settings : les noms des champs modifiés et l'auteur de la
  modification, jamais les valeurs.

Les entrées sont en lecture seule dans Frappe : les modifications et suppressions sont refusées.

### Mode de signature

Chaque minute, la tâche `chain_journal` signe les entrées en attente dans l'ordre de création,
sous un verrou :

```text
mac = HMAC-SHA256(key, seq|at|kind|record|digest|prev_mac)
```

Une entrée attend au plus une minute avant d'être signée.

La clé est `wolf_journal_key` dans la configuration du site. Wolf la crée à la première utilisation
et ne la stocke jamais dans la base de données : quelqu'un qui ne peut qu'écrire dans la base ne
peut donc pas forger une chaîne.

::warning
Sauvegardez `wolf_journal_key` avec la configuration du site. Sans elle, la chaîne ne peut pas être
vérifiée.
::

### Vérifier le journal

```bash
bench --site wolf.example.com wolf-verify-journal
bench --site wolf.example.com wolf-verify-journal --anchor <seq>:<mac>
```

Ou cliquez sur **Vérifier** dans **Wolf → Sécurité**. Les deux recalculent chaque empreinte et chaque
mac, et repèrent une entrée modifiée, supprimée ou réordonnée.

Supprimer les entrées les plus récentes laisse une chaîne valide, mais plus courte. Pour le
détecter, conservez une **ancre** :

::steps{level="4"}
#### Copier l'ancre

**Wolf → Sécurité** affiche le `seq:mac` le plus récent. **Copier** le place dans le presse-papiers.

#### La stocker là où Wolf ne peut pas écrire

Un ticket, un gestionnaire de mots de passe, un autre serveur.

#### Vérifier par rapport à elle

Lancez `wolf-verify-journal --anchor seq:mac`. Une chaîne coupée avant cette entrée échoue.
::

::tip
L'[export SIEM](/fr/security/siem-export) peut envoyer chaque entrée du journal (seq, empreinte,
mac) à votre collecteur. Cette copie externe est la meilleure ancre.
::

### Conservation

**Wolf Settings → Conservation du journal (jours)** (par défaut `0` : conservé indéfiniment). Avec une valeur
définie, la tâche nocturne `purge_journal` supprime les entrées signées plus anciennes que cette
durée, en tant que partie la plus ancienne de la chaîne :

- elle écrit et signe d'abord une entrée `journal_purge` qui enregistre où la purge s'est arrêtée
  (`through_seq` et son mac), puis supprime, sous le verrou de signature ;
- elle conserve toujours l'entrée la plus récente, et ne supprime jamais une entrée que l'export
  SIEM n'a pas encore envoyée (quand l'export envoie le journal) ;
- la vérification exige alors qu'un journal qui ne commence pas à l'entrée 1 commence juste après
  la coupure de l'enregistrement de purge le plus récent. Supprimer davantage d'entrées anciennes,
  ou en supprimer sans purge, la fait échouer ;
- une ancre située dans la partie purgée est signalée comme purgée : copiez-en une plus récente. La
  coupure elle-même se vérifie toujours, puisque l'enregistrement de purge conserve son mac.

## Leurres (honeytokens)

**Wolf Settings → Renseignement sur les menaces et leurres**. Aucune personne légitime ne connaît un
leurre : un seul contact déclenche donc un événement `honeytoken_triggered` critical. La règle
prédéfinie *Honeytoken touched* alerte dessus. Chaque leurre déclenche au plus un événement par
adresse toutes les 10 minutes.

| Paramètre | Un par ligne | Déclenche un événement quand | ATT&CK |
|---|---|---|---|
| **Utilisateurs leurres** | l'e-mail d'un compte que personne n'utilise | toute tentative de connexion sur ce compte, échouée ou non (Activity Log) | T1078, T1110 |
| **Clés d'API leurres** | une clé API, par exemple laissée dans une vieille sauvegarde ou un dépôt | toute requête dont l'en-tête `Authorization` (`token key:secret` ou Basic) la contient | T1552 |
| **Chemins leurres** | un chemin lié depuis nulle part, comme `/app/backup-admin` | toute requête vers ce chemin | T1083 |

La vérification des clés API leurres a lieu avant que Frappe ne rejette la clé inconnue, et valide
l'événement immédiatement.

::caution
Ne créez pas de clé API leurre sur un utilisateur réel. La clé n'a besoin de figurer que dans le
paramètre.
::

## Listes de réputation d'IP

**Wolf Settings → Utiliser des listes de réputation IP** (désactivé par défaut).

- Une fois par jour, la tâche `refresh_reputation` télécharge les listes indiquées dans **Listes de réputation IP**
  dans `private/wolf/ip_reputation.json`.
- Chaque ligne de **Listes de réputation IP** est un nom, suivi d'une URL ou d'un chemin de fichier
  relatif au site. Chaque liste contient une adresse ou un CIDR par ligne. Prérempli :

  ```text
  firehol_level1 https://iplists.firehol.org/files/firehol_level1.netset
  spamhaus_drop https://www.spamhaus.org/drop/drop.txt
  ```

- À l'ingestion, un événement de sécurité dont l'`ip` du payload figure sur une liste reçoit
  `reputation: {listed, lists}` et un cran de gravité supplémentaire.
- Les recherches ne quittent jamais le site : seules les listes sont téléchargées. Une liste dont le
  téléchargement échoue conserve sa dernière copie.

::warning
Vérifiez les conditions d'utilisation de chaque liste avant de l'activer.
::

Le format CEF de l'[export SIEM](/fr/security/siem-export) indique dans `cs5` les listes sur
lesquelles figure une IP.

Wolf peut aussi lire les décisions d'une Local API CrowdSec (**Wolf Settings → CrowdSec**, désactivé
par défaut). Les événements dont l'IP fait l'objet d'une décision CrowdSec sont étiquetés et
relevés d'un cran de la même façon. Voir [Actions de réponse](/fr/agent/response-actions).
