Le site qui exécute Dodock Wolf enregistre ses propres signaux à partir des documents et des
requêtes de Frappe. Aucun agent n'est nécessaire. Chaque signal a un interrupteur dans
**Wolf Settings**, et tous sont activés par défaut.

Ces signaux ne sont visibles que depuis l'intérieur d'un site. Pour les obtenir sur les autres
sites d'un bench, installez le Wolf App sur chacun d'eux en mode satellite : il capte les mêmes
signaux, avec les mêmes interrupteurs, et les transmet au site central. Voir
[Tous les sites d'un bench](/fr/install/every-site).

## Connexions et rôles

**Wolf Settings → Local signals (this site)** (signaux locaux de ce site) :

| Paramètre | Catégorie | Ce qu'il enregistre | Gravité | Règle prédéfinie |
|---|---|---|---|---|
| **Capture failed logins** | `frappe_failed_login` | une connexion au Desk échouée (Activity Log), avec l'utilisateur et l'IP | warning | *Repeated failed Frappe logins* : 5 ou plus en 10 min, par site |
| **Flag privileged logins from new IPs** | `new_admin_ip` | un utilisateur privilégié se connecte depuis une IP dont aucune de ses connexions précédentes n'est venue | warning | *Admin login from new IP* |
| **Flag privileged logins from new countries** | `admin_login_new_country` | une connexion privilégiée depuis un pays dont aucune des connexions précédentes de l'utilisateur n'est venue. Nécessite une [base GeoIP](#base-geoip) | critical | *Admin login from new country* |
| **Flag users granted privileged roles** | `privileged_user` | un utilisateur actif reçoit un rôle privilégié | critical pour System Manager ou Administrator, sinon warning | *Privileged role granted* |

**Privileged Roles** liste les rôles considérés comme privilégiés, un par ligne. Par défaut :
`System Manager`, `Administrator`, `Wolf Manager`.

La même section contient les signaux locaux hors sécurité : **Capture failed Scheduled Job Logs**
(`cron_failure`) et **Capture Error Logs** (les sauvegardes échouées en `backup_failed`).
**Watch the Email Queue** enregistre les retards de l'Email Queue et les erreurs d'envoi.

## Modifications applicatives risquées

**Wolf Settings → Flag risky application changes** (activé par défaut) couvre :

| Catégorie | Ce qui la déclenche | ATT&CK | Règle prédéfinie |
|---|---|---|---|
| `server_script_change` | un Server Script créé, activé, ou dont le code, le type ou le déclencheur change | T1059.006 | *Server Script can run new code* (l'événement est critical pour les scripts API et planifiés ou l'accès invité) |
| `client_script_change` | la même chose pour un Client Script | T1059.007 | *Client Script can run new code* |
| `console_execution` | chaque exécution de la System Console (Python ou SQL) | T1059.006 | *System Console used* |
| `permission_change` | voir [Dérive des permissions](#derive-des-permissions) | T1098 | *Permission rules changed* |
| `security_settings_weakened` | voir [Paramètres affaiblis](#parametres-affaiblis) | T1562.001 | *Security settings weakened* (critical) |
| `api_key_generated` | un nouveau secret d'API écrit pour un utilisateur | T1098.001 | *API key generated* (l'événement est critical pour les utilisateurs privilégiés) |
| `api_key_new_ip` | voir [Clé API utilisée depuis une nouvelle IP](#cle-api-utilisee-depuis-une-nouvelle-ip) | T1078, T1552 | *API key used from a new IP* |
| `webhook_external` | un Webhook créé, activé ou pointé vers un autre hôte | T1567 | *Webhook to a new host* |

Modifier la description d'un script ou désactiver un script ne déclenche rien.

::caution
Les événements de script conservent les 300 premiers caractères du code. Un script qui contient un
secret en place une partie dans l'événement.
::

### Dérive des permissions

Tous ces cas sont des événements `permission_change` :

- **Role Permission Manager** : ajout, mise à jour, suppression et réinitialisation. Les anciennes
  versions de Frappe écrivent `update`, `remove` et `reset` en SQL brut, Wolf les lit donc dans la
  requête.
- **Custom DocPerm** enregistré ou supprimé partout ailleurs : Data Import, l'API REST, le code
  (`payload.kind` vaut `custom_docperm`, `via` indique par quel moyen). Chaque événement liste les
  droits accordés et retirés. Une nouvelle règle est comparée à la règle standard du DocType, si
  bien que les copies que Frappe crée avant la première modification personnalisée n'accordent
  rien. Un droit donné à `Guest` ou `All` est critical.
- **User Permission** qui permet à son utilisateur de voir davantage (`user_permission`). La
  première User Permission d'un utilisateur pour un DocType ne fait que restreindre et ne
  déclenche rien. Une valeur supplémentaire, une modification qui autorise une autre valeur, un
  autre utilisateur ou un autre DocType, ou la suppression de la dernière (qui lève la
  restriction) déclenche un événement.
- **Accès au Desk** : un utilisateur Website (client, portail fournisseur) qui reçoit un rôle Desk,
  ce qui en fait un System User (`desk_access`).
- **Role Profile** créé ou accordant davantage de rôles.

### Paramètres affaiblis

Un enregistrement des System Settings déclenche `security_settings_weakened` (critical) quand il :

- désactive l'authentification à deux facteurs, la politique de mots de passe, la session unique
  par utilisateur, la connexion SSO uniquement ou la déconnexion lors de la réinitialisation du mot
  de passe ;
- abaisse le score minimal des mots de passe ou la durée de verrouillage ;
- autorise davantage de connexions échouées, ou supprime le verrouillage ;
- allonge les sessions ;
- permet aux invités de téléverser des fichiers.

### Clé API utilisée depuis une nouvelle IP

Chaque requête réussie authentifiée par une clé API (`Authorization: token key:secret` ou
`Basic`) enregistre l'adresse de la clé dans **Wolf API Key IP**.

- La première adresse de la clé, et toute adresse vue pendant ses 24 premières heures, forment sa
  référence.
- Ensuite, une adresse hors de tout /24 (IPv4) ou /64 (IPv6) connu déclenche `api_key_new_ip`,
  critical pour les utilisateurs privilégiés. Une nouvelle adresse dans un réseau connu est
  enregistrée sans bruit.
- Les adresses inutilisées depuis un an sont oubliées. Supprimer une ligne oublie une adresse.
- Les réponses proposées sont la révocation des clés API de l'utilisateur et le blocage de
  l'adresse.

### Limites

- Les modifications faites en SQL brut (un patch, `bench mariadb`) ne déclenchent aucun événement
  de document et ne sont pas vues. Les patchs et migrations sont ignorés volontairement.
- Une User Permission restreinte à un DocType (`applicable_for`) est comptée avec les autres
  permissions de l'utilisateur pour le même DocType autorisé.

## Exports de données inhabituels

**Wolf Settings → Flag unusual data exports** (activé par défaut) déclenche `data_exfiltration`
(T1567, T1030). Règle prédéfinie : *Unusual data export*.

- **Ce qui compte** : les exports de rapports, Data Export, les modèles Data Import avec
  enregistrements, les PDF en masse, et toute lecture de liste (`frappe.client.get_list`, les vues
  liste et rapport, `/api/resource/<DocType>`), quelle que soit la taille de page. Un script qui
  parcourt une table page par page s'additionne comme une grosse lecture.
- **Comment** : la taille de la réponse de chaque requête s'ajoute au total de l'utilisateur pour
  l'heure d'horloge. Chaque heure, les totaux deviennent des échantillons `user_export_bytes`, une
  série par utilisateur (`labels.user`).
- **Quand** : au-delà de **Export Floor (MB per hour)** (par défaut `50`), l'heure est comparée à
  la plus grosse heure de l'utilisateur sur les 14 derniers jours. Warning à **Export Factor**
  (par défaut `5`) fois cette heure, critical à 20 fois. Un utilisateur sans historique est
  critical, sauf tant que le site lui-même a moins de 14 jours d'historique : c'est alors un
  warning.
- **À quelle fréquence** : au plus un événement par utilisateur, heure et gravité, si bien qu'un
  warning peut être suivi d'un critical. Le payload contient les octets, requêtes et lignes de
  l'heure, la référence, le ratio, la dernière requête et l'IP.

::note
La série `user_export_bytes` nomme les utilisateurs. Toute personne autorisée à lire les métriques
du site dans Wolf voit combien chaque utilisateur a sorti par heure.
::

Ne sont pas comptés : les fichiers envoyés tels quels (fichiers privés, sauvegardes), l'impression
d'un seul document, et le fichier d'un export de liste en arrière-plan (sa requête est comptée).
Un export réparti sur deux heures d'horloge est coupé en deux. Les satellites conservent les
échantillons bruts 2 jours, leur référence couvre donc 2 jours, et non 14.

## Base GeoIP

*Admin login from new country* nécessite une base GeoIP hors ligne sur le serveur. Wolf n'appelle
jamais de service de géolocalisation en ligne.

::steps{level="3"}
### Télécharger une base

Les deux formats conviennent :

- un fichier `.mmdb` au format MaxMind : GeoLite2-Country ou GeoLite2-City (compte MaxMind
  gratuit), DB-IP « IP to Country Lite » (`dbip-country-lite-*.mmdb`, CC BY 4.0) ou IPinfo Lite.
  Wolf le lit avec son propre lecteur, aucun paquet Python supplémentaire n'est donc nécessaire ;
- un CSV de plages, une par ligne : `start_ip,end_ip,CC` (CSV « country lite » de DB-IP ou
  d'IPinfo), entiers `start,end,CC,...` (IP2Location LITE DB1) ou `network/prefix,CC`. Les lignes
  d'en-tête sont ignorées.

### Définir le chemin

Renseignez dans **Wolf Settings → GeoIP Database** le chemin du fichier. Un chemin relatif est lu
depuis le répertoire du site, par exemple `private/files/dbip-country.mmdb`.

### La tenir à jour

Actualisez le fichier chaque mois. Wolf le recharge quand il change.
::

Les adresses privées et de boucle locale n'ont pas de pays. Un utilisateur dont toutes les
connexions précédentes venaient de telles adresses n'a pas encore de référence : rien n'est
signalé tant qu'une première connexion publique n'est pas connue.

## Désactiver un signal

Décochez son interrupteur dans **Wolf Settings**. Sur un satellite, les mêmes interrupteurs
s'appliquent aux signaux qu'il transmet.
