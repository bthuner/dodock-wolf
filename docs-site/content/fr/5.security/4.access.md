## Rôles

L'installation du Wolf App crée deux rôles.

| Rôle | Peut |
|---|---|
| **Wolf Manager** | tout voir et tout configurer, approuver les actions de réponse, modifier les lignes Wolf User Scope |
| **Wolf User** | lecture seule. Peut commenter les incidents. Peut être limité avec Wolf User Scope |

System Manager a les mêmes droits que Wolf Manager. La Wolf UI, à `/wolf`, répond 403 aux
utilisateurs qui n'ont ni le rôle Wolf User ni le rôle Wolf Manager.

## Wolf User Scope

Par défaut, un Wolf User voit tous les sites, benches et hôtes. Pour en limiter un, ajoutez des
lignes **Wolf User Scope** à `/app/wolf-user-scope` (Wolf Managers uniquement). Une ligne par
autorisation :

| Champ | Valeur |
|---|---|
| User | le Wolf User |
| Scope | `site`, `bench` ou `host` |
| Value | le nom tel qu'il apparaît sur les Wolf Events |

Par exemple :

| User | Scope | Value |
|---|---|---|
| jane@client.com | site | erp.client.com |
| jane@client.com | site | shop.client.com |
| ops-team@dokos.io | host | bench-02 |

Un utilisateur restreint ne voit alors que les Wolf Events, Metric Samples et Rollups, Incidents,
Silences et Agents dont le site, le bench ou l'hôte correspond à l'une de ses lignes. Cela
s'applique aux vues liste, aux rapports, aux formulaires, aux recherches de liens, à la page Wolf
Overview, aux graphiques et aux chronologies d'incidents.

- Les lignes se combinent par OU.
- Les enregistrements qui concernent tout un hôte (CPU, disque, connexions SSH : pas de site)
  nécessitent une ligne `host`.
- Un Wolf User sans aucune ligne n'est pas restreint.
- Les définitions des règles d'alerte restent lisibles par tous les Wolf Users.

::note
Les User Permissions de Frappe ne permettent pas cela, car site, bench et hôte sont de simples
champs Data. Wolf utilise à la place les hooks `permission_query_conditions` et `has_permission`.
::

## Secrets des agents

Chaque Wolf Agent s'authentifie avec un identifiant d'agent et un secret.

- Wolf ne stocke qu'une empreinte HMAC-SHA256 salée du secret.
- Le secret est affiché une seule fois : à l'enregistrement, ou quand vous cliquez sur
  **Rotate secret** dans le formulaire Wolf Agent.
- Personne ne peut le relire depuis le site. Pour déplacer un agent ou récupérer une configuration
  perdue, faites tourner le secret ou enregistrez à nouveau l'hôte.

Les agents enregistrés avant l'introduction du hachage continuent de fonctionner : `bench migrate`
hache leur secret stocké et supprime la copie chiffrée.

Un site satellite conserve son propre secret chiffré dans ses Wolf Settings, puisqu'il doit
l'envoyer. Le site central ne stocke que l'empreinte.

**Wolf Settings → Registration Token** est le secret partagé que `wolf-agent register --token` doit
présenter. Laissez-le vide pour refuser les nouveaux enregistrements. Pour ne plus accepter les
événements d'un agent, désactivez son **Wolf Agent**.

## Limite de débit des envois

Chaque agent, satellites compris, peut envoyer au plus **Wolf Settings → Max Pushes Per Minute**
fois par minute (par défaut `120`, `0` désactive la limite). Les envois excédentaires reçoivent
un HTTP 429. L'agent les garde dans sa file locale (spool) et réessaie avec un délai croissant.

Le point d'accès de l'intégration Wazuh a sa propre limite de 600 appels par minute, car Wazuh
envoie un appel par alerte. Voir [Wazuh et Suricata](/fr/security/wazuh-suricata#route-dintégration-wazuh).

Détails du protocole : [Protocole](/fr/reference/protocol).

## Nettoyage (scrubbing)

L'agent retire des événements les adresses e-mail, identifiants, numéros de carte et IBAN avant
qu'ils ne quittent l'hôte. Les adresses IP sont conservées par défaut, car les règles de sécurité
regroupent par IP. Voir [Nettoyage (scrubbing)](/fr/agent/scrubbing).
