[Pilot](https://github.com/frappe/pilot) est le gestionnaire de serveurs de **Frappe** (« Frappe Server Manager »). Ce n'est pas un outil Dokos : le groupe GitLab public de Dokos ne contient aucun dépôt Pilot. La documentation Dokos ne mentionne Pilot qu'à travers les clés de site `pilot_endpoint` / `pilot_auth_token`, utilisées par le panneau Cloud Settings pour les sites Frappe Cloud v2. Ce sont les mêmes clés que Pilot écrit dans `site_config.json`.

## Installation

Installez l'agent comme sur n'importe quel hôte ([Wolf Agent](/fr/install/wolf-agent)). Les benches Pilot sont trouvés sans aucune étape supplémentaire.

::steps{level="3"}
### Laisser la découverte opérer

La découverte parcourt `/home/*/pilot/benches/*`, en plus des emplacements habituels des benches. Un `bench.toml` avec `[bench] name` et `python` signale un bench Pilot, et Wolf le lit avec les vraies clés de Pilot.

### Vérifier ce que Wolf trouve

```bash
wolf-agent discover
```

`discover` affiche ce que trouve la découverte des benches.

### Vérifier ce qui serait envoyé

```bash
wolf-agent check
```

`check` collecte une fois et affiche la charge utile JSON. Rien n'est envoyé. Voir [Commandes](/fr/agent/commands).
::

::warning
Les noms des logs des workers sont résolus par glob à l'enregistrement. Relancez `wolf-agent register` après avoir modifié `[[workers]]` dans `bench.toml`.
::

### Configuration

Les événements de déploiement issus des tâches Pilot sont activés par défaut. La section `pilot` de `/etc/wolf-agent/config.json` :

```json [config.json]
{
  "pilot": {
    "deployments": true,
    "api_url": null,
    "token": null,
    "jwt_secret": null
  }
}
```

::field-group
  :::field{name="pilot.deployments" type="boolean"}
  Interroge régulièrement les tâches Pilot et les transforme en événements. `false` désactive cette interrogation. Par défaut `true`.
  :::
  :::field{name="pilot.api_url" type="string | null"}
  Remplace l'adresse de l'Admin API propre à chaque bench, `http://127.0.0.1:<admin.port+1>`. Elle s'applique à tous les benches Pilot de l'hôte : ne la définissez que sur les hôtes à un seul bench.
  :::
  :::field{name="pilot.token" type="string | null"}
  Un jeton de l'Admin API limité au bench. S'il est défini, Wolf l'utilise tel quel.
  :::
  :::field{name="pilot.jwt_secret" type="string | null"}
  Le `[admin] jwt_secret` du bench. Wolf en tire son propre jeton valable une heure.
  :::
::

`token` ou `jwt_secret` est nécessaire, sauf si l'utilisateur `wolf-agent` peut lire `bench.toml`. Les modes que Pilot donne à `bench.toml` n'ont pas été vérifiés. Le fichier de configuration de l'agent est écrit avec le mode 0600.

La configuration complète est décrite dans [Configuration](/fr/agent/configuration).

::caution
`jwt_secret` signe les sessions de l'Admin de Pilot. Quiconque le détient peut émettre des jetons limités au bench. Wolf ne lit `[admin] jwt_secret` dans `bench.toml` qu'à l'exécution et ne l'écrit jamais dans la configuration de Wolf.
::

## Ce que fait Wolf sur un bench Pilot

| Domaine | Ce que fait Wolf | État |
|---|---|---|
| Découverte | Parcourt `/home/*/pilot/benches/*` en plus des anciens globs. Un `bench.toml` avec `[bench] name` et `python` est traité comme un bench Pilot et lu avec ses vraies clés | fait, testé unitairement |
| Sites | Lit `sites/*/site_config.json`, ainsi que `domains` (chaînes simples ou `{"domain": …, "route": …}`) pour la correspondance hôte → site | fait, testé unitairement |
| Logs des processus | Suit `web`, `schedule`, `worker_<queues>_<i>` et leurs fichiers stderr, pour le nommage systemd comme pour celui de supervisor | fait, testé unitairement |
| nginx | Suit `<bench>/logs/nginx-access.log`, au format `pilot_access` | fait, testé unitairement |
| File d'attente Redis | Lit `queue_length`, les registres RQ failed/started, les workers actifs et la mémoire/les évictions Redis depuis `redis://127.0.0.1:<[redis] queue_port>`. `redis_queue` dans `common_site_config.json` est prioritaire quand il est présent | fait |
| Sauvegardes, TLS, MariaDB | Comme sur n'importe quel bench : `sites/<site>/private/backups/`, chaque site et chaque entrée `domains`, les identifiants de base de données du site | fait (générique) |
| Processus | `supervisorctl status`, sinon les unités systemd dont le nom contient le nom du bench (`bench_processes_down`). Si les noms d'unités ou de programmes de Pilot ne contiennent pas le `[bench] name`, rien n'est signalé | non vérifié |
| Déploiements | Un événement `deployment` (catégorie `pilot`) quand une tâche de mise à jour, de migration, de changement de branche, d'installation d'application, de build, de redémarrage ou de restauration **démarre**, et un événement `error` (`pilot_task_failed`) quand l'une d'elles échoue. Lu depuis l'Admin API, ou depuis les fichiers de tâches | fait, testé unitairement |
| Interrupteur « Enable Wolf for this bench » dans Pilot | Demande une modification de frappe/pilot | **non fait** |
| Vrai hôte Pilot | **Pas encore testé** | — |

Les métriques elles-mêmes sont décrites dans [Ce qui est collecté](/fr/agent/collected).

## Organisation du bench

### Benches

Le `install.sh` de Pilot installe dans `$HOME/pilot`. Les benches se trouvent par défaut dans `~/pilot/benches/<name>/`. Sur un VPS où seul root existe, l'installateur crée un utilisateur de bench non root, d'où le glob `/home/*/pilot/benches/*`.

Chaque bench contient `apps/`, `sites/`, `env/`, `logs/`, `config/`, `pids/` et `bench.toml`.

### bench.toml

Wolf lit ces clés :

| Clé | Usage |
|---|---|
| `[bench] name` | Obligatoire, avec `python`. Le nom du bench et le marqueur Pilot |
| `[redis] queue_port` | Port du Redis de la file d'attente. Par défaut `11000` |
| `[admin] port` | Par défaut `7000`. Le backend Admin écoute sur `127.0.0.1:<port + 1>` |
| `[admin] jwt_secret` | Lu uniquement à l'exécution, jamais écrit dans la configuration de Wolf |
| `[production] enabled` | Conservé pour information |

`bench.toml` n'a **aucune** clé nginx ni de logs : « Nginx uses compiled-in defaults; it has no `[nginx]` table ». `[monitor]` ne nomme que le log de métriques propre à Pilot. Un `bench.toml` qui n'est pas celui de Pilot (sans `[bench] python`) passe toujours par l'ancien parseur défensif.

### Logs des processus

Les logs des processus vont dans `<bench>/logs/` :

- `web.log`
- `worker_<queue-slug>_<i>.log`. Le slug est la liste des files d'attente, où chaque suite de caractères non alphanumériques est remplacée par `_`.
- `schedule.log`

stderr va dans `<log>.error.log` sous systemd (par exemple `web.log.error.log`) et dans `<name>.error.log` sous supervisor. Wolf suit les deux graphies. Les fichiers absents ne coûtent rien.

Les fichiers `frappe.web.log`, `scheduler.log` et `worker.log` de Frappe sont suivis comme sur tous les benches.

### nginx

Le vhost de chaque site journalise `location /` dans `<bench>/logs/nginx-access.log`, avec ce format :

```nginx
log_format pilot_access '$pilot_client_addr [$time_local] "$request_method $uri" $status "$host" $request_time';
```

Ce n'est pas le format combined : il n'a ni ident ni utilisateur, ni nombre d'octets, ni protocole. Le parseur nginx de Wolf l'accepte. Le lecteur de logs d'accès de Pilot utilise la même structure. `$host` est le site ou l'un de ses `domains`.

### Tâches

Les opérations longues sont des tâches, stockées sous la forme `<bench>/tasks/<YYYYMMDD-HHMMSS-hex>/` :

- `meta.json` : `task_id`, `command`, `args`, `queued_at`, `started_at`, `finished_at` (UTC ISO-8601), `exit_code`, `failure`.
- `status` : `queued`, `running`, `success`, `failed` ou `killed`.

Les répertoires sont créés avec le mode `0700` : seul l'utilisateur du bench peut les lire.

## Événements de déploiement issus des tâches Pilot

Wolf signale ces commandes de tâche :

`update`, `retry-update`, `complete-migration`, `migrate`, `revert-migration`, `revert-apps`, `revert-site`, `switch-branch`, `get-and-install-app`, `install-app`, `uninstall-app`, `remove-app`, `build`, `restart-services`, `switch-lite-mode`, `setup-nginx`, `restore-site`, `reinstall-site`.

Le site provient des arguments `site` / `sites` de la tâche. Le bench est le bench Pilot lui-même, puisque les tâches sont propres à chaque bench.

### Sources des tâches

Wolf essaie deux sources, dans cet ordre.

1. **Admin API** : `GET http://127.0.0.1:<admin.port+1>/api/v1/tasks?limit=100`. Elle renvoie des lignes `TaskInfo.as_dict()`. Le point d'accès exige une session **limitée au bench** : `Authorization: Bearer <JWT>`. Pilot signe ces jetons localement en HS256 sur `{"sub": "admin", "iat", "exp", "scope": "bench", "jti"}` avec `[admin] jwt_secret`, et les vérifie avec `require: ["exp"]`. Wolf utilise `pilot.token` si vous en définissez un. Sinon, il émet un jeton valable une heure avec la même structure de claims, à partir de `pilot.jwt_secret` ou de `bench.toml` quand Wolf peut le lire. Chaque jeton émis porte un jti `wolf-…`, si bien qu'il apparaît dans les sessions actives de Pilot et peut être révoqué.
2. **Fichiers de tâches** : `<bench>/tasks/*/meta.json` et `status`. Cela ne fonctionne que si le Wolf Agent tourne sous l'utilisateur du bench, à cause du mode `0700`.

### Production des événements

Les deux sources suivent les mêmes règles que sur les [serveurs Press](/fr/install/press).

- Un événement `deployment` est envoyé au démarrage de la tâche, horodaté à `started_at`. Un incident qui survient pendant une longue migration s'y rattache, par exemple via la [règle prédéfinie](/fr/alerts/presets) « 502 spike after deployment ».
- Un événement `error` est envoyé si la tâche se termine en `failed`. Il porte `failure.code`, `failure.message` et `exit_code`.
- Les identifiants des tâches signalées sont conservés 3 jours dans `<spool_dir>/pilot-tasks.json`.
- La première interrogation ignore l'historique et ne prend en compte que les tâches en file ou en cours.

Cela remplace les marqueurs manuels `wolf-agent mark-deployment --source pilot` sur les benches Pilot. Les champs des événements sont décrits dans le [protocole](/fr/reference/protocol).

## Wolf aux côtés du monitoring de Pilot

D'après la documentation de Pilot :

- `pilot-monitor.service` collecte les métriques de l'hôte, de la base de données et du bench toutes les 10 s et interroge les sites de production toutes les 5 s. Ses logs vont dans `system/logs/`.
- `[resource_limits]` déclenche des alertes de CPU, de mémoire, de disque et de disponibilité au bout de 5 minutes. Elles partent vers Central (sur les hôtes gérés par Central), vers `webhook_endpoints` (POST avec un en-tête Bearer) et par e-mail.
- `[telemetry]` envoie les métriques et les logs (Fluent Bit suit `benches/*/logs/*.log`) vers le point d'accès « Datum » d'une région, avec un jeton délivré par Central.

Wolf lit les mêmes fichiers locaux et n'interfère avec aucun de ces éléments. Ce qu'il ajoute sur un hôte Pilot auto-hébergé :

- Les tracebacks, les tâches planifiées en échec et les plantages de workers, sous forme d'événements.
- Les 5xx/502 par site.
- Les signaux SSH.
- Des incidents rattachés à la tâche Pilot qui les a précédés.

Tout cela reste sur votre propre site Wolf.

::note
Les alertes de ressources de Pilot pourraient être dirigées vers Wolf via `webhook_endpoints`, mais leur charge utile n'est pas documentée, donc Wolf ne les accepte pas encore.
::

## Limites et points non vérifiés

### Ce dont Pilot aurait besoin

Ces éléments de l'issue #17 demandent des modifications ou des réponses de la part des mainteneurs de Pilot :

1. **Interrupteur « Enable Wolf for this bench ».** Une table `[wolf]` dans `bench.toml` (`enabled`, `url`) et un réglage dans l'Admin, qui installerait et enregistrerait l'agent avec les chemins du bench. Cela relève de frappe/pilot, et rien de tel n'y existe aujourd'hui.
2. **Un jeton machine pour l'Admin API.** Aujourd'hui, une session limitée au bench est soit une session par mot de passe de 24 h, soit un JWT signé avec `jwt_secret` ou émis par le JWKS configuré. Un jeton `tasks:read` en lecture seule et de longue durée éviterait de partager `jwt_secret` avec Wolf.
3. **Un flux d'événements de tâches** (webhook ou SSE couvrant toutes les tâches) au lieu d'interroger `/tasks`.
4. **Les modes des fichiers.** La confirmation que `bench.toml` et `logs/` restent lisibles par un groupe de monitoring, puisque les tâches sont en `0700` par conception.

### Points non vérifiés

Ces points proviennent de la lecture des sources et de tests unitaires sur des jeux de données construits à partir d'elles. Rien n'a été exécuté sur un hôte Pilot réel. En particulier, ceci n'a pas été testé :

- Le jeton émis face à un vrai backend Admin.
- `/api/v1/tasks` à travers les limites de débit de Pilot.
- Les permissions des fichiers pour un utilisateur autre que celui du bench, y compris les modes que Pilot donne à `bench.toml`.
- La graphie exacte du slug des files d'attente des workers sur un bench en fonctionnement.
- Les noms exacts des unités systemd et des programmes supervisor de Pilot, dont dépendent les vérifications de processus.
