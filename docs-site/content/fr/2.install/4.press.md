[Press](https://github.com/frappe/press) est l'application Frappe qui fait tourner Frappe Cloud. Elle gère les serveurs via l'**agent Press** ([frappe/agent](https://github.com/frappe/agent)), un service Flask + RQ présent sur chaque serveur. Cette page traite du Wolf Agent sur un *serveur d'applications* géré de cette façon.

::note
Cette page concerne les déploiements **Press auto-hébergés**, où vous avez la main sur le serveur. Les serveurs hébergés par Frappe Cloud ne sont pas ouverts aux clients.
::

Tout ce qui figure sur cette page a été vérifié sur un serveur d'applications Press installé par **les propres rôles Ansible de Press** (frappe/press [`7ce25f2`](https://github.com/frappe/press/tree/7ce25f221378cb4558cd3993f3283d75cc8fe7d7), frappe/agent [`6bbd199`](https://github.com/frappe/agent/tree/6bbd199c13e90f48950e2a06401ca98738455aaf), novembre 2026), avec des benches et des sites créés par l'API de l'agent Press comme Press les crée, et de vrais déploiements : New Bench, Update Site Migrate, Bench Restart, Archive Bench et des jobs en échec. Le dossier [`dev/press`](https://github.com/bthuner/dodock-wolf/tree/main/dev/press) du dépôt installe ce même serveur dans un conteneur.

::tip
Pas de serveur Press sous la main ? `dev/press` ci-dessus, ou la [démo Press](/fr/reference/development), qui en simule un pour le Wolf Agent.
::

## Installation

Installez l'agent comme sur n'importe quel hôte ([Wolf Agent](/fr/install/wolf-agent)). Le mode Press ne demande aucune étape supplémentaire ni aucun identifiant Press : tout est lu dans des fichiers locaux.

::steps{level="3"}
### Laisser la détection opérer

L'agent passe en mode Press quand `/home/frappe/agent/config.json` existe et contient une clé `benches_directory`. L'utilisateur du démon ne peut pas lire ce fichier (mode `0600`) : il suffit alors que ce fichier et `jobs.sqlite3` soient présents. L'enregistrement s'exécute en root et enregistre aussi `"platform": "press"` et le dossier des benches dans la configuration de Wolf. En mode Press, la liste `benches` de la configuration est rafraîchie depuis le disque au démarrage et à chaque nouvelle découverte.

### Vérifier ce que Wolf trouve

```bash
wolf-agent discover --platform press
```

`discover` affiche ce que trouve la découverte des benches. `wolf-agent register --platform press` enregistre l'arborescence Press dans la configuration.

### Vérifier ce qui serait envoyé

```bash
wolf-agent check --platform press
```

`check` collecte une fois et affiche la charge utile JSON. Rien n'est envoyé. Voir [Commandes](/fr/agent/commands).
::

### Configuration

Le mode Press est détecté automatiquement. Pour le forcer, ou pour changer les chemins, modifiez `/etc/wolf-agent/config.json` :

```json [config.json]
{
  "platform": "press",
  "press": {
    "agent_dir": "/home/frappe/agent",
    "nginx_access_log": "/var/log/nginx/access.log",
    "rediscover_interval": 60,
    "deployments": true
  }
}
```

::field-group
  :::field{name="platform" type="string | null"}
  `null` détecte Press automatiquement, `"press"` le force, `"generic"` désactive la prise en charge de Press.
  :::
  :::field{name="press.agent_dir" type="string"}
  Répertoire de l'agent Press. Par défaut `/home/frappe/agent`.
  :::
  :::field{name="press.benches_directory" type="string | null"}
  Le `benches_directory` de l'agent Press, enregistré par l'enregistrement, qui le lit en root. Utilisé quand le démon ne peut pas lire la configuration de l'agent Press. Par défaut `/home/frappe/benches`.
  :::
  :::field{name="press.nginx_access_log" type="string"}
  Log d'accès nginx partagé. Par défaut `/var/log/nginx/access.log`.
  :::
  :::field{name="press.rediscover_interval" type="number"}
  Secondes entre deux nouvelles analyses des benches. Par défaut `60`.
  :::
  :::field{name="press.deployments" type="boolean"}
  Transforme les jobs de l'agent Press en événements `deployment`. Par défaut `true`.
  :::
  :::field{name="backups.press" type="boolean"}
  Vérification de l'âge des sauvegardes sur les benches Press. Par défaut `false`.
  :::
::

La configuration complète est décrite dans [Configuration](/fr/agent/configuration).

### Permissions

`install.sh` ajoute l'utilisateur `wolf-agent` aux groupes `frappe` et `adm`. Sur un serveur installé par les rôles de Press, cela lui donne :

| Fichier | Mode | `wolf-agent` |
|---|---|---|
| `/home/frappe` | `0750 frappe:frappe` | y entre (groupe) |
| `<bench>/logs/*` | `0644` | lit |
| `jobs.sqlite3`, `-wal`, `-shm` | `0644` | lit, avec `mode=ro` |
| `/var/log/nginx/access.log` | `0640 www-data:adm` | lit (groupe `adm`) |
| `<bench>/docker-compose.yml`, `<bench>/nginx.conf` | `0644` | lit |
| `/home/frappe/agent/config.json` | `0600` | non |
| `<bench>/config.json` | `0600` | non |
| `sites/common_site_config.json`, `sites/<site>/site_config.json` | `0600` | non |

L'agent Press écrit ses configurations en `0600` : le démon ne les lit donc qu'au travers de l'enregistrement, qui s'exécute en root. En fonctionnement, un nouveau bench est trouvé à partir des fichiers qu'il peut lire : son image dans `docker-compose.yml` ; son port web, ses sites et ses domaines personnalisés dans son `nginx.conf` ; et son `rq_port` à partir de ce port web, puisque Press donne à un bench un même décalage pour tous ses ports (`web_port` 18000 + décalage, `rq_port` 11000 + décalage).

## Ce que fait Wolf sur un serveur Press

| Domaine | Ce que fait Wolf | État |
|---|---|---|
| Détection | Le mode Press s'active quand `/home/frappe/agent/config.json` contient une clé `benches_directory`, quand il est présent à côté de `jobs.sqlite3` (illisible), ou quand `"platform": "press"` est défini | vérifié |
| Benches | Liste les `<benches_directory>/*` qui ont un répertoire `sites/` et un `config.json` avec un `docker_image`, ou, s'il est illisible, un `config.json` à côté d'un `docker-compose.yml` | vérifié |
| Nouvelle découverte | Réanalyse toutes les `press.rediscover_interval` secondes (60 par défaut), car chaque déploiement crée un nouveau répertoire de bench | vérifié : un nouveau bench est suivi en moins d'une minute |
| Logs du bench | Suit `<bench>/logs/*` (monté depuis le conteneur) et `sites/<site>/logs/*`, avec les mêmes parseurs que pour les autres benches | fait |
| nginx | Suit `/var/log/nginx/access.log` (au format `main` de Press, qui journalise `$host`) et associe les domaines personnalisés aux sites | fait, testé unitairement |
| File d'attente Redis | Lit `queue_length`, les registres RQ failed/started, les workers actifs et la mémoire/les évictions Redis depuis `redis://127.0.0.1:<rq_port>` (`config.json` du bench, ou 11000 + le décalage de ports du bench) | vérifié |
| Expiration TLS | Vérifie chaque site et chaque domaine personnalisé comme sur les autres benches. Les certificats sont sur le serveur proxy, donc la poignée de main publique mesure ce que voient les clients | fait (générique) |
| Sauvegardes | **Ignorées** par défaut (`backups.press: false`). Press fait les sauvegardes via son agent et les envoie hors site | désactivé |
| Processus | **Ignorés** : supervisor tourne dans chaque conteneur de bench et Wolf n'exécute jamais `docker` | — |
| MariaDB | Pas sur Press : le mot de passe de base de données du site est dans son `site_config.json`, lisible par `frappe` seulement | — |
| Risques de configuration des sites | `developer_mode`, `allow_tests`… demandent les configurations de site en `0600` : pas d'échantillon, affiché comme inconnu | vérifié |
| Services exposés | L'agent Press publie le Redis de file d'attente et de cache de chaque bench sur toutes les interfaces (`-p 0.0.0.0:<rq_port>:11000`, `<rq_cache_port>:13000`), pour les serveurs secondaires. Wolf les signale en `service_exposed` : Press compte sur le pare-feu du serveur pour les garder privés | vérifié |
| Corrélation des déploiements | Un événement `deployment` pour chaque job de déploiement, de mise à jour ou de migration dans le `jobs.sqlite3` de l'agent Press, et un événement `error` quand l'un d'eux échoue | vérifié |
| Événements des sites | Le Wolf App d'un bench Press nomme son bench et son serveur comme l'agent : le nom d'hôte du conteneur est le bench (`docker run --hostname <bench>`), et le `supervisor.conf` de Press nomme le serveur (`<server>-gunicorn.access.log`, son nom dans Press). L'enregistrement nomme l'hôte de l'agent de la même façon, depuis la configuration de l'agent Press, sauf si `--hostname` est donné ou si l'agent a déjà été enregistré | vérifié (le nom d'hôte du serveur de test est son nom dans Press) |
| Solution de repli | Si `jobs.sqlite3` est illisible, un événement `deployment` quand un nouveau bench apparaît ou qu'un site passe sur un autre bench | fait, testé unitairement |

Les métriques elles-mêmes sont décrites dans [Ce qui est collecté](/fr/agent/collected).

## Organisation du serveur

### Répertoire de l'agent Press

Ansible clone l'agent Press dans `/home/frappe/agent/repo`, crée un venv dans `/home/frappe/agent/env`, et lance `agent setup config` et `agent setup database` depuis `/home/frappe/agent`. `agent setup config` écrit `config.json` avec `benches_directory: /home/<user>/benches`, `nginx_directory: /home/<user>/agent/nginx`, `redis_port: 25025`, `web_port: 25052` et d'autres clés. Wolf détecte Press grâce à ce fichier et à sa clé `benches_directory`.

### Benches

Chaque bench est un `<benches_directory>/<name>/` avec `logs/`, `sites/`, `config/` et un `config.json` de bench. Les noms de benches suivent le motif `bench-<candidate>-<server>`. Wolf utilise le nom du répertoire.

Les applications se trouvent **dans l'image Docker**. Il n'y a pas d'`apps/frappe` sur l'hôte, donc la vérification générique de Wolf (`sites/` + `apps/frappe`) ne voit pas les benches Press. Un bench Press se reconnaît à son `config.json` qui contient une clé `docker_image`.

Les clés de configuration du bench viennent du doctype `Bench` de Press : `docker_image`, `web_port` (18000 + décalage), `socketio_port`, `rq_port` (11000 + décalage), `rq_cache_port`, `single_container: true`, entre autres.

Les conteneurs du bench montent `<bench>/sites` et `<bench>/logs` (bind mount), que le bench tourne dans un seul conteneur ou via `docker stack deploy`. Les logs du bench sont des fichiers ordinaires sur l'hôte. Wolf n'exécute jamais `docker`.

### Sites et domaines personnalisés

Les sites sont des répertoires `sites/<site>/` qui contiennent un `site_config.json`. Les domaines personnalisés d'un site sont listés dans son `site_config.json` sous `domains`, et la configuration nginx du bench les rattache au site. Wolf lit la même clé, si bien qu'un 502 journalisé pour `erp.customer.com` est compté pour le bon site.

### Logs

Dans le conteneur, supervisor écrit ces fichiers dans `logs/` :

- `web.log`, `web.error.log`
- `schedule.log`, `schedule.error.log`
- `worker.log`, `worker.error.log`

Les loggers de Frappe écrivent `frappe.web.log`, `scheduler.log` et les autres fichiers au même endroit, comme sur n'importe quel bench. Wolf suit aussi `schedule.error.log` pour les tracebacks, sur tous les benches. Là où rien ne l'écrit, le fichier est simplement absent.

### File d'attente Redis

`sites/common_site_config.json` contient l'adresse **interne au conteneur** `redis://localhost:11000`. Depuis l'hôte, le Redis de la file d'attente est joignable sur le `rq_port` publié, là où se connecte l'exporteur RQ de l'agent Press lui-même. Wolf utilise `redis://127.0.0.1:<rq_port>`. Quand un bench n'a pas de `rq_port`, Wolf ignore ses métriques de file d'attente.

### nginx

Le `nginx.conf` racine est généré dans `/home/frappe/agent/nginx/nginx.conf`, lié symboliquement à `/etc/nginx/nginx.conf`, et inclut chaque `<benches_directory>/*/nginx.conf`. Tous les vhosts utilisent un même log :

```nginx
log_format main '$remote_addr - $remote_user [$time_local] "$request" $status $body_bytes_sent "$http_referer" "$http_user_agent" "$http_x_forwarded_for" "$host" $request_time';
access_log /var/log/nginx/access.log main;
```

Le nom du site, ou un domaine personnalisé, est le dernier champ entre guillemets, `"$host"`. Le parseur nginx de Wolf lit les champs entre guillemets en fin de ligne, et le mode Press ajoute la correspondance domaine → site. Les modèles de bench ne définissent pas d'`access_log` par bench. Derrière un proxy Press, `$remote_addr` est le proxy.

::tip
Les serveurs proxy (hôtes `n*`) utilisent le même modèle racine mais n'ont pas de bench. Pour y compter les 5xx, ajoutez le log comme entrée `extra_logs` :

```json [config.json]
{
  "extra_logs": [{"path": "/var/log/nginx/access.log", "parser": "nginx"}]
}
```
::

## Événements de déploiement

### Historique des jobs

Chaque job de l'agent Press est stocké dans la base SQLite `jobs.sqlite3`, dans le répertoire de travail de l'agent (`/home/frappe/agent`). Elle fonctionne en mode WAL. Deux tables comptent :

- `jobmodel(id, name, status ∈ Pending/Running/Success/Failure, agent_job_id, data, enqueue, start, end, duration)`
- `stepmodel(id, name, job_id, status, data, start, end, duration)`

`agent_job_id` est le nom du document **Agent Job** dans Press. Wolf le recopie dans la charge utile de l'événement, pour que vous puissiez ouvrir le même job dans le tableau de bord Press.

Au moment de la mise en file, `data` vaut `{"function", "args", "kwargs"}`. À la fin du job, il est écrasé par le résultat ou par `{"traceback": …}`. Le `data` d'une étape conserve le résultat de la commande de chaque étape, y compris la ligne de commande `docker exec … <bench> bench --site <site> …`.

Les horodatages sont en heure locale du serveur, sans fuseau. Wolf les convertit en UTC en les considérant comme de l'heure locale.

### Jobs traités comme des déploiements

| Job de l'agent Press | Bench / site tiré de |
|---|---|
| New Bench | `args[0]` (bench) |
| Update Site Pull, Update Site Migrate | `args[0]` site, `args[2]` bench cible |
| Recover Failed Site Migrate, Recover Failed Site Pull, Move Site to Bench | `args[0]` site, `args[2]` bench cible |
| Recover Failed Site Update | `args[0]` site, `args[1]` bench |
| Update Bench In Place | `args[0]` sites ; bench tiré des étapes |
| Patch App, Bench Restart, Rebuild Bench Assets | étapes |
| Migrate Site, Install App on Site, Uninstall App on Site | étapes |

Les méthodes de `Bench` et de `Site` ne portent aucun nom de bench ni de site dans leurs arguments. Pour ces jobs, Wolf cherche dans le `data` du job et des étapes un nom de bench connu et un `--site <name>`.

### Production des événements

- **Accès en lecture seule.** Wolf ouvre `jobs.sqlite3` avec `file:…?mode=ro`, ce qui suppose que les fichiers `-wal` et `-shm` de l'agent soient lisibles. En cas d'échec, il réessaie avec `immutable=1`. Wolf n'écrit jamais dans la base.
- **Un événement `deployment` par job**, envoyé dès que le job a démarré. Son horodatage est le `start` du job, si bien que la [règle prédéfinie](/fr/alerts/presets) « 502 spike after deployment » rattache les incidents qui surviennent pendant une longue migration. Si le bench ne peut pas encore être déterminé, l'événement attend jusqu'à 2 minutes qu'une étape le nomme, puis part avec le périmètre de l'hôte. La corrélation des incidents prend aussi en compte les déploiements au périmètre de l'hôte. Champs : `category: "press"`, `source: "press-agent"`, et `payload.press_job`, `agent_job_id`, `local_job_id`, `sites`.
- **Un événement `error`** (`category: "press_job_failed"`, warning) quand un tel job se termine en `Failure`. Sa charge utile contient les noms des étapes en échec et la fin du traceback ou de la sortie.
- **Déduplication.** Les identifiants des jobs émis et un identifiant plancher sont enregistrés dans `<spool_dir>/press-jobs.json`, si bien qu'un redémarrage n'émet jamais deux fois le même événement. Au premier lancement, l'historique est ignoré et seuls les jobs encore Pending ou Running sont pris en compte. Un job bloqué en Pending ou Running depuis plus de 24 h (par exemple à cause d'un worker RQ planté) est abandonné, pour qu'il ne bloque pas la progression.
- **Repli sans accès à la base.** `<spool_dir>/press-benches.json` conserve un instantané bench → site. Un nouveau répertoire de bench, ou un site dont le répertoire est passé sur un autre bench, produit un événement `deployment` horodaté au moment où le changement a été constaté.

Une nouvelle découverte reconstruit les sources de logs quand l'ensemble des benches ou des sites change. Les logs d'un bench créé pendant que Wolf tourne sont lus depuis le début, puisque ce sont de nouveaux fichiers. Les logs d'un site déplacé suivent son répertoire ; ils sont donc lus depuis la fin, pour éviter de les rejouer.

Les champs des événements sont décrits dans le [protocole](/fr/reference/protocol).

## Wolf aux côtés du monitoring de Press

Press fournit déjà sa propre pile de monitoring. Wolf ne la remplace pas et n'y touche pas.

- **Serveur de monitoring** (`monitor.yml`) : Prometheus, Alertmanager, Blackbox exporter et Grafana. Prometheus sonde les sites, les domaines et TLS avec le module blackbox `http_2xx` et collecte les métriques des serveurs gérés par Press. Press lui transmet ses règles d'alerte et ses routes via la classe `Monitor` de l'agent, à partir de doctypes Press comme *Prometheus Alert Rule*. Le webhook d'Alertmanager arrive dans *Alertmanager Webhook Log*. Le doctype *Incident* de Press escalade les pannes par téléphone (Twilio) vers l'équipe de Frappe et les clients.
- **Serveurs d'applications** (`server.yml`) : node_exporter, cAdvisor, statsd_exporter (la configuration du bench définit `statsd_host`), filebeat et fail2ban, entre autres rôles. Filebeat envoie `/var/log/*.log`, le module nginx et le `logs/monitor.json.log` de chaque bench vers un serveur de logs Elasticsearch/Kibana central. L'agent Press met aussi `monitor.json.log` de côté pour les analyses de Press. Wolf ne suit pas ce fichier.
- L'agent Press expose des métriques RQ par bench sur `/benches/metrics`.

Ce que Wolf ajoute sur une installation Press auto-hébergée :

- Les tracebacks au niveau de Frappe, les tâches planifiées en échec et les plantages de workers, lus dans les logs du bench.
- Les 5xx/502 par site.
- Les signaux SSH.
- Des incidents corrélés au job Press qui les a causés.

Tout cela reste sur votre propre site Wolf, sans accès au serveur de monitoring de Press.

Les deux piles se recoupent sur les métriques de l'hôte (node_exporter contre l'échantillonnage de `/proc` par Wolf) et sur les longueurs de files d'attente. Celles de Wolf sont légères. Désactivez les métriques de l'hôte avec `collect_host_metrics: false`.

## Limites et points non vérifiés

### Limites

- Seuls les serveurs d'applications qui hébergent des benches sont pris en charge directement. Les serveurs proxy et de base de données n'ont pas de bench : ajoutez leurs logs via `extra_logs`.
- Quand un job se termine, l'agent Press remplace ses arguments par son résultat. Un job que Wolf voit pour la première fois une fois terminé prend le bench dans lequel sa dernière étape s'est exécutée (un déplacement de site se termine sur sa cible) et le site dans le `--site` d'une commande d'étape. Un job sans aucune étape de ce genre est signalé avec le périmètre de l'hôte.
- La solution de repli par le système de fichiers ne distingue pas un déploiement d'un déplacement manuel, et elle ne remonte aucun échec.
- Un bench trouvé après l'enregistrement affiche l'image avec laquelle il a été créé (son `docker-compose.yml`) : Update Bench In Place ne modifie que sa configuration en `0600`.
- Les jobs sont reconnus par leur nom d'affichage. Si Press renomme un job, il n'est plus reconnu. Ajoutez le nouveau nom à `DEPLOY_JOBS` dans [`agent/wolf_agent/press.py`](https://github.com/bthuner/dodock-wolf/blob/main/agent/wolf_agent/press.py).
- Les benches sur système de fichiers partagé (`Run Benches on Shared FS`) changent `benches_directory`. Wolf le relit dans la configuration de l'agent Press à chaque nouvelle découverte, mais ce cas n'a pas été testé.
- Personne n'a vérifié si les copies locales des sauvegardes restent dans `sites/<site>/private/backups`, c'est pourquoi les sauvegardes sont désactivées par défaut.

### Vérifié sur un serveur Press

1. **Modes.** `jobs.sqlite3` et ses fichiers `-wal` et `-shm` sont en `0644`, et `mode=ro` fonctionne pour un membre du groupe `frappe`. Les configurations sont en `0600` : voir [Permissions](#permissions).
2. **Données des jobs.** Les noms des jobs correspondent à `DEPLOY_JOBS`. Le `data` d'un job terminé vaut `null`, et ses étapes gardent leur commande et leur `directory`, par exemple `docker exec … bench-0001-000002-f1 bench --site <site> migrate` pour une migration.
3. **`$host`.** Chaque requête d'un site porte le site dans `"$host"`. Le vhost de l'agent Press lui-même, sur le port 443, y journalise le nom du serveur, qui n'est pas un site : Wolf écarte ces lignes.
4. **`rq_port`.** Press le définit sur chaque nouveau bench et le publie. Un bench dont la configuration n'en a pas (un bench plus ancien) n'a pas de métriques de file d'attente : le démon garde ce que l'enregistrement y a lu plutôt que de déduire un port du port web.

Non vérifié : un site derrière un serveur proxy Press (ici, les requêtes arrivent directement sur le serveur d'applications), les benches sur système de fichiers partagé, et les copies locales des sauvegardes.
