Installer

Benches Pilot

Faites tourner le Wolf Agent sur un hôte Frappe Pilot et transformez les tâches Pilot en événements de déploiement.

Pilot est le gestionnaire de serveurs de Frappe (« Frappe Server Manager »). Ce n'est pas un outil Dokos : le groupe GitLab public de Dokos ne contient aucun dépôt Pilot. La documentation Dokos ne mentionne Pilot qu'à travers les clés de site pilot_endpoint / pilot_auth_token, utilisées par le panneau Cloud Settings pour les sites Frappe Cloud v2. Ce sont les mêmes clés que Pilot écrit dans site_config.json.

Tout ce qui figure sur cette page a été vérifié sur un vrai hôte Pilot : Pilot v1.0.0-rc.1 en mode production (unités utilisateur systemd, nginx, l'Admin), un bench Frappe 16 et un site qui fait tourner la Wolf App. Le dossier dev/pilot du dépôt monte le même hôte dans un conteneur.

Installation

Installez l'agent comme sur n'importe quel hôte (Wolf Agent). Il tourne sous son propre utilisateur wolf-agent, hors de portée du bench : du code qui prend la main sur un site Frappe ne peut ni lire sa configuration, sa clé d'intégrité ou son état, ni l'arrêter.

Pilot ne laisse lire le bench.toml d'un bench, ses tasks/ et les configurations de ses sites qu'à l'utilisateur du bench, et fait tourner le bench en unités utilisateur systemd de cet utilisateur, qu'un autre utilisateur ne peut pas lister. Sur un hôte Pilot, l'installeur met donc aussi en place wolf-pilot-export, un utilitaire root lancé toutes les 20 secondes par wolf-pilot-export.timer. Il écrit /var/lib/wolf-pilot-export/<bench>.json (root:wolf-agent, mode 0640, dans un dossier qui appartient à root) avec :

  • les 100 dernières tâches : commande, statut, horaires, code de sortie, code et message d'échec, et des arguments seulement le site ;
  • l'état des unités utilisateur <bench>-*.service du bench.

Il lit les fichiers du bench sous l'utilisateur du bench, dans un processus enfant limité dans le temps : un lien que cet utilisateur y place ne donne accès à rien de plus que ce qu'il pouvait déjà lire. Il ne prend un bench que si son [bench] name est le nom de son dossier et si ce dossier appartient à l'utilisateur dont le home le contient. Il ne copie rien d'autre : ni bench.toml (son secret Admin), ni les configurations des sites (leurs mots de passe de base de données). L'enregistrement tourne en root : la découverte lit donc toujours bench.toml et les configurations des sites une fois, pour le nom du bench, ses sites, ses domaines et ses ports.

Ce que cela coûte sur Pilot : les contrôles MariaDB, qui demandent le mot de passe de base de données d'un site.

Vérifier ce que Wolf trouve

sudo wolf-agent discover

Vérifier ce qui serait envoyé

sudo -u wolf-agent wolf-agent --config /etc/wolf-agent/config.json check

check collecte une fois et affiche la charge JSON. Rien n'est envoyé. Voir Commandes.

Les noms des journaux des workers sont résolus à l'enregistrement. Relancez wolf-agent register après avoir modifié [[workers]] dans bench.toml.

Configuration

Les événements de déploiement issus des tâches Pilot sont activés par défaut. La section pilot de /etc/wolf-agent/config.json :

config.json
{
  "pilot": {
    "deployments": true,
    "api_url": null,
    "token": null,
    "jwt_secret": null
  }
}
pilot.deployments
boolean
Interroge les tâches Pilot et les transforme en événements. false désactive l'interrogation. Par défaut true.
pilot.api_url
string | null
Remplace l'adresse de l'API Admin de chaque bench, http://127.0.0.1:<admin.port+1>. Elle s'applique à tous les benches Pilot de l'hôte : ne la renseignez que sur un hôte à un seul bench.
pilot.token
string | null
Un jeton de l'API Admin à portée bench, utilisé seulement sans la copie de wolf-pilot-export.
pilot.jwt_secret
string | null
Le [admin] jwt_secret du bench, pour créer un jeton d'une heure, seulement sans la copie de wolf-pilot-export.

Avec wolf-pilot-export, Wolf n'a besoin ni de l'un ni de l'autre. La configuration complète est sur Configuration.

Organisation d'un bench

Benches

Le install.sh de Pilot s'installe dans $HOME/pilot sous un utilisateur de bench non root (frappe par défaut). Les benches sont dans ~/pilot/benches/<nom>/, chacun avec apps/, sites/, env/, logs/, config/, tasks/ et bench.toml.

bench.toml

Mode 0600, lisible par l'utilisateur du bench seulement. Wolf le lit à l'enregistrement, qui tourne en root :

CléUsage
[bench] nameObligatoire, avec python. Le nom du bench et le marqueur Pilot
[redis] queue_portPort Redis de la file. Par défaut 11000
[admin] portPar défaut 7000. Le backend Admin écoute sur 127.0.0.1:<port + 1>
[admin] jwt_secretSeulement quand Wolf crée un jeton Admin, ce qui demande un bench.toml lisible. Pilot l'écrit à la première session de l'Admin
[production] enabledConservé pour information

Processus et journaux

Pilot fait tourner un bench de production en unités utilisateur systemd de l'utilisateur du bench (systemctl --user), avec le linger activé : <bench>-web, <bench>-redis_cache, <bench>-redis_queue, <bench>-admin (démarré par son socket, <bench>-admin.socket) et les processus des apps. Le MariaDB de Pilot est l'unité utilisateur pilot-mariadb.

Le mode lite, activé par défaut ([lite_mode] enabled), fait tourner le serveur web, les workers et le scheduler dans un seul processus web (frappe.runner). Ses journaux, y compris la sortie logging de Python, vont dans logs/web.log.error.log. Hors du mode lite, il y a des processus workers et scheduler, journalisés dans worker_<queues>_<i>.log et schedule.log, avec stderr dans <journal>.error.log.

L'isolation (sandbox). Un nouveau bench systemd fait tourner ses processus de travail isolés, et les journaux de Frappe (frappe.log, scheduler.log…) sont alors dans logs/workload/. L'isolation demande des espaces de noms utilisateur non privilégiés, qu'Ubuntu 24.04 refuse par défaut (kernel.apparmor_restrict_unprivileged_userns = 1) : pilot setup production échoue alors, et Pilot conseille sandbox = false sous [production]. Wolf lit les deux organisations.

nginx

Chaque vhost de site journalise dans <bench>/logs/nginx-access.log :

log_format pilot_access '$pilot_client_addr [$time_local] "$request_method $uri" $status "$host" $request_time';

Ce format n'a pas de chaîne de requête ($uri, pas $request_uri) ni de User-Agent. Sur un bench Pilot, la détection web de Wolf voit les chemins sondés (/.env, /.git/, chemins de CMS et d'équipements), mais pas les injections ni les traversées de chemin portées par une chaîne de requête, ni les scanners reconnus à leur User-Agent. Suricata voit les requêtes complètes.

Tâches

Les opérations de l'Admin sont des tâches, stockées dans <bench>/tasks/<AAAAMMJJ-HHMMSS-hex>/, en mode 0700 :

  • meta.json : task_id, command, args, queued_at, started_at, finished_at (UTC, ISO-8601), exit_code, failure.
  • status : queued, running, success, failed ou killed.

Événements de déploiement issus des tâches Pilot

Wolf signale ces commandes de tâche :

update, retry-update, complete-migration, migrate, revert-migration, revert-apps, revert-site, switch-branch, get-and-install-app, install-app, uninstall-app, remove-app, build, restart-services, switch-lite-mode, setup-nginx, restore-site, reinstall-site.

Le site vient des arguments site / sites de la tâche ; rien d'autre des arguments n'est conservé.

Où les tâches sont lues

  1. Les fichiers de tâches, <bench>/tasks/*/meta.json et status, quand l'agent peut les lire (un agent qui tourne sous l'utilisateur du bench).
  2. La copie de wolf-pilot-export, /var/lib/wolf-pilot-export/<bench>.json, quand elle a moins de 5 minutes : le cas normal.
  3. L'API Admin, GET http://127.0.0.1:<admin.port+1>/api/v1/tasks?limit=100, seulement sans les deux autres. Elle demande un jeton à portée bench : pilot.token, ou un jeton que Wolf crée depuis pilot.jwt_secret ou bench.toml. Pilot liste chaque jeton qu'il vérifie parmi les sessions actives de l'Admin, et un jeton à portée bench peut tout ce que peut l'Admin : la copie évite les deux.

Comment les événements sont produits

Les mêmes règles que sur les serveurs Press :

  • Un événement deployment est envoyé au démarrage de la tâche, horodaté à started_at. Un incident pendant une longue migration s'y rattache, par exemple via le préréglage « 502 spike after deployment ».
  • Un événement error est envoyé si la tâche se termine en failed. Il porte failure.code, failure.message et exit_code.
  • Les identifiants des tâches signalées sont conservés 3 jours dans <spool_dir>/pilot-tasks.json.
  • La première interrogation ignore l'historique et ne prend que les tâches en file ou en cours.

Une migration enregistre aussi l'événement deployment du site lui-même (source frappe), comme sur tout bench : celui de Pilot dit quelle tâche l'a lancée.

Wolf à côté de la supervision de Pilot

D'après la documentation de Pilot :

  • pilot-monitor.service collecte les métriques de l'hôte, de la base et des benches, et interroge les sites de production.
  • [resource_limits] lève des alertes CPU, mémoire, disque et disponibilité au bout de 5 minutes. Elles partent vers Central (sur les hôtes gérés par Central), vers webhook_endpoints et par e-mail.
  • [telemetry] envoie les métriques et les journaux vers le point d'entrée « Datum » d'une région, avec un jeton délivré par Central.

Wolf lit les mêmes fichiers locaux et n'interfère avec aucun de ces éléments. Ce qu'il ajoute sur un hôte Pilot auto-hébergé :

  • Les tracebacks, les tâches planifiées en échec et les plantages de workers sous forme d'événements.
  • Les 5xx/502 par site.
  • Les signaux SSH.
  • Des incidents rattachés à la tâche Pilot qui les a précédés.

Tout reste sur votre propre site Wolf.

La Wolf App sur un bench Pilot

La Wolf App s'installe sur un bench Pilot comme n'importe quelle app (pilot get-app, pilot install-app). Pilot vérifie que chaque app requise dans hooks.py est déclarée dans [tool.bench.frappe-dependencies] du pyproject.toml, sauf Frappe : Frappe est implicite, et une app qui le liste dans required_apps est refusée.

Ce qu'il faudrait dans Pilot

  1. Un bouton « activer Wolf pour ce bench ». Une table [wolf] dans bench.toml (enabled, url) et un interrupteur dans les réglages de l'Admin, qui installerait et enregistrerait l'agent. Cela relève de frappe/pilot.
  2. Un jeton machine en lecture seule pour l'API Admin (tasks:read, états des unités), qui rendrait l'utilitaire root inutile.
  3. La chaîne de requête et le User-Agent dans pilot_access, pour détecter les attaques web depuis le journal d'accès.
