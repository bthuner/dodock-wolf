Protocole de l'agent

Chaque point d'accès, champ et code de statut qu'utilisent le Wolf Agent, les satellites et les intégrations pour dialoguer avec le Wolf App (protocole v1).

Tout le trafic est en HTTPS + JSON. Tous les horodatages sont des chaînes ISO-8601 en UTC (2026-10-29T02:00:13Z). L'app les convertit dans le fuseau horaire système du site.

Les réponses suivent la convention de Frappe : la réponse se trouve sous la clé message.

{

  "kind": "agent",
  "agent_version": "0.1.0",

ChampSignification
registration_tokenLa valeur de Wolf Settings → Registration Token.
hostnameLe nom de l'hôte. Pour un satellite, le nom de son site.
kindFacultatif. agent (par défaut), satellite ou integration (voir Intégration Wazuh).

Réponse :

Réponse
{"message": {"agent_id": "WAG-0001", "agent_secret": "<random 40 chars>", "push_interval": 30}}

La réponse contient aussi server_version, la version du Wolf App.

Le secret n'est renvoyé qu'une fois. L'agent le stocke dans /etc/wolf-agent/config.json (mode 0600). Le site Wolf ne conserve qu'une empreinte salée (hmac-sha256$<salt>$<digest> sur Wolf Agent) et ne peut donc pas réafficher le secret. Deux moyens le remplacent :

  • enregistrer à nouveau le même nom d'hôte ;
  • Rotate secret dans le formulaire Wolf Agent, qui affiche une seule fois le nouveau secret.

Satellites

Un satellite est un autre site Frappe qui exécute dodock_wolf en mode satellite (voir Tous les sites d'un bench). Il s'enregistre avec hostname égal au nom de son site et une entrée de bench portant son vrai host :

Enregistrement d'un satellite
{"registration_token": "...", "kind": "satellite", "hostname": "b.example.com", "agent_version": "0.1.0",
 "os": "Linux-6.1...", "benches": [{"name": "frappe-bench", "path": "/home/frappe/frappe-bench",
 "sites": ["b.example.com"], "host": "bench-01"}]}

Refus

  • Un nom d'hôte déjà enregistré avec un autre type est refusé.
  • Un site en mode satellite refuse tout enregistrement : enregistrez-vous plutôt auprès de son site central.
  • Un jeton d'enregistrement erroné est refusé.
  • L'enregistrement est limité à 20 appels par heure.

Actions de réponse

actions contient les blocages qu'un Wolf Manager a approuvés pour cet agent et que celui-ci n'a pas encore rapportés :

actions
[{"id": "WRA-00001", "action": "block_ip", "ip": "45.33.32.156", "seconds": 86400}]

L'agent envoie chaque résultat dans un envoi ultérieur :

action_results
"action_results": [{"id": "WRA-00001", "ok": true, "detail": "..."}]

Un id n'est accepté qu'une fois, et uniquement de la part de l'agent auquel il a été donné. Voir Actions de réponse et Sécurité.

Mode d'ingestion

Se définit dans Wolf Settings → Ingest Mode.

ModeComportement
async (par défaut)L'app valide et normalise le lot pendant la requête, met les insertions en file d'attente pour un worker en arrière-plan et répond "queued": true. Le worker les insère et rattache les événements aux incidents ouverts quelques secondes plus tard. Un échec dans le worker n'est pas remonté à l'agent : il figure dans l'Error Log du site.
syncLe lot est stocké pendant la requête et queued vaut false. Les erreurs de stockage font échouer la requête (HTTP 5xx) et l'agent réessaie.

Si la file d'attente est injoignable en mode async, le lot est stocké comme en mode sync. Dans les deux modes, la dernière heure de contact de l'agent et son décalage d'horloge sont enregistrés pendant la requête, pour que les heartbeats n'attendent pas la file d'attente.

Limite de débit

Les envois sont comptés par agent sur des fenêtres d'une minute : Wolf Settings → Max Pushes Per Minute, par défaut 120, 0 = désactivé. Au-delà de la limite, le serveur répond HTTP 429. Les agents et les satellites traitent un 429 comme une erreur réseau : le lot reste dans la file locale et est rejoué après un délai croissant.

Nettoyage (scrubbing)

L'agent retire les adresses e-mail, identifiants, numéros de carte et IBAN des titres et payloads des événements avant l'envoi (voir Nettoyage (scrubbing)). Le serveur stocke ce qu'il reçoit tel quel.

Décalage d'horloge

  • sent_at est horodaté au moment de l'envoi de la requête, y compris pour les lots rejoués depuis la file locale.
  • Le serveur enregistre sent_at - server time comme clock_skew_seconds de l'agent (positif = agent en avance, affiché sur Wolf Agent) et le renvoie. L'agent journalise un avertissement au-delà de 60 s.
  • Les horodatages de métriques et d'événements situés dans le futur au-delà de Wolf Settings → Max Clock Skew (par défaut 300 s, 0 = désactivé) sont ramenés à l'heure du serveur et comptés dans clamped.
  • Les fenêtres des règles et les graphiques ignorent aussi les lignes horodatées plus d'une minute dans le futur.

Satellites

Les satellites utilisent le même point d'accès avec leurs identifiants de satellite.

  • Ils n'envoient aucune métrique.
  • Au plus 100 événements par requête.
  • Chaque événement a des host, bench, site, fingerprint et count explicites. Les doublons vus avant la transmission sont fusionnés en un seul événement.
  • Un corps vide envoyé chaque minute leur sert de heartbeat.
RéponseComportement du satellite
401 / 403Nouvel essai dans 15 minutes.
Autre 4xx (sauf 408 / 429)Le lot est abandonné.
5xx ou erreur réseauNouvel essai après 1, 2, 4, 8, puis 15 minutes.

Enrichissement à l'ingestion

  • Réputation d'IP. Quand la réputation d'IP est activée, un événement de sécurité dont l'ip du payload figure sur une liste de blocage téléchargée reçoit reputation: {"listed": true, "lists": [...]} et un cran de gravité supplémentaire.
  • MITRE ATT&CK. Les payloads de sécurité peuvent porter attack_techniques, une liste d'identifiants de techniques (T1110, T1552.001). L'app ajoute mitre_attack, une liste de {id, name, tactic} qui fusionne ces identifiants avec la correspondance propre à la catégorie (voir Sécurité).
  • Entités. Chaque événement security reçoit payload.entities, quelle que soit sa source : {"ip": [...], "host": [...], "site": [...], "user": [...]}, normalisé et résolu via les lignes Wolf Entity Alias. Les agents ne l'envoient pas : le site le calcule.

silence_minutes a été ajouté après la v1 et reste rétrocompatible : les apps plus anciennes l'ignorent, et les agents l'omettent sauf si --silence est fourni. Quand c'est un entier positif, l'app crée un Wolf Silence à partir de maintenant pour ce nombre de minutes, plafonné à 24 h, dont le périmètre est l'hôte de l'agent plus le bench et le site indiqués.

  • Les incidents correspondant au silence s'ouvrent et se mettent à jour quand même, pour que la chronologie reste complète.
  • Leurs notifications sont retenues.
  • Les incidents encore ouverts à la fin de la fenêtre sont alors notifiés.

Réponse :

Réponse
{"message": {"event": "<Wolf Event name>", "silence": "WSIL-00001", "silence_until": "2026-10-29 02:15:00"}}

silence et silence_until (fuseau horaire du site) ne sont présents que lorsqu'un silence a été créé.

Un agent qui a demandé un silence et ne reçoit pas de clé silence en retour dialogue avec une app qui ne gère pas les silences, et doit émettre un avertissement.

Santé de Wolf (heartbeat)

GET|POST /api/method/dodock_wolf.api.ingest.status
GET /api/method/dodock_wolf.api.ingest.status
X-Wolf-Agent-Id: WAG-0001
X-Wolf-Agent-Secret: <secret>

Réponse : {"message": {"agent": "WAG-0001", "push_interval": 30, "health": {...}}}.

Le même objet health revient avec chaque envoi : l'agent n'a donc pas besoin d'interroger status. Cet appel sert à wolf-agent check et aux scripts. Il est en lecture seule : il ne met pas à jour la dernière heure de contact de l'agent.

health
{
  "ok": false,
  "problems": ["alert rules not evaluated for 12 min; scheduler disabled (pause_scheduler)"],
  "checked_at": "2026-10-29T02:12:30Z",
  "server_version": "0.1.0",
  "rules": {"last_evaluated": "2026-10-29T02:00:01Z", "age_seconds": 749},
  "scheduler": {"enabled": false, "reason": "pause_scheduler",
                "last_job_run": "2026-10-29T02:00:00Z", "age_seconds": 750},
  "queues": {"lengths": {"short": 0, "default": 3, "long": 0}, "workers": 2,
             "ingest_queue": "short", "ingest_backlog_seconds": null}
}
ChampSignification
rules.last_evaluatedLe last_evaluated le plus récent parmi les Wolf Alert Rules activées (le moteur de règles tourne à chaque tick du planificateur) ; null si aucune règle n'a encore tourné.
scheduler.enabled / reasonfalse avec maintenance_mode, pause_scheduler, disable_scheduler ou enable_scheduler unset in System Settings.
scheduler.last_job_runLe Scheduled Job Type.last_execution le plus récent, horodaté quand un worker démarre un job.
scheduler.tick_secondsSecondes entre deux ticks du planificateur (scheduler) de Frappe, donc entre deux évaluations des règles : 240 sur Frappe 15 et Dodock sauf si scheduler_tick_interval est défini ; null sur un Frappe sans ce paramètre. Informatif, jamais un problème.
*.age_secondsnow - timestamp côté serveur, si bien que le décalage d'horloge de l'agent n'a pas d'importance. Négatif quand l'heure stockée est dans le futur, ce qui arrive après un changement de fuseau horaire du système et bloque le planificateur jusqu'à cette heure.
queuesLongueurs des files d'attente RQ et nombre de workers du bench, ou {"error": "..."} si Redis est injoignable.
queues.ingest_backlog_secondsDepuis combien de temps le plus ancien job de la file d'ingestion (ingest_queue) attend ; null quand elle est vide. Les envois mis en file d'attente reçoivent une réponse avant d'être stockés : c'est donc le seul signe que la télémétrie n'arrive pas.
ok / problemsLa lecture propre du serveur, avec un seuil de 5 minutes.

Deux situations sont des problèmes :

  • obsolescence : abs(age) >= stale threshold sur rules, ou sur scheduler quand aucune règle n'est activée ;
  • retard d'ingestion : ingest_backlog_seconds >= stale threshold.

L'état du planificateur et des files d'attente est un contexte ajouté au texte d'obsolescence. L'agent applique son propre seuil (watchdog.stale_minutes) aux âges bruts plutôt que de se fier à ok.

Tant que les règles sont obsolètes, chaque envoi enregistre aussi un événement host_metric_alert / scheduler_stalled sur le site, incrémenté plutôt que dupliqué pendant 15 minutes. La règle prédéfinie Scheduler stalled le transforme en incident dès que le planificateur tourne à nouveau. Un site bloqué ne peut pas alerter sur lui-même : l'alerte en direct est donc émise par le chien de garde (watchdog) de l'agent via son propre canal de secours (voir Chien de garde (watchdog)).

Liens d'action sur les incidents

Les alertes par e-mail, Raven et webhook pour les incidents non résolus portent des liens signés :

GET /api/method/dodock_wolf.api.actions.incident_action
GET /api/method/dodock_wolf.api.actions.incident_action
    ?incident=WINC-00012&action=ack|resolve&expires=<unix seconds>[&actor=<email>]&sig=<hex>
ParamètreSignification
incidentLe Wolf Incident.
actionack ou resolve.
expiresSecondes Unix.
actorL'adresse du destinataire dans les e-mails (un e-mail par destinataire). Absent pour Raven et les webhooks.
sigHMAC-SHA256 sur wolf-incident-action\n<incident>\n<action>\n<expires>\n<actor>, avec une clé dérivée de l'encryption_key du site.

Les liens expirent après Wolf Settings → Action Link Hours (par défaut 24, 0 les désactive).

Un GET affiche seulement une page de confirmation. Son bouton envoie les mêmes paramètres en POST, et seul le POST acquitte ou résout : les scanners de liens ne peuvent donc pas agir sur un incident. L'incident enregistre acknowledged_by / resolved_by comme l'utilisateur connecté, sinon l'actor, sinon link.

Wolf Delivery

Chaque requête est enregistrée comme un Wolf Delivery :

ChampSignification
incident, alert_ruleCe qui a été notifié.
atQuand.
channel_typeSlack, Matrix, PagerDuty…
targetLa destination sans secrets : hôte, salon, numéros de téléphone masqués.
kind, action, digestCe qui a été envoyé.
ok, http_statusLe résultat.
errorL'erreur, sans les secrets ni les chemins et paramètres des URL.

Les résumés des canaux natifs sont regroupés selon un SHA-256 des paramètres du canal, et l'élément de résumé garde une référence à la ligne du canal plutôt qu'un quelconque secret.
