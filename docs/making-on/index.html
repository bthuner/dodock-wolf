0101 / Le virage

Frappe built the rest. So we stopped.

The brief of October asked for observability for Frappe benches. Three weeks later, Frappe's own cloud had a telemetry store, a control plane, and an incident manager with a status page. The last one appeared on 14 November.

On 19 November Dokos decided not to build what Frappe builds (#136). New work goes to the one thing no Frappe tool covers, on Frappe Cloud or anywhere else: the security and compliance of the bench. To build next to something, you first have to know its shape. So we read it.

Not pursued any more: Frappe has them

  • NoSLOs and error budgets
  • Nouptime bars
  • Nophone paging
  • Notraces
  • Nolog search
“Where Frappe or an existing tool already does something, Wolf connects to it rather than rebuilding it.”

From #136. The catch: Frappe's stack cannot be run outside Frappe Cloud today. Datum has no license, and Beacon needs a Datum, a ClickHouse and an Atlas per region. Operators who host themselves keep what Wolf already has.

0202 / La carte

Six applications, three planes, no shared database.

Two applications are global, one site each. Each region repeats three more, with a proxy in front. And every customer server is one virtual machine that runs the sixth.

They talk over HTTPS and nothing else: short signed tokens going down, signed webhooks coming back up. Every arrow below points from the caller. Pick an application to see only its links, or a kind of link to see only those.

0303 / Les habitants

Each one owns one thing, and says so.

The division of labour is strict. Central knows who you are and what you pay. It does not know which apps your bench runs: it has no Bench DocType and no deployment record. That is Pilot's business, in files on your server.

CentralGlobal

“Who is this, and may they?”

Teams, 18 capabilities, billing, the console. A server is a Virtual Machine record; every action on it is a Resource Action. It never opens an SSH session to a server.

  • Frappe 16 app + Vue · v0.2.0 · AGPL-3.0
  • one site, outside every region's private network
  • frappe/central @ 5027a0c
AtlasRegion

“Is this machine running?”

Firecracker machines on physical hosts, driven by a Go daemon, metald. The proxy, the private network between a team's servers, snapshots. A small guest agent sits in every image.

  • Frappe 16 app + Go + OpenResty + eBPF · AGPL-3.0
  • one site per region; AWS, Scaleway or own hardware
  • frappe/atlas @ 31aa231
CargoRegion

“What does a new server boot?”

It builds the Pilot images and hands them to Atlas as tagged snapshots. It also runs the region's S3 storage, and the host where Datum and ClickHouse live.

  • Frappe app on a Pilot bench · v0.0.1 · MIT
  • one platform machine per region
  • frappe/cargo @ 0f18a8a
PilotServer

“What runs on this server?”

The successor of bench: benches, sites, apps, backups, certificates, an Admin with about 300 routes. No database: bench.toml and folders. One switch, [central] enabled, separates a self-hosted Pilot from Frappe Cloud.

  • Python CLI + Flask + Vue · AGPL-3.0
  • inside every customer server, as user frappe
  • frappe/pilot @ 77acd72
DatumRegion

“Write this down.”

Four routes that only write: samples, Prometheus remote write, log lines, traces. It checks a token, stamps its resource_id on every row and inserts into ClickHouse. It has no read route.

  • FastAPI + ClickHouse · v0.1.0 · no license
  • one per region, installed by Cargo
  • frappe/datum @ a08c555
BeaconGlobal

“Is the platform all right?”

It only pulls: SQL on each region's ClickHouse, a list of machines from each Atlas, rule files from each producer's repository. Incidents, service levels, phone paging, the status page.

  • Frappe 16 app + Vue · v0.0.1 · AGPL-3.0
  • one site, created 14.11.2026
  • frappe/beacon @ d83a532

0404 / Les clés

Trust is a chain of public keys.

Going down, a call carries an Ed25519 token that names its audience: atlas-admin:<region>, atlas-proxy, atlas-cargo, atlas-datum. Coming back up, a report carries an HMAC of its body. No application stores another's password.

The surprise is where each verifier gets its keys. Not from Central: from the layer just above it. Each layer republishes what it fetched, and adds its own.

How long a credential lives

The calls between applications are short. What sits on a machine is not. Nothing here can be revoked before it expires, and no rotation of the signing keys is implemented yet.

  1. Secrets travel in the metadata, not in the image.

    An image holds no token and no team. At creation Central writes four attributes to the machine's metadata service; Pilot reads them at first boot. The X-Pilot-Token is read from there at every call and never written to disk.

  2. The team comes from the credential, never from the request.

    Central looks up the SHA-256 of the token and takes the team and the server from that record. A Pilot cannot ask on behalf of another.

  3. One key set, two planes.

    Central publishes its region key and its Pilot key at the same address. A verifier that checked the signature alone would accept one for the other, so everything rests on the audience.

  4. The regions see a number, not a customer.

    Atlas knows a 32-bit tenant id. Capabilities, names and invoices stay in Central.

0505 / Les trajets

Follow one request, and the system explains itself.

A map shows who may talk to whom. A flow shows who actually starts. Six of them, hop by hop: each line is one request, drawn between the two applications that exchange it.

A server is bornFrom a click to the first heartbeat

TeamCentralAtlasHostServer
  1. Team → CentralCreate server

    central.api.servers.create_server. Central checks the server:create capability and the billing gate, and stores a Resource Action.

  2. CentralMint the server's credential

    A random X-Pilot-Token; Central keeps its SHA-256. It goes into the machine's metadata with the team's id, the mailbox, the telemetry address.

  3. Central → AtlasPOST /api/atlas/virtual-machines

    Image, size, SSH keys, user_data, firewall, metadata. A 5-minute token and X-Tenant-ID. A request lost in transit is never sent twice.

  4. Atlas → HostPlace the machine

    Atlas picks a host and tells metald over mutual TLS.

  5. Host → ServerBoot

    Clone the image's disk, build the network, start a jailed Firecracker, fill the metadata service at 169.254.169.254.

  6. ServerFirst boot

    Pilot's bootstrap unit polls the metadata every 0.1 s, applies three settings once, stores Central's keys.

  7. Atlas → Centralvm.state: running

    A webhook signed with HMAC. Central also reconciles every 10 minutes.

  8. Central → ServerAdopt admin-vm-<label>

    Through the region's proxy, with a 5-minute token whose audience is this bench.

  9. Server → Centraldatum_token

    X-Pilot-Token. Central answers with a 7-day write token. Telemetry starts.

A hostname is routedA custom domain, from the site to the proxy

SitePilotCentralProxyDNS
  1. Site → PilotAdd a domain

    POST /sites/<site>/domains on the loopback, with the site's own token.

  2. Pilot → Centraldomain_records

    Pilot runs bench-domain-provider, a program from Cargo's image. It calls Central with X-Pilot-Token.

  3. Central → DNSCheck the proof

    The customer set a CNAME to the proxy and a TXT record _frappe-verification. Central reads the TXT.

  4. Central → ProxyDoes the name arrive here?

    Central reads http://<domain>/.well-known/frappe-pre-authorize/: the proxy must answer.

  5. Central → ProxyPATCH /v1/domains/<domain>

    Central stores a Site Domain and writes the route. Token atlas-proxy:<region>. Retried every 5 minutes.

  6. PilotCertificate

    The proxy passes this domain's TLS through, so Pilot obtains the certificate itself.

  7. Proxy → PilotTraffic

    TLS on port 443 with a PROXY protocol header. The region's own names arrive as HTTP on port 80.

A number is measuredFrom a server to a rule

CargoCentralPilotDatumBeacon
  1. Cargo → Centraltelemetry: Available

    Cargo runs the Datum host. Its webhook gives Central the address http://internal-telemetry-svc.<region>.

  2. Central → PilotThe address, at creation

    In the metadata of every new server.

  3. Pilot → Centraldatum_token

    A 7-day token, resource_id = the machine's Atlas id. Stored in [telemetry] token, renewed when a day is left.

  4. Pilot → DatumPOST /v1/ingest

    pilot_sites every 60 s; seven other metrics and update events every 5 minutes. Over the region's private network.

  5. DatumCheck and stamp

    The token is checked against the keys Cargo publishes. resource_id is written on every row.

  6. Beacon → DatumRead

    Every minute, the SQL of pilot/beacon/rules/, as ClickHouse user beacon.

  7. BeaconTrust the sender

    Rows whose resource_id is not a machine in Atlas' tree, or is younger than 10 minutes, are dropped.

A person is pagedFrom a row to a phone

ClickHouseBeaconChatTwilioOn call
  1. Beacon → ClickHouseA rule returns a row

    The alert is Pending, then Firing after the rule's pending_for.

  2. BeaconGroup

    Into an open incident that covers the resource or its parent, or one of the same rule. Otherwise a new Internal incident.

  3. Beacon → ChatPost

    Every new incident, whatever its severity.

  4. BeaconWait 90 s

    When the resource has a parent, so a host's alert can absorb its machines'.

  5. Beacon → TwilioCall the first responder

    High and Critical only, with an email to all. The next one after 2 min (Critical) or 5 (High).

  6. Twilio → On callThe phone rings

    A new round every 15 minutes until someone acknowledges.

  7. Twilio → BeaconAnswered

    An answered call acknowledges the incident as that responder.

  8. BeaconResolve

    Only an Internal incident Beacon created resolves itself. Otherwise a person does.

A customer is toldOne failing site is not a Beacon alert

BenchPilotWebhooksCentralTeam
  1. Pilot → BenchPing every 15 s

    pilot-monitor. A site that fails for 1 minute is down; CPU, memory or disk over the limit for 5 minutes is a breach.

  2. PilotRaise an event

    site_unavailable, backup_failure, migration_failure, certificate_expiry, resource_limit_breached…

  3. Pilot → WebhooksDeliver

    To each [[webhook_endpoints]], signed with HMAC, and to mail. This works without Frappe Cloud.

  4. Pilot → Centralreport_pilot_event

    X-Pilot-Token. Central accepts only its fixed list of event types from a Pilot.

  5. Central → TeamNotify

    In the console and by email.

An image is builtCargo hands images over as tags

GitHubCargoAtlasBuild machineCentral
  1. Cargo → GitHubEvery 2 hours

    The newest Pilot release, and the head of each Frappe branch Cargo follows.

  2. Cargo → AtlasRent a machine

    On the base Ubuntu image, as tenant 0.

  3. Cargo → Build machineprovision.sh, over SSH

    User frappe, Pilot, default-bench, site.local, production mode, the domain program. No secret in its environment.

  4. Cargo → AtlasStop, then snapshot

    Tags: purpose=pilot, pilot_version, frappe_version, has_site. Base and Apps images keep a memory snapshot.

  5. Central → AtlasList images by tag

    When a server is created. Cargo never tells Central about a Pilot image.

  6. Cargo → AtlasRetire

    Cargo keeps the 3 newest builds.

Two of these go opposite ways on purpose. Beacon pages Frappe's staff when many servers fail together: 3 sites and 20% of a server, or 5 servers and 10% of a region. One failing site is told to its owner, through Pilot and Central. Neither path reads a bench log.

0707 / L’angle mort

The platform watches the machine. Not the bench.

That is a design, not an oversight. A platform should not read its customers' logs. Atlas measures a machine from its edge, Pilot reports that sites answer, Beacon looks for many servers failing at once.

What is left over is exactly what #136 chose. On a customer's server, nothing else collects it.

The platform can look in.

Staff with access to a host can snapshot a server's disk or mount it in rescue mode, and the serial console's last 128 KiB are kept. A guest agent in every image answers the host over vsock, which a firewall in the machine cannot block. None of that reads a log, but a tenant's risk register should say it.

The server holds keys.

Any process outside the bench's sandbox can ask 169.254.169.254 for the server's X-Pilot-Token, and with it reach the team's billing methods at Central. The Datum token, the backup bucket's keys and the mailbox password sit in files the bench user reads.A process that is not Pilot reads the metadata → an alert

0808 / Les ponts

Connect, don't rebuild.

The reading turned three vague bridges into a list with costs. Planned, cheapest first. None is built yet.

  1. Recognise the ground.

    [central] enabled in common_config.toml and fc_team in common_site_config.json say “Frappe Cloud v2” and name the team. Not pilot_endpoint: a self-hosted Pilot writes it too.

  2. Stay quiet about what the platform does.

    The web console signs in as root from a host-side address. Pilot posts to the telemetry address every minute and restarts an idle bench after 900 seconds. A frozen trial server is not an outage. None of it is an incident.

  3. Take Pilot's events from Pilot.

    Pilot posts every bench event to any [[webhook_endpoints]], signed with HMAC. A Wolf endpoint for them gives deployments and failed backups with nothing from Frappe, on a self-hosted Pilot too.

  4. Register without a shared secret.

    A site can ask its own Pilot for a team identity token: 5 minutes, signed by Central, for any audience. A hosted Wolf checks it against Central's public keys and knows which team is calling.

  5. Show the platform's incidents as context.

    The status page's get_status is open. A Wolf incident can say that the region reports trouble since 01:52, without opening anything.

  6. A Beacon channel, with two guards.

    page_on_call pages at any severity, and a Responder key can probably publish. So: never page below critical, never set the visibility.

Closed, for now

  • Write Wolf's findings to Datum

    Datum accepts three issuers, and a customer holds none of them. And the repository has no license.

  • Read Datum

    The ClickHouse passwords are staff's, and a reader sees the whole region.

  • Read a server's events from Central

    No customer token, no outbound webhook. The activity feed is in the console only.

  • Report an alert through Pilot's token

    It is Pilot's credential, with a fixed list of event types. Using it from Wolf would be impersonation.

  • Install the agent at creation

    user_data is stored in clear on the action's record. Only a short-lived, single-use token could go there.

0909 / Les corrections

The code corrected us. And its own documents.

Three reviews (#133, #134, #135) were written from each repository's documents and a first pass on the code. Reading both ends of every call changed them. What we had wrong, or half right:

  • “Central writes fc_team on the server.”

    Central writes it to the machine's metadata. Pilot merges it once, at first boot, without ever naming it.

  • “Pilot calls five methods of Central.”

    More than forty: billing, mailbox sign-in, GitHub repository tokens, storage regions, the trial lock.

  • “The firewall allows outbound traffic by default.”

    It is off by default, which allows everything, both ways.

  • “Machine metrics are taken from outside.”

    Partly. A guest agent in every image adds load, memory and the state of systemd.

  • “A tenant machine sends counts only.”

    A failed backup sends the site's name. A failed update sends up to 8,192 characters of output.

  • “Reading Datum needs a row policy.”

    There is none. Beacon's reader and Insights see every tenant of the region.

  • “Datum trusts Central, Atlas and Cargo.”

    It trusts Cargo's address, which republishes the other two.

  • “A trial server sleeps.”

    And it is locked: no SSH, no console, no Admin until the trial is converted.

Where their documents lag their code

Eleven gaps, listed in the analysis. Three of them would have misled an integration:

  1. Enrolment.

    Central's specification describes a bootstrap token exchanged at first boot. In code the durable token is in the metadata, and the function that would mint a bootstrap token has no caller.

  2. The log shipper.

    Pilot's production guide says setup installs one. There is none; its architecture page says so.

  3. The receiver.

    Cargo's contract with Central names an address and two status values that no longer exist.

1010 / Le terrain

A map is not the territory.

Everything above was read, not run. Dokos is moving its hosted customers to its own Frappe Cloud v2 tenant. The first server there has questions to answer before any of the bridges is built.

  • The paths

    default-bench, logs/ or logs/workload/, and what the nginx log holds as the client for a region name and for a custom domain.

  • Lite mode

    Which log files exist with one process for web, realtime and jobs, and where a failed scheduled job is written.

  • Names

    The site's folder is site.local; its public name is elsewhere. What wolf-agent discover reports.

  • The markers

    [central], [telemetry], fc_team. And that no file holds the X-Pilot-Token.

  • Logins

    auth.log for a key added in the console, a web console session, and “open bench”.

  • The way out

    HTTPS to the Wolf site with the firewall off, then on. The private network between two servers of one team.

  • Sleep

    Whether a paid server ever freezes, and what the agent's spool does across a jump of the clock.

  • First passwords

    Whether two servers of one image share the Admin and Administrator passwords.

  • A snapshot

    File systems freeze for up to 30 seconds. What a log reader sees.

  • Pilot's webhooks

    The events and their bodies, towards a test receiver.

  • The team identity token

    From a site, for a test audience, checked against Central's keys.

  • The status page

    The shape of get_status, and whether one region can be told from another.

What we noticed about the platform itself is in the analysis, as notes for a tenant's risk register: an unsigned self-update at 00:00 UTC, a registry that merges by itself, tokens of 365 days, no key rotation yet. They are read from code, not reported and not tested.
