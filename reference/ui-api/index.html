Reference

UI API

The read and action APIs behind the Wolf UI at /wolf, their arguments, answers and access rules.

These are the APIs behind the Wolf UI (/wolf, #19). They need the Wolf User, Wolf Manager or System Manager role, and apply the caller's access rules inside the query (see Access). Answers are not cached per user, so each one is the caller's own; two reads share a short cache filtered per caller (see Short cache).

AreaMethods
Home pagesecurity_overview.get_overview
Operationsscope.get_counts, scope.get_inventory
Incident pageincident_view.list_incidents, get_incident, get_timeline, act, merge_preview, split_preview
Dashboardsdashboard.get_signals, get_http, get_monitoring
Explorersexplore.list_events, list_error_groups, get_error_group
Securitysecurity.list_sites, get_posture
Regulatory reportingcompliance.get_report
Response actionsresponse.get_response, approve

Every method is under dodock_wolf.api., for example /api/method/dodock_wolf.api.scope.get_counts.

Common arguments

Time window

ArgumentMeaning
rangeRelative window ending now: a number and m, h or d, such as 15m, 24h, 7d. Default 24h.
since, untilExplicit window, ISO 8601. A time without an offset is read as UTC, as in the agent protocol. until defaults to now and needs since. They win over range.
  • A relative window is measured in real time: across a DST change, 24h is 24 hours, not 23 or 25 hours of wall clock.
  • Windows longer than 400 days, or with since after until, are refused.
  • The Desk overview APIs (api/ui.py) accept the same range values.

Every response that reads a window returns what it actually read, in UTC:

window
"window": {"since": "2026-10-29T13:00:00Z", "until": "2026-10-30T13:00:00Z", "relative": "24h", "time_zone": "Europe/Paris"}

time_zone is the site's. Stored times are in that zone. The UI converts with it, never with the browser's zone.

In the Wolf UI, the window is in the URL (?range=7d or ?since=…&until=…). A range selected on the HTTP chart of a dashboard becomes an explicit since/until: the dashboard's counts and chart, and the event and error explorers opened from it, are read with it. Back to a relative window drops it.

Scope

site, bench and host narrow a query to records with those values.

bench needs host. Bench names such as frappe-bench repeat across hosts, so a bench alone is ambiguous and refused.

Access

A restricted Wolf User, one with Wolf User Scope rows, gets counts and inventory over the records they may see, and "restricted": true.

A Wolf User without any Wolf User Scope row is not restricted: they see everything, as in Desk. That is the current rule, kept as is.

Home page

The Wolf UI opens on the security of the bench (/wolf, Overview). The general overview it used to show is Operations (/wolf/operations), below.

dodock_wolf.api.security_overview.get_overview

No argument. One answer with a key per panel, each within the caller's access. A panel the caller may not have is null; a panel that could not be read is {"error": "…"} (the reason goes to the Error Log) or {"forbidden": true}, and the others are still answered. satellite is true on a satellite, which records no score and keeps no incidents: scores, incidents and responses are then null, and the page says that the scores are kept on the central site.

PanelWhat it reads
scoresThe stored security_score of each site the caller may see by a site grant, as on the Security page (a score is stored with its site's host, but a host grant does not show it): the newest sample of the last 7 days, never recomputed. change is the difference with the newest score of 23 to 25 hours earlier, null when there is none or when the newest score is not newer than 23 hours (it would be compared with itself). late when the newest is over 3 hours old (the job is hourly). Worst first; a site the Security page knows but that has no score yet comes last with score: null, never 0.
incidentsOpen or Acknowledged incidents holding at least one event of type security, merged ones excluded, under the incident access rules. Exact counts, and the 5 newest. null on a satellite, which keeps no incidents.
responsesWolf Response Actions Approved and not expired (waiting for the agent or satellite that applies them) and Failed in the last 7 days, with the 5 newest. The label of a user action waiting for a satellite names its site. Wolf Managers and System Managers only.
journalThe newest signed entry, the entries waiting to be signed and the oldest of them. behind when one has waited over 5 minutes (signing runs every minute). Wolf Managers and System Managers only.
agentsAgents and satellites per state, as on Monitoring, and the reporting hosts whose last setup check found a failure or a warning.

Operations

The general overview, at /wolf/operations. Observability is frozen (#136): it is kept as it is.

dodock_wolf.api.scope.get_counts

Exact counts for Operations and the entity dashboards. Arguments: window and scope.

get_counts
{
  "window": {...},
  "scope": {"host": "bench-01"},
  "restricted": false,
  "incidents": {
    "unresolved": 60, "unacknowledged": 40, "critical_unresolved": 7,
    "by_status": {"Open": 40, "Acknowledged": 20},
    "by_severity": {"info": 0, "warning": 53, "critical": 7},
    "sites_with_unresolved": 1, "unresolved_without_site": 5,
    "opened_in_window": 61, "resolved_in_window": 1,
    "basis": "..."
  },
  "events": {"records": 12, "occurrences": 140, "by_type": {"error": {"records": 3, "occurrences": 90, "by_severity": {...}}}, "basis": "..."},
  "agents": {"agent": {"fresh": 3, "stale": 1, "never_seen": 0, "disabled": 0}, "satellite": {...}, "silence_minutes": 5, "basis": "..."}
}
PartRule
incidentsunresolved counts Open and Acknowledged incidents now, whatever the window. unacknowledged is Open only. Merged incidents are excluded. unresolved_without_site counts host- or bench-wide incidents, which have no site. opened_in_window and resolved_in_window use started_at and resolved_at.
eventsrecords are Wolf Events first seen in the window. occurrences sums their reported count. A deduplicated record keeps counting repeats, including repeats after the window, so occurrences is not a count of occurrences inside the window.
agentsAgents are hosts, so site and bench do not filter them. A satellite is not a host and is counted apart; with host, it counts when one of its registered benches runs on that host. fresh means seen within the agent silence threshold of Wolf Settings, the same rule as the Desk overview's online flag.

dodock_wolf.api.scope.get_inventory

The hosts, benches and sites the caller may see. Argument: days, the telemetry window (default 7, at most 90).

get_inventory
{
  "hosts": [
    {"host": "bench-01", "sources": ["agent", "events", "metrics"], "last_seen": "2026-10-30T12:59:30Z",
     "benches": [{"bench": "frappe-bench", "host": "bench-01", "sources": [...], "last_seen": "...",
                  "sites": [{"site": "a.example.com", "sources": [...], "last_seen": "..."}]}],
     "sites": []}
  ],
  "unplaced_sites": [],
  "note": "Hosts and benches come from agent registrations and from telemetry in the window. ...",
  "days": 7,
  "restricted": false,
  "as_of": "2026-10-30T13:00:02Z"
}

as_of is when the registrations and telemetry were read: they are cached for a few seconds (see Short cache).

SourceMeaning
agent, satelliteWhat an agent declared when it registered.
eventsBy when they last happened, so a recurring deduplicated event keeps its site listed.
metricsRollups.
incidentsUnresolved ones, whatever their age.

A registration names every site of a bench; a restricted user sees only the granted ones. Neither kind of source is complete on its own: a bench added after its agent registered appears once it sends telemetry, and a quiet site only through its agent's registration. The UI shows sources and note rather than presenting the list as complete.

  • A bench is always under its host.
  • host.sites holds sites seen on a host whose bench is unknown.
  • unplaced_sites holds sites seen without a host, for example a satellite with no host information. They are not attached to a guessed host.
  • Times are UTC.

Incident page

dodock_wolf.api.incident_view.list_incidents

Incidents the caller may see, newest first.

ArgumentMeaning
statusunresolved (default), resolved or all.
site, bench, hostScope.
limitAt most 200.
cursorContinues a page.

Pages follow (started_at, name), so two incidents started at the same second are neither repeated nor skipped. Returns incidents, paging (has_more, next_cursor) and time_zone.

dodock_wolf.api.incident_view.get_incident

The incident header in one call: title, status, severity, scope, start, acknowledgement, resolution and owner, rule, silence, notification and escalation times, merge and split links, and the timeline window.

FieldMeaning
deploymentTime of the deployment before the incident, with available: false when retention deleted its event but the incident kept the time.
event_recordsLinked Wolf Events. event_count is the same number, as on Wolf Incident.
event_occurrencesThe occurrences they report, repeats included. A different number from event_records.
canWhich actions the caller may take.
regulatorySee Regulatory reporting.

Wolf Users read and comment. Wolf Managers also acknowledge, resolve, take the incident, and:

  • merge: the incident is not merged;
  • split: not merged, and at least two events are linked (one must stay);
  • postmortem: not merged, and either resolved or already has one (postmortem names it).

Each matches the check the action itself makes.

dodock_wolf.api.incident_view.get_timeline

One page of the timeline, oldest first.

ArgumentMeaning
incidentThe Wolf Incident.
limitDefault 100, at most 500.
cursorContinues a page.
familiesComma-separated subset of the families below.
FamilyRows
evidenceWolf Events linked to the incident, at any time.
contextOther events in its scope (site, the same bench on the same host, or host-wide) during its window, if the caller may see them, and the deployment before it even when that is older than the window. When the incident took events from other scopes (by IP or user, or a sequence rule), also the deployments and health events (error, cron_failure, worker_failure, host_metric_alert) of those scopes in the window: of the site; of the bench on its host; on a host, its host-wide events and its benches' deployments and failed crons and workers, not its sites' Error Logs. At most 10 such scopes, the same on every page. An incident with no site, bench or host has only that second kind, in Desk too. A user who may read one of those scopes but not the event that brought it in can still tell, from its rows, that the incident reached it.
activityStatus changes, assignments, comments and notes, from Frappe's Version and Comment history.
deliveryNotification attempts (Wolf Delivery).

Each row has a stable id, family, kind, at (UTC) and a plain-text summary. Ids: event:<name>, activity:comment:<name>, activity:version:<name>:<field>, delivery:<name>, deployment:<incident>.

Per kind:

KindFields
Eventsrelation: linked, context or preceding_change (the deployment before the incident, never called its cause). count, first_seen and last_seen describe a deduplicated record: one row, not one row per occurrence. details is the event payload, for display as text. source_label says who raised it (Wolf agent, Wolf site, Suricata, Wazuh). duplicate_of names another source's event about the same finding, seen first (overlapping detectors in both mode); its row id is event:<duplicate_of>.
Activityuser_name. Comments and notes come as plain text, never HTML to render.
Deliverieschannel, action, target, result and http_status. result is accepted when the endpoint took the message, which does not mean a person read it.
  • Rows are ordered by time, then events, activity and deliveries, then id. Rows with the same time have no causal order.
  • paging.next_cursor continues after the last row. The same rows come back once each, whatever the page size.
  • Activity keeps the newest 200 recorded changes and 300 comments. truncated.activity_version and truncated.activity_comment report when older ones exist.
  • window is the incident's window: start minus padding_minutes, to its resolution or now. It is the same window Desk and the postmortem use.

dodock_wolf.api.incident_view.act

POST incident and action, one of acknowledge, resolve or assign_to_me. It runs the incident's own method, so Frappe's write permission applies, and returns the new get_incident.

The incident's state is checked first:

  • acknowledging needs an Open incident;
  • resolving or taking needs an unresolved one;
  • merged incidents refuse every action.

A page left open on a stale incident gets an error instead of reopening it.

dodock_wolf.api.incident_view.merge_preview

Arguments: source, and optionally target. Wolf Managers with write permission only. Nothing is written.

  • candidates: where the source may go. These are unresolved, unmerged incidents the caller may read: the newest 50 (more_candidates says when there are more), the source's site first, then its bench.
  • preview, for a target:
    • error: the merge's own refusal (itself, a merged incident, no write permission) or null;
    • the events and comments that would move;
    • target_after: severity, start and status, once the target covers both;
    • source_after: Resolved, merged into the target.

The merge itself is dodock_wolf.api.incident.merge (POST source, target), which checks again.

dodock_wolf.api.incident_view.split_preview

Arguments: incident, and optionally events (a JSON list of Wolf Event names). Wolf Managers only. Nothing is written.

  • events: the linked events, oldest first, at most 500 (more_events).
  • preview, for a selection:
    • error: the split's own refusal (nothing ticked, an event not linked, all of them ticked) or null;
    • moved and kept;
    • new_incident: title, severity, start and status. It is Open, or Resolved when the source is. It has no alert rule, so nothing resolves it by itself.

The split itself is dodock_wolf.api.incident.split (POST incident, events, title). The postmortem is created by dodock_wolf.api.incident.create_postmortem and edited in Desk.

Dashboards

dodock_wolf.api.dashboard.get_signals

The newest value of every signal series in scope (site, bench with host, host): one series per metric, host, bench, site and label. Each series has a state:

StateMeaning
firingAn enabled rule on this metric applies to the series and has an open incident for its scope and, for rules grouped by label, its label (incidents). A firing series whose samples stopped stays firing, with stale: true.
staleSamples stopped: none in the last 2 hours, or none for three collection intervals, at least 5 minutes (backups: 30 min). The old value is not presented as current. The cadences are the agent's defaults: an agent set to probe TLS or backups less often looks stale sooner.
watchedRules apply (rules: aggregation, operator, threshold, window) and none has an open incident.
unwatchedA value, but no rule watches it. The dashboard does not invent a threshold.
FieldMeaning
missingSignals with no series at all in the last 7 days: not collected for this scope, not set up, or not available here. They are never shown as zero.
countsExact states per group, whatever the 300-series limit.
emailEmail queue problems the site recorded about itself in the last 24 hours.
as_ofWhen the series were read (see Short cache). Rules, incidents and states are read with each request.

A restricted user sees what each rule checks, but not the host, bench or site filters it names. The metric meanings (unit, kind, cadence) are in wolf/catalog.py.

Short cache

get_inventory and get_signals, the overview's two slow reads, keep what they read for wolf_read_cache_seconds: site config, default 30 (an agent's push interval), 0 turns it off. get_inventory caches its registrations and telemetry triples, get_signals its series (newest value and last time seen).

The cached value is read without access conditions and is the same for every caller. Each request then keeps the rows its caller may see, by the rule of wolf/scopes.py. A cached value never carries one user's grants to another.
  • Rules, open incidents and the email queue are read per request: a signal's state follows an incident at once.
  • A value is fresh for wolf_read_cache_seconds. Older, and up to 4 times that (2 min by default), it is still served at once, and one background job (deduplicated, short queue) reads it again. Older still, or missing, the request reads.
  • Between visits, the scheduler reads again, every minute, the values asked for in the last 10 minutes (10 at most per site) that are no longer fresh (read_cache.refresh_active). It needs scheduler_tick_interval at 60 (see Install the Wolf App): at Dodock's default 4 min tick, a visit after 2 quiet minutes reads.
  • A series that starts, or a value that changes, shows up a minute or two later at most. as_of says when the data was read. A live update refetches, and may get the cached value.
  • A change of wolf_read_cache_seconds takes effect within a minute: Dodock's web workers keep the site config in memory for up to 60 s.
  • There is one cached value per site and per scope (get_signals' site, bench and host; the inventory's days): a dashboard of another scope has its own.

Measured effect: Performance.

dodock_wolf.api.dashboard.get_http

Requests, 5xx and 502 per bucket over the window. Arguments: the common window and scope arguments.

  • Values are summed across labels and read at the resolution of the window (resolution).
  • Only whole buckets are read (window; requested_window is what was asked): the bucket still filling shows once it closes, instead of drawing a drop in traffic.
  • 502 is part of 5xx and is never added to it.
  • A bucket without samples is null: a gap, not a zero. has_data tells "no data" from "zero".
  • deployments lists the deployments in the requested window. On a site's dashboard that includes deployments recorded for its whole bench (no site), as incidents link them.

dodock_wolf.api.dashboard.get_monitoring

Whether Wolf itself works: the site's health (rules, scheduler, ingest queue), rollup watermarks, every agent and satellite with its state, last contact, clock skew and version, its setup (the agent's last wolf-agent doctor run: checked_at, failed, warnings, and the problems with their fix), and this site's mode. Each part is reported on its own.

An online agent says nothing about its watchdog's fallback channel.

Explorers

Wolf Events are deduplicated: one record holds its first time (first_seen), last time (last_seen) and the number of repeats it absorbed (count). Explorer lists are lists of records. They never say how many times something happened inside a window when a record spans the window's edge, and each response says so in basis.

Searches (q) match a plain substring of the title, at most 100 characters: % and _ match themselves, and there is no regex.

dodock_wolf.api.explore.list_events

Event records active in the window (first seen before its end, last seen after its start), newest first, paged by (first seen, name).

ArgumentMeaning
range, since, untilWindow.
site, bench, hostScope.
event_type, severity, categoryFilters.
qTitle substring.
limitAt most 200.
cursorContinues a page.
entitySecurity events naming an entity (below).

Payloads are not in the list: get_event(name) returns one record with its payload.

entity keeps the security events of every source (Wolf, Suricata, Wazuh) that name it: ip:203.0.113.5, host:erp-01, site:erp.example.com or user:jane@example.com. Values are normalised and resolved through the aliases. For example, host:erp-01 also finds the Wazuh alerts of the agent named wazuh-erp01 when an alias says they are the same host. dodock_wolf.api.entities.find(entity, ...) is the same list. The response echoes entity.

dodock_wolf.api.explore.list_error_groups

Groups of error records, by fingerprint, that have a record active in the window, latest first. The window and q choose the groups. Their figures cover every record of the group the caller may see, whatever its age, as on the group's page, so a recurring error is not presented as new:

  • records, and records_in_window;
  • occurrences, the sum of the records' counts;
  • first_seen and last_seen;
  • the number of sites, and whether some records are host-wide;
  • the number of linked incidents;
  • the title of the most recently seen record, which stands for the group.

A fingerprint includes the site unless the agent sends its own, so most groups concern one site.

dodock_wolf.api.explore.get_error_group

Every visible record of one group, whatever its age:

  • where it happened, by site, bench and host;
  • the incidents it is linked to that the caller may read (incidents_not_visible counts the others);
  • its most recently seen record with the payload: the representative traceback, the same record the list shows;
  • its 50 most recently seen records.

A restricted user sees only the records of their sites, benches or hosts, and counts over those.

Live updates

The Wolf UI stays current over Frappe's own socket.io server (dodock_wolf/wolf/live.py, frontend/src/services/live.js). The server never pushes telemetry. It sends an invalidation, the event wolf_invalidate, and the page fetches again through the APIs above, which check permissions as usual.

RoomJoined withFrappe checksMessage
doc:Wolf Incident/<name>doc_subscriberead permission on that incident (Wolf User Scope applies){"kind": "incident", "incident": "<name>"}
doctype:Wolf Incidentdoctype_subscriberead permission on the DocType{"kind": "incidents"}
doctype:Wolf Eventdoctype_subscriberead permission on the DocType{"kind": "events"}
  • Sent when: an incident is created, saved, updated by the engine (new linked events, reopen, auto-resolve, silence, escalation, assignment, postmortem) or deleted; a comment on an incident is added, edited or deleted; a delivery is recorded; an event is stored.
  • At most one message per room and transaction, after commit. The bookkeeping is cleared on commit and on rollback, so a job that commits many times announces each transaction and a rolled-back one announces nothing. List messages are also throttled to one per 5 s per kind. One held back is marked after commit and sent by flush_live_updates (every minute): a committed change can be delayed, never lost.
  • No names in list rooms: a restricted reader only learns that something changed somewhere.
  • Boot: capabilities.realtime gives namespace (/<site>), port (socketio_port, for bench start), dev_server and poll_seconds. Behind nginx the socket uses the site's own origin (/socket.io is proxied, as for Desk).

What each page does with a message:

PageOn a messageWithout a socket
IncidentHeader refreshed. New timeline rows are added without scrolling, and a "N new rows: show" button takes the reader to the first one. Loaded rows and expanded rows stay. Past 500 loaded rows only the header follows and the rows wait for Refresh.Polls every 60 s
IncidentsRefreshed, unless "Load more" was used: then "Incidents changed · Refresh".Polls, same rule
Home page, Operations and dashboardsRefreshed at most every 10 s (messages carry no scope; relative windows move). Also polled every 60 s while live, because metrics are not announced.Polls
Events, ErrorsNever reshuffled under the reader: "New events recorded · Refresh" (the new events may not match the filters).Not polled: "Not live: refresh by hand"
  • Every page reconciles once when the socket first joins its rooms (what changed after its first fetch is unknown) and after each reconnect (messages sent while offline are lost).
  • A page that does not reload by itself shows "Reconnected, changes may have been missed · Refresh" after a reconnect. A poll or the first connect never claims a change.
  • Pause holds messages, and the page says changes are waiting, until Resume.
  • Every refresh, the reader's included, goes through one queue: never two at once.
  • Polling skips hidden tabs.
