Performance

Load test results at 100 hosts for 7 days, what changed to reach them, and how to run the test again.

The target is the "done when" of #10: a synthetic load of 100 hosts for 7 days keeps push p95 under 200 ms and the overview under 1 s.

It was measured on 2026-11-01, three times:

  • first as #55 found it;
  • then after the row order and inventory index of #56;
  • then after #57 moved the remaining reads to SQL (see What changed).
All runs used synthetic data and a demo bench, not production observations.

The page time runs from navigation start until every panel is drawn, in Chromium on the bench (see The page in a browser). Without the cache its median is under 1 s, its p95 is not. With the cache, and with it read again in the background (see The short cache), visits after 45 s and 150 s idle were all served from it. A visit that still reads takes the time without cache:

  • the first of the day;
  • a scope nobody opened for 10 min;
  • the scheduler at its default 4 min tick.

In short, from the README:

  • Push p95 is 108 ms over HTTP.
  • Metric rows are stored in metric and time order, and the inventory reads an index alone.
  • Reads of known metrics scan the primary key by name range, chart buckets are summed in SQL, and the newest value of each series is picked in one pass.
  • The Wolf UI overview went from 13 to 24 s down to 1.5 s, then 0.73 s for its slowest read.
  • In Chromium, the whole page is drawn in 0.9 to 1.0 s at the median and 1.0 to 1.3 s at p95, and in 0.53 s (p95 0.61 s) when the inventory and signals come from their 30 s cache (wolf_read_cache_seconds, shared by every caller and filtered per caller).
  • The cache is read again in the background, so pages opened 45 s or 150 s apart all came from it (max 0.65 s), showing data 11 to 51 s old.

What changed

Row order and inventory index (#56)

Row order. InnoDB stores a table's rows in primary key order, and Frappe's primary key is name.

  • Before, metric samples got a random name and rollups a hash of their key. One metric's day was spread over the whole table, and each row of a read was a page read of its own.
  • Now names start with the resolution, a 6-character hash of the metric and the time, then end with a hash of the key (storage.rollup_name, sample_name). A time range of one metric is read from neighbouring pages.
  • Rows are inserted in name order, so InnoDB fills its pages instead of splitting them in the middle.

Inventory index. get_inventory asks which host, bench and site sent anything in a range.

  • MariaDB answered through (resolution, metric_name, bucket_start), then fetched every row of the range.
  • (resolution, bucket_start, host, bench, site) answers it from the index alone.
  • It replaces (resolution, bucket_start), which it starts with. That index served the rollup job and the purge, and still does. bucket_start loses its own index too: no read filters it without a resolution.

A first try put the full metric name in the row name (61 characters). That made the rollup table 50 % bigger and filled the bench's disk:

  • every secondary index entry repeats the primary key;
  • rows of one bucket arrived in hash order, so pages split in the middle.

The names are now 33 characters for rollups and 28 for samples, against 32 and 12 before.

Table (data + indexes)BeforeAfter
Wolf Metric Rollup7.2 GB for 15.2 M rows7.3 GB for 15.5 M rows

On an existing site:
  • bench migrate creates the index and drops the two it replaces. On 15 M rows, that took 1.5 min.
  • Rows already stored keep their names, so a read speeds up once its window holds only new rows: after a day for the 24 h reads of the metrics explorer (removed in 0.2), 7 days for the hourly reads.

SQL reads (#57)

  1. Name ranges. A read of known metrics scans one primary key range per metric (rollups.name_passes): rows of one metric and resolution sit together in the key since #56, so a window is a stretch of it. No row is looked up through a secondary index. Postgres does not store rows in key order and keeps one plain read.
  2. Chart buckets in SQL (rollups.bucket_cells). The metrics explorer, removed in 0.2, read one metric's 144 k minute rollups twice, for the totals and the chart, and merged them in Python. It now reads one row per host and bucket, summed by the database; the totals are the merge of those.
  3. Last values in one pass. The value at each series' newest time came from a join of the rows with their own group-by. On fresh data MariaDB turned that join into a lookup per series, each walking all of its metric's minute rollups: get_signals took 194 to 233 s (two runs). row_number() over each series reads the rows once: 0.62 s.
  4. Host chart index. (resolution, host, metric_name, bucket_start) replaces (resolution, host, bucket_start): Desk's host chart (removed in 0.2, with the host resource metrics) read four metrics of one host, no longer all fifteen.

The 194 s were missed at first. #56's "after" reads ran on data 40 to 45 min old, and a later run on data 85 to 103 min old: get_signals reads the last 2 h, so it saw part of its window. One read of 243 s in that later run, taken for an outlier, was this. Only a full run on fresh data showed it on every read.

Rows named before #56. Their names are 32 hex digits and sort below every new name, outside the name ranges. While some remain, a second pass reads them (name < 'g'), and MariaDB weighs it against the indexes. Measured with the 153 k minute rollups of one metric's last day renamed to old names, the metrics explorer (removed in 0.2) over 24 h:

Second passPlanMedian
name < 'g'primary key, old rows only770 ms
left(name, 1) < 'g' (a function: indexes only)(resolution, metric_name, bucket_start)1,145 ms

With millions of old rows, the primary key range would cost more than the index and the optimizer takes the index. The plain range stays. Old rows go with retention: 30 days for minute rollups, 365 for hour rollups, by default.

Data and machine

Data, written by ci/load_test.py on a throwaway site:

  • 100 hosts × 15 metrics × 7 days, samples every 30 s;
  • raw samples for the last 48 h (8.7 M rows);
  • 1-minute and 1-hour rollups before that, then the real rollup job over the raw window (15.3 to 15.5 M rollups);
  • 16,900 events (one per host per hour).

How it compares with a real site:

  • Rows are named as the app names them. #55's run named its synthetic rows in sequence, so in time order. Only the last 48 h, written by the rollup job, had the scattered layout of a real site. A real site was therefore slower than #55 measured, not faster.
  • All hosts' samples of one instant go in at once, in name order. Real pushes arrive host by host and a little out of time order, so a real sample table is somewhat less dense than this one.
  • The data end when loading starts, and read windows end when they are read:
    • the full run read 20 to 35 min after the newest data;
    • #56's "after" reads (--reads-only, once the index was in) read 40 to 45 min after it;
    • #57's run loaded everything again and read straight after, like the first.

    Between the two runs, reads the index does not touch moved by 11 % at most. --reads-only refuses data over 2 h old.

Bench: the demo stack in Docker, on 4 vCPU and 15 GB RAM:

  • Dodock 5.18.8;
  • gunicorn, 2 workers × 4 threads;
  • MariaDB 10.6 with its default 128 MB innodb_buffer_pool_size.

Loading took 34 min, down from 75 (#56), then 20 min (#57). The rollup job caught up on 48 h of raw samples at once in 12.5 min, down from 32, then 9.5 min. A running site never does that.

#57's numbers were taken before its review fixes. Those keep only the charted groups' buckets in memory and let get_http use name ranges: neither adds a read.

The page in a browser

frontend/scripts/page-time.mjs opens /wolf in headless Chromium 153, logged in, through the bench's nginx. A page is ready once its six reads have answered and no panel says it is loading. Two series of 10 runs each:

  • cold: a new browser context each time, so the app's scripts and styles are fetched again;
  • warm: the same tab navigating again, with its cache.

Where the time goes, at the median of a cold page:

  • 0.21 s before the first read: the app's scripts, then its session check.
  • 0.57 s of reads. They go out at once and overlap well:
    • get_inventory, 0.56 s, and get_signals, 0.51 s, set the length;

So the p95 goes over 1 s by up to a quarter of a second, in the two slow reads and in drawing.

The demo's nginx serves one site whatever the host name (wolf.localhost). The measurement used a second nginx in the same container, on another port, with the same configuration set to the load site. A first run through the demo's own nginx timed the demo site, not the load: it is not counted.

The short cache

get_inventory and get_signals keep what they read for 30 s (wolf_read_cache_seconds, wolf/read_cache.py). The cached value is read without access conditions, shared by every caller, and each request keeps what its caller may see (see UI API). Rules and incidents are read per request.

Read again in the background

A cached value is fresh for 30 s. Up to 2 min old, it is still served at once while one background job reads it again; and every minute the scheduler reads again the values asked for in the last 10 minutes. Timed on another fresh load, with the load site's scheduler on and scheduler_tick_interval at 60, one cold page every 45 s, then every 150 s (6 visits each), in ms:

/wolf, page readyp50p95maxget_inventory / get_signals, p50
Every 45 s54864964936 / 78
Every 150 s56365465449 / 70
  • Every visit was served from the cache. At 150 s, past the 2 min a value is kept, only the scheduler's read could have kept it: without it, each of those visits would read (0.9 to 1.2 s, as without cache).
  • The data such a page shows is older. as_of sampled 8 times, 40 s apart: 11 to 51 s old, 40 s for most. A value read by the scheduler can be up to its minute plus a tick old; at most 2 min, after which a request reads.
  • A first try of the 45 s series had one 3.2 s page. It came right after bench clear-cache, run to register the new scheduled job, which empties all of Frappe's cache (its app shell took 1.8 s): it is not counted. On a site, bench migrate registers the job.

What is left

Each read is under 1 s, and so is the overview page when its two slow reads come from the cache.

  • A visit that reads still takes 0.9 to 1.2 s: the first after 10 quiet minutes on a scope, or after 2 minutes when the scheduler ticks every 4 min (Dodock's default; the install sets 60 s).
  • Drawing takes 0.13 to 0.32 s on the bench with every row. Drawing the first rows only halves it on a faster load bench (100 to 53 ms cold, 50 to 20 ms warm); the rest is the page's own. The 4 vCPU bench was not run again.
  • The metrics explorer over 24 h, 0.86 s, was the closest other read (the metrics explorer, removed in 0.2).

These margins are for 100 hosts on this bench. At several times that, the inventory and the 24 h reads grow with the rows of their window, and so does a visit that reads.

Not measured

  • A user's network: the page was opened on the bench itself, without latency.
  • Browsers other than Chromium, and slower machines than this bench's 4 vCPU.
  • Rows named before #56 at the scale of an upgraded site: only one metric's day was renamed.
  • Postgres. CI installs the app there, which creates the new index, but nothing was timed and the upgrade from the old indexes was run on MariaDB only. Postgres stores rows roughly in insertion order, which is already time order, so row names matter less there.
  • Several sites at once.
  • Rule evaluation of every preset at once.
  • Disk other than this container's.

Run it again

load_test.py deletes and rewrites the site's metric tables: never point it at a real site.

ci/load_test.py fills a throwaway site with N hosts × M metrics × D days and times push and the overview. CI does not run it. At 100 hosts × 7 days it writes about 20 M rows, which takes 15 to 25 minutes on a GitHub runner before any timing starts. ci/load_http.py times the agent's push over HTTP on the same site. Since 0.2 it loads queue, Redis and database gauges where it loaded the host resource metrics, and no longer times Desk's host chart (both removed in 0.2): a new run is not comparable, row for row, with the Desk overview numbers above.

Load and time the reads

On a throwaway site of the bench, from sites/:

sites/
../env/bin/python /path/to/ci/load_test.py <site> --hosts 100 --metrics 15 --days 7
  • To time the reads again on the data already loaded, for instance after an index change, add --reads-only.
  • On a site loaded before, empty the three tables first (truncate). The script deletes its own rows one transaction per table, which on 20 M rows takes long and needs as much undo space.

Time the push over HTTP

sites/
../env/bin/python /path/to/ci/load_http.py <site> --url http://127.0.0.1:8000 --agents 100 --pushes 600 --concurrency 8

load_http.py comes second:

  • Its agents report as 100 more hosts (load-http-NNN), which the reads would then include. The next load_test.py run deletes them.
  • It raises the site's push limit for the run and puts it back afterwards.
  • Its p50 / p95 are over accepted pushes (HTTP 200) only. Every other status or connection error is counted separately.

Time the page in a browser

From frontend/, once yarn install has run:

frontend/
node scripts/page-time.mjs --url http://127.0.0.1:8080 --site <site> --password <admin password> --runs 10
  • --url is the bench's nginx. It must serve <site>: the demo's serves wolf.localhost only (see The page in a browser).
  • --path and --reads time another page: its path, and how many Wolf reads it sends.

In the CI container

Add -e WOLF_LOAD_TEST=1, and optionally -e WOLF_LOAD_ARGS="--hosts 20 --days 2", to the docker run ... integration.sh command of the integration job.
