Reference

Agent protocol

Every endpoint, field and status code the Wolf Agent, satellites and integrations use to talk to the Wolf App (protocol v1).

All traffic is HTTPS + JSON. All timestamps are ISO-8601 UTC strings (2026-10-29T02:00:13Z). The app converts them to the site's system time zone.

Responses follow the Frappe convention: the answer is under the message key.

Registration

POST /api/method/dodock_wolf.api.agent.register
POST /api/method/dodock_wolf.api.agent.register
Content-Type: application/json

{
  "registration_token": "<Wolf Settings → Registration Token>",
  "hostname": "bench-01",
  "kind": "agent",
  "agent_version": "0.1.0",
  "os": "Debian GNU/Linux 12",
  "benches": [{"name": "main", "path": "/home/frappe/frappe-bench", "sites": ["a.example.com"]}]
}
FieldMeaning
registration_tokenThe value of Wolf Settings → Registration Token.
hostnameThe host's name. For a satellite, its site name.
kindOptional. agent (default), satellite, or integration (see Wazuh integration).
agent_versionVersion of the sender.
osOperating system string.
benchesList of {name, path, sites}. A satellite adds host.

Response:

Response
{"message": {"agent_id": "WAG-0001", "agent_secret": "<random 40 chars>", "push_interval": 30}}

The response also carries server_version, the Wolf App version.

The secret is returned once. The agent stores it in /etc/wolf-agent/config.json (mode 0600). The Wolf site keeps only a salted hash (hmac-sha256$<salt>$<digest> on Wolf Agent), so it cannot show the secret again. Two things replace it:

  • re-registering the same hostname;
  • Rotate secret on the Wolf Agent form, which shows the new secret once.

Satellites

A satellite is another Frappe site running dodock_wolf in satellite mode (see Every site on a bench). It registers with hostname set to its site name and one bench entry carrying its real host:

Satellite registration
{"registration_token": "...", "kind": "satellite", "hostname": "b.example.com", "agent_version": "0.1.0",
 "os": "Linux-6.1...", "benches": [{"name": "frappe-bench", "path": "/home/frappe/frappe-bench",
 "sites": ["b.example.com"], "host": "bench-01"}]}

Refusals

  • A hostname already registered with another kind is refused.
  • A site in satellite mode refuses all registrations: register with its central site instead.
  • A wrong registration token is refused.
  • Registration is rate limited to 20 calls an hour.

Response actions

actions holds the blocks a Wolf Manager approved for this agent and that it has not yet reported:

actions
[{"id": "WRA-00001", "action": "block_ip", "ip": "45.33.32.156", "seconds": 86400}]

The agent sends each result with a later push:

action_results
"action_results": [{"id": "WRA-00001", "ok": true, "detail": "..."}]

An id is accepted once, and only from the agent it was given to. See Response actions and Security.

Ingest mode

Set in Wolf Settings → Ingest Mode.

ModeBehaviour
async (default)The app validates and normalizes the batch during the request, queues the inserts for a background worker and answers "queued": true. The worker inserts them and attaches the events to open incidents a few seconds later. A failure in the worker is not reported back to the agent: it is in the site's Error Log.
syncThe batch is stored during the request and queued is false. Storage errors fail the request (HTTP 5xx) and the agent retries.

If the queue is unreachable in async mode, the batch is stored as in sync mode. In both modes, the agent's last seen time and clock skew are recorded during the request, so heartbeats do not wait for the queue.

Rate limit

Pushes are counted per agent in one-minute windows: Wolf Settings → Max Pushes Per Minute, default 120, 0 = off. Over the limit the server answers HTTP 429. Agents and satellites treat 429 like a network error: the batch stays spooled and is replayed after a backoff.

Scrubbing

The agent removes e-mail addresses, credentials, card numbers and IBANs from event titles and payloads before sending (see Scrubbing). The server stores what it receives as is.

Clock skew

  • sent_at is stamped when the request is sent, also for replayed spool batches.
  • The server records sent_at - server time as the agent's clock_skew_seconds (positive = agent ahead, shown on Wolf Agent) and returns it. The agent logs a warning above 60 s.
  • Metric and event timestamps more than Wolf Settings → Max Clock Skew in the future (default 300 s, 0 = off) are clamped to the server time and counted in clamped.
  • Rule windows and charts also ignore rows stamped more than a minute in the future.

Status codes and limits

AnswerAgent behaviour
HTTP 401 / 403Bad credentials: the agent stops and logs.
HTTP 429Over the rate limit: treated as a network error.
HTTP 5xx or network errorThe agent keeps the batch in its on-disk spool and retries with backoff.

At most 5000 metrics and 1000 events per request. The agent splits larger batches.

Satellites

Satellites use the same endpoint with their satellite credentials.

  • They send no metrics.
  • At most 100 events per request.
  • Every event has explicit host, bench, site, fingerprint and count. Duplicates seen before forwarding are merged into one event.
  • An empty body every minute is their heartbeat.
AnswerSatellite behaviour
401 / 403Retry in 15 minutes.
Other 4xx (except 408 / 429)The batch is dropped.
5xx or network errorRetry after 1, 2, 4, 8, then 15 minutes.

Enrichment at ingest

  • IP reputation. With IP reputation enabled, a security event whose payload ip is on a downloaded blocklist gets reputation: {"listed": true, "lists": [...]} and one severity step more.
  • MITRE ATT&CK. Security payloads may carry attack_techniques, a list of technique IDs (T1110, T1552.001). The app adds mitre_attack, a list of {id, name, tactic} merging those IDs with the category's own mapping (see Security).
  • Entities. Every security event gets payload.entities, whatever its source: {"ip": [...], "host": [...], "site": [...], "user": [...]}, normalised and resolved through the Wolf Entity Alias rows. Agents do not send it: the site computes it.

Deployment marker

POST /api/method/dodock_wolf.api.ingest.deployment
POST /api/method/dodock_wolf.api.ingest.deployment
X-Wolf-Agent-Id: WAG-0001
X-Wolf-Agent-Secret: <secret>

{"bench": "main", "site": null, "note": "bench update", "source": "manual", "timestamp": "...",
 "silence_minutes": 15}

Equivalent to pushing a single deployment event. wolf-agent mark-deployment calls it (see Commands).

FieldMeaning
bench, siteScope of the deployment.
noteFree text.
sourceFor example manual.
timestampUTC.
silence_minutesOptional. Positive integer: also open a maintenance window.

silence_minutes was added after v1 and is backward compatible: older apps ignore it, and agents omit it unless --silence is given. When it is a positive integer, the app creates a Wolf Silence from now for that many minutes, capped at 24 h, scoped to the agent's host plus the given bench and site.

  • Incidents matching the silence still open and update, so the timeline stays complete.
  • Their notifications are held back.
  • Incidents still open when the window ends are notified then.

Response:

Response
{"message": {"event": "<Wolf Event name>", "silence": "WSIL-00001", "silence_until": "2026-10-29 02:15:00"}}

silence and silence_until (site time zone) are present only when a silence was created.

An agent that asked for a silence and gets no silence key back is talking to an app without silence support, and should warn.

Wolf health (heartbeat)

GET|POST /api/method/dodock_wolf.api.ingest.status
GET /api/method/dodock_wolf.api.ingest.status
X-Wolf-Agent-Id: WAG-0001
X-Wolf-Agent-Secret: <secret>

Response: {"message": {"agent": "WAG-0001", "push_interval": 30, "health": {...}}}.

The same health object comes back with every push, so the agent does not need to poll status. It is for wolf-agent check and scripts. The call is read-only: it does not update the agent's last seen time.

health
{
  "ok": false,
  "problems": ["alert rules not evaluated for 12 min; scheduler disabled (pause_scheduler)"],
  "checked_at": "2026-10-29T02:12:30Z",
  "server_version": "0.1.0",
  "rules": {"last_evaluated": "2026-10-29T02:00:01Z", "age_seconds": 749},
  "scheduler": {"enabled": false, "reason": "pause_scheduler",
                "last_job_run": "2026-10-29T02:00:00Z", "age_seconds": 750},
  "queues": {"lengths": {"short": 0, "default": 3, "long": 0}, "workers": 2,
             "ingest_queue": "short", "ingest_backlog_seconds": null}
}
FieldMeaning
rules.last_evaluatedLatest last_evaluated over enabled Wolf Alert Rules (the rule engine runs at each scheduler tick); null if no rule ran yet.
scheduler.enabled / reasonfalse with maintenance_mode, pause_scheduler, disable_scheduler or enable_scheduler unset in System Settings.
scheduler.last_job_runLatest Scheduled Job Type.last_execution, stamped when a worker starts a job.
scheduler.tick_secondsSeconds between Frappe scheduler ticks, so between two rule evaluations: 240 on Frappe 15 and Dodock unless scheduler_tick_interval is set; null on a Frappe without the setting. Informative, never a problem.
*.age_secondsServer-side now - timestamp, so agent clock skew does not matter. Negative when the stored time lies in the future, which happens after a system time-zone change and stalls the scheduler until that time.
queuesRQ queue lengths and worker count for the bench, or {"error": "..."} if Redis is unreachable.
queues.ingest_backlog_secondsHow long the oldest job of the ingest queue (ingest_queue) has waited; null when it is empty. Queued pushes are answered before they are stored, so this is the only sign that telemetry is not arriving.
ok / problemsThe server's own reading, with a 5 minute threshold.

Two things are problems:

  • staleness: abs(age) >= stale threshold on rules, or on scheduler when no rule is enabled;
  • ingest backlog: ingest_backlog_seconds >= stale threshold.

Scheduler and queue state are context appended to the staleness text. The agent applies its own threshold (watchdog.stale_minutes) to the raw ages rather than trusting ok.

While rules are stale, each push also records a host_metric_alert / scheduler_stalled event on the site, bumped rather than duplicated for 15 minutes. The Scheduler stalled preset turns it into an incident once the scheduler runs again. A stalled site cannot alert about itself, so the live alert is raised by the agent watchdog through its own fallback channel (see Watchdog).

Each native channel is a pure builder in dodock_wolf/wolf/channels/ that maps a notification to the documented format of the service. The module docstrings cite the reference pages. See Channels for setup.

Wolf Delivery

Every request is recorded as a Wolf Delivery:

FieldMeaning
incident, alert_ruleWhat was notified.
atWhen.
channel_typeSlack, Matrix, PagerDuty…
targetThe destination without secrets: host, room, masked phone numbers.
kind, action, digestWhat was sent.
ok, http_statusThe result.
errorThe error, with secrets and URL paths and queries removed.

Digests of native channels are merged on a SHA-256 of the channel settings, and the digest item keeps a reference to the channel row rather than any secret.
